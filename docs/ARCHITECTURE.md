# Архитектура DPpass

Срез на 4 октября 2026 (начало этапа 2: компилятор Xray, D-24). Решения, на которых держится
архитектура, — `docs/direction/DECISIONS.md`; здесь — как они разложены
по модулям и как через модули идут данные.

## 1. Обзор

```
            app/ (Android)                     cli/ (JVM)
   VpnService · Keystore · оболочка     команды · модель сети · замеры
                    \                         /
                     ─────── DPpassCore ──────            connection/
                    /     │         │        \
        активация (LKG)  план   оркестратор  отчёт
           │              │         │
   ┌───────┼──────────────┼─────────┼───────────────┐
 engine/  subscriptions/  network/  tunnel/      storage/
 граница   ревизии,       пробы,    TunnelSpec   атомарно,
 ядра,     ссылки,        бюджет,                шифрование,
 mock,     метаданные     классы                 карантин
 xray
   │          │                       │
   └────── config/ ──────────────────┘
        формат, IR, проверка
              │
          routing/  маршрутизация и DNS (смысл, эталонный вычислитель)
              │
           core/    IP, CIDR, хосты, строгий JSON, Clock, SHA-256
              │
        diagnostics/ коды, Outcome, Secret, Redactor, журнал, отчёт
```

Три свойства, которые держат эту схему:

1. **Ядро не знает Android** (D-02): всё ниже `app/` — чистый
   Kotlin/JVM, собирается и проверяется на хосте; `cli` — вторая
   оболочка над тем же `DPpassCore`.
2. **Домен не знает ядро прокси** (D-04): конфигурация — собственный IR
   (D-05), ядро — за `ProxyEngine`/`BackendCompiler` с матрицей
   возможностей.
3. **Всё, что может отказать, возвращает `Outcome`** с диагностикой и
   причинами (D-22); время — через `Clock` (D-21).

Правила, которые Gradle не выражает (`code.forbidden` DP Verify, правила
`android-import`, `simulation-import`, `mock-engine-import`, `native-load` —
`tools/dpverify.toml`, D-50):

- `android.*` — только в `app/`.
- Синтетическая модель сети (`network.simulation`), здоровье по ней
  (`connection.SimulatedHealthChecker`) и фиктивное ядро (`engine.mock`) —
  тестовые фикстуры Gradle (`src/testFixtures` модулей `network`,
  `connection`, `engine`): их берут тесты и `cli`
  (`testFixtures(project(":connection"))`), в основной код модулей и в APK
  они не попадают — импорт в `src/main` разрешён только `cli`, в APK их

- Нативный код (`external fun`, `System.load*`) — только мост ядра:
  объявления JNI — `engine.xray.XrayRuntime`, загрузка — `AppGraph` и тест
  JNI на хосте.

Сборка: convention-плагины в `build-logic/` (`dppass.kotlin-library`,
`dppass.kotlin-application`, `dppass.test-suite`, `dppass.android-app`),
версии — `gradle/libs.versions.toml`. Байт-код — Java 17 (его принимает
D8), инструменты — JDK 21, предупреждения компилятора — ошибки. Модуль
`app` подключается, только если найден Android SDK.

## 3. Потоки данных

### 3.1. Документ → активная конфигурация

```
текст ─► ConfigLoader.load
          размер ≤ 1 МиБ → строгий JSON (глубина ≤ 32, повтор ключа — ошибка)
          → format = "dppass.config" → Migrator (до текущей версии)
          → DocumentMapper (IR; неизвестное поле — ошибка)
          → Normalizer (только то, что не меняет смысл)
          → ConfigValidator (смысл, не зависящий от ядра)
       ─► LoadedConfig(ir, sha256 исходника, версия исходника)
       ─► ActivationService.activate
          VALIDATION (прочитается ли при следующем запуске: ConfigLoader)
          → CAPABILITY (матрица ядра) → COMPILE → BACKEND_VALIDATION
          → [HEALTH_CHECK] → COMMIT (одна атомарная запись)
       ─► ActivationResult.Activated | Rejected(шаг, причины)
```

Отказ на любом шаге оставляет действующую конфигурацию (D-07);
отвергнутый импорт не сохраняется — исходник у пользователя.

### 3.2. Подписка → новая ревизия

```
SubscriptionUpdater.update
  SubscriptionRequest (адрес, User-Agent DPpass, x-hwid — только с согласия, D-33)
  fetch (SubscriptionFetcher) → отказ по лимиту устройств? (x-hwid-*) → размер ≤ maxBytes → SHA-256
  → совпала с последней удачной? → Unchanged
  → PayloadDecoder: документ DPpass | список ссылок | base64 списка
  → MetadataParser: информационные поля применяются, директивы — нет (D-11)
  → ConfigValidator.validateProfile по каждой записи (пропуск — с причиной)
  → ProfileFilter (EngineProfileFilter: матрица ядра; исключение — с причиной)
  → маршрутизация/DNS поставщика — только при RoutingBinding.PROVIDER_ROUTING
  → Ready(кандидат) | Failed (lastFailed записан, lastSuccessful не тронут)
DPpassCore.activateSubscription(base, кандидат)
  → активация (3.1) → recordSuccess только при успехе (D-08)
```

В приложении это `SubscriptionService` (`connection/`, D-36): список
подписок — запись `subscriptions/state`, загрузка — `SourceFetcher`
(адрес — HTTPS, встроенный список своих серверов — без сети, D-42),
основа активации — `PolicyService.baseFor` (3.5). Итог —
`SubscriptionRun`: применилось ли, нужен ли переподключение (подключённого
сервера больше нет). Обновление по расписанию (D-39): `UpdateSchedule`
решает, пора ли (интервал подписки; после отказа — не раньше чем через
30 мин), `refreshDue` обновляет только активную подписку; задание
`SubscriptionJobService` (`app/`) — раз в час при любой сети.

### 3.3. Подключение

```
NetworkAssessor.assess  (пробы по одной, с бюджетом) → NetworkAssessment
CandidatePlanner.plan   (детерминированно, ≤ maxAttempts, с причинами) → ConnectionPlan
ConnectionOrchestrator.connect
  для каждой попытки (пауза между попытками):
    compile → engine.validate → engine.start → HealthChecker (полезная
    нагрузка, тайм-аут) → успех: Connected | отказ: stop, backoff в HealthBook
  → ConnectionReport (каждая попытка — причина из плана и исход)
Отказ в работе («подключено, но пусто»): ActivationService.rollback → предыдущая.
```

### 3.4. Туннель

`TunnelSpecBuilder.build(ir, selfPackage, PlatformTraits)` → `TunnelSpec`
(адреса `172.19.0.1/30` и `fdfe:dcba:9876::1/126`, маршруты, исключения
или дополнение маршрутов, DNS `172.19.0.2`, MTU, политика приложений,
IPv6) → `TunnelProvider.establish` (Android: `AndroidTunnelProvider`,
один к одному в `VpnService.Builder`) → `TunnelHandle(fd)` → `TunInput`
→ `ProxyEngine.start`. На Android это делает `DPpassVpnService`
(этап 2, работа 6): TUN поднимается, затем `DPpassCore.connect` перебирает
кандидатов плана. Каждый проверяется запросом DNS через сервер профиля к
DNS-серверу конфигурации (`XrayProxyEngine.probeHealth`, D-32). Ни один
не прошёл — TUN закрывается: без ядра он «съел» бы весь трафик
устройства. Остановка — сначала ядро, потом fd TUN (D-25).

### 3.5. Политика пользователя

`UserPolicy` (D-38) — что пользователь выбрал на экране «Настройки»:
режим маршрутизации (всё через туннель | российское напрямую | авто,
D-45), блок рекламы, DNS-резолвер, приложения (все | кроме | только),
IPv6. Запись `settings/policy` (документ `dppass.policy` v1; испорчена —
в карантин и политика по умолчанию). `PolicyBuilder` строит из неё
маршрутизацию и DNS IR: правило рекламы — первым, затем, в режиме
«российское напрямую», российские сайты (`geosite`) и адреса (`geoip`)
явными правилами. Режим «авто» (D-45) вместо явных правил включает
`automatic_domestic` — отечественное назначение уходит напрямую запасным
правилом после всех правил пользователя, без выбора сайтов; имена
российских сайтов в обоих режимах — системному резолверу. Источник
маршрутизации активной конфигурации:

```
активная конфигурация — свой документ пользователя (источник user-import)?
  да  → его маршрутизация и DNS (политика не применяется)
  нет → PolicyBuilder.ir(политика) — основа для подписок и смены политики
PolicyService.change(политика)
  → активные серверы + маршрутизация и DNS политики → активация (3.1)
  → сохраняется только при успехе; отказ — прежняя политика и конфигурация
```

### 3.6. Раздача туннеля

Другие устройства пользователя — по точке доступа, USB- или
Bluetooth-модему — ходят через туннель по прокси на телефоне (D-51):
Android ведёт трафик раздачи мимо `VpnService`.

```
ShareService.current()            — settings/share, dppass.share v2: включена ли, порт, логин, пароль,
                                    сопряжённые устройства со своими входами (D-56)
  выключена → без входов
  включена  → TetherInterfaces.find() дважды через 1,5 с, адреса из обоих снимков
                                        — поднят, широковещательный, частный IPv4,
                                          не сеть ConnectivityManager (не узнать — пусто)
            → ShareSettings.spec(адреса) → ShareSpec → CompilePlan.share
XrayCompiler: вход socks (+HTTP) с паролем на каждом адресе раздачи;
              первое правило — на входы раздачи только из подсетей раздачи
              и не с адресов телефона, остальное — block;
              «напрямую» раздачи — исходящий dppass:direct-share, закрытый
              для loopback телефона (копии правил direct для входов раздачи)
мост (D-25):  пропускает вход, кроме TUN, только такой (T11)
ConnectionOrchestrator: ядро с входами раздачи не запустилось → та же попытка
              без раздачи (ConnectionReport.Connected.shareRefused), сервер
              не наказан; отмена посреди проверки здоровья останавливает ядро
DPpassVpnService: опрос интерфейсов раз в 5 с, смена против предложенных
              адресов → переподключение
```

Правила пользователя, раздельный маршрут (D-45) и блокировка действуют
и для раздачи; правила по приложениям — нет (пакетов других устройств
DPpass не знает).

### 3.7. Подключение через устройство раздачи

Другой телефон с DPpass, который раздаёт свой туннель (§3.6), — сервер
особого вида (D-55): SOCKS5 с паролем на частном IPv4 своей сети.

```
RelayService            — settings/relays, dppass.relays v1: имя, адрес (null — шлюз), порт, логин, пароль
  добавить: вручную или ссылкой socks5://… («Поделиться входом» того телефона, импорт D-42)
выбор (AppPrefs.selectedRelay) → DPpassVpnService:
  RelayNetworks.locate  — шлюзы IPv4 сетей Wi-Fi, Bluetooth, Ethernet/USB (не VPN)
                          или сеть, в подсети которой явный адрес;
                          Socks5Login сокетом этой сети: принят → адрес и сеть
  DPpassCore.relayConfig — основа пользователя (свой документ или политика) + один профиль
  DPpassCore.connectVia  — план из одного кандидата (выбор пользователя), активация не меняется;
                           проверка здоровья не прошла — RELAY_UPSTREAM_FAILED (D-59): сбоит туннель того телефона
  защитник сокетов: protect + Network.bindSocket(сеть устройства); сеть под туннелем — она же
XrayCompiler: исходящий socks с user и pass (без надстроек транспорта)
```

Сопряжение по коду (D-56): хозяин — `PairingLink.acceptOne` на адресах
раздачи, порт 47521, две минуты, одно соединение; гость —
`PairingLink.connectToHost` на шлюзе своей сети; между ними `Pairing`
(P-256, обязательство, 6-значный код на обоих экранах, AES-GCM) →
`ShareService.pair` (свой вход) → `RelayService.add` у гостя.

В документе и подписке протокола `socks` нет (`DocumentMapper`), запись
в документ отвергается (`ConfigWriter`); адаптивная модель на классе
`LOCAL_RELAY` не обобщает.

### 3.8. Импорт

`ImportClassifier.classify(текст)` (D-42) — без сети и записи:
пусто | документ DPpass | адрес подписки (`https://`) | ссылки на
серверы (сколько годных из скольких, причины пропуска) | не распознано.
Источники в `app/`: буфер обмена, файл (≤ 1 МиБ), «Поделиться» текстом.
Ничего не применяется без подтверждения: документ — `importAndActivate`,
адрес — подписка, ссылки — подписка со встроенным списком (без
автообновления), `http://` — отказ с причиной.

## 4. Конфигурация и IR

Формат документа — `docs/CONFIG_FORMAT.md`. IR (`config/Ir.kt`):
`ConfigIr` = имя + профили + `RoutingPolicy` + `DnsPolicy`. Профиль —
id, имя, `Endpoint`, протокол (`Vless`, `Trojan`, `Shadowsocks`,
`Hysteria2`), транспорт (`Tcp`, `WebSocket`, `Grpc`, `XHttp`,
`HttpUpgrade`, `Native`), защита (`None`, `Tls`, `Reality`) и подсказки
(`priority`, `reachableUnderAllowlist`). Класс транспорта профиля
(`TCP_STREAM`, `HTTP_CDN`, `UDP_QUIC`) выводится из протокола и
транспорта — по нему политика подбирает кандидатов под сеть.

IR не содержит полей ни одного ядра; секреты в нём — `Secret`.
Проверка в два слоя: `ConfigValidator` — смысл, общий для всех ядер
(сочетания протокола, транспорта и защиты, форматы ключей, ссылки,
пределы); `CapabilityChecker` — что умеет конкретное ядро.

## 5. Маршрутизация и DNS

Модель — D-09, D-10. Эталонный смысл — `RouteEvaluator`: приложение вне
туннеля → `DIRECT` до всяких правил; затем первое сработавшее правило;
при `domain_resolution = if_no_domain_match` — повтор по IP после
резолва; при `automatic_domestic` (D-45) — запасное: отечественное
назначение (`geosite:category-ru`, `geoip:ru`) → `DIRECT` **после** всех
правил пользователя; иначе — действие по умолчанию. Используется для
объяснения решений, сверки компиляторов и тестов; трафик маршрутизирует
ядро (`XrayCompiler` добавляет те же два правила отдельными, не И, D-45).
Геоданные вычислителю даёт `GeoResolver`: в тестах — таблица, при
объяснении решения (`DPpassCore.explain` → `ProxyEngine.explain`) — набор
самого ядра (§6), поэтому объяснение не расходится с ядром (D-27).

`AppLowering` переносит **ведущие** правила «только приложения →
`direct`» в политику приложений `VpnService` (исключение из туннеля).
Правило с приложениями после правила с другими условиями перенести
нельзя (более раннее правило перестало бы действовать) — оно требует
от ядра `APP_RULES_IN_ENGINE`, иначе отказ.

`RoutingValidator` находит пустые, повторённые и затенённые правила
(достаточное условие тени: пропущенная тень — не ошибка, ложная — была
бы), и правила `proxy`/`block` для приложений вне туннеля. `DnsValidator`
проверяет ссылки на серверы, системный резолвер через туннель
(невозможно) и риск утечки (защита включена, а сервер по умолчанию —
напрямую).

## 6. Граница ядра

`EngineCapabilities` — матрица одной версии одного ядра: протоколы,
транспорты, защиты, flow, возможности (`APP_RULES_IN_ENGINE`,
`DOMAIN_RESOLUTION_IF_NO_MATCH`, `DNS_DOH`, `DNS_DOT`, `DNS_RULES`,
`GEOSITE`, `GEOIP`, `TUN_FD`, `NETWORK_CONDITION`). Смена версии ядра —
смена матрицы; `capabilityDiff` — обязательная часть обзора обновления
(D-18).

`BackendCompiler.compile(ir, CompilePlan)` → `CompiledConfig`
(содержимое с секретами не печатается, в журнале — SHA-256).
`ProxyEngine.validate` — проверка ядром без запуска; `start` → одна
`EngineSession` за раз; `explain` — решение `RouteEvaluator` на
геоданных этого ядра (у фиктивного геоданных нет — `GeoResolver.None`). Фиктивное ядро: `MockBackend.FULL` (всё из IR v1)
и `MockBackend.LIMITED` (без XHTTP, Hysteria2, DoT, правил DNS и
приложений в ядре) — второй бэкенд для доказательства абстракции.

**Xray** (`engine.xray`, D-24) — первое реальное ядро, версия 26.9.30.
`XrayBackend.CAPABILITIES` — всё из IR v1, кроме `DNS_DOT`,
`APP_RULES_IN_ENGINE` и `NETWORK_CONDITION`. `XrayCompiler` строит JSON
Xray так, чтобы смысл IR сохранился, а где Xray понял бы иначе или
молча проигнорировал — отказывает с путём (D-05):

- исходящие `proxy` (профиль), `direct` (`freedom`, имя резолвит DNS
  ядра по DnsPolicy без отката к системе), `block`, с TUN — `dns-out`;
  первым стоит исходящий действия по умолчанию — его Xray берёт, когда
  ни одно правило не сработало;
- правила: с раздачей (D-51) первым — `dppass:share-guard` (на входы
  раздачи только из подсетей раздачи и не с адресов телефона, остальное
  — `block`); перехват DNS из TUN (адрес `172.19.0.2:53` → `dns-out`),
  затем маршрут запросов каждого DNS-сервера, идущего через диспетчер
  ядра (по тегу сервера: через туннель или напрямую — до правил
  пользователя, T4), затем правила пользователя по порядку с
  `ruleTag` = id; правила, перенесённые `AppLowering` на уровень
  VpnService, в ядро не попадают;
- DNS: по записи сервера на правило DNS в порядке правил
  (`finalQuery`, `skipFallback`), сервер по умолчанию — единственный
  запасной: имя видит только сервер первого сработавшего правила;
- вход TUN с распознаванием имени только для маршрутизации
  (`routeOnly`); `domainStrategy` с TUN — всегда `AsIs` (у соединения
  из TUN всегда есть адрес);
- журнал ядра выключен (D-11); полей, выключающих проверку
  сертификата, нет (T5);
- у исходящего `proxy` нет `sockopt`: имя сервера резолвит система вне
  туннеля, а не DNS ядра (D-29).

Ядро в процессе (D-25): мост Go `tools/xray/bridge` (одно ядро на
процесс, входы — TUN и, при раздаче, SOCKS с паролем на адресах раздачи
(D-51), хук `protect()` с отказом, закрывающим
путь, счётчики `proxy`) и экспорт JNI `tools/xray/jni` →
`libdppassxray.so`; в Kotlin — `XrayRuntime` (`JniXrayRuntime`) и
`XrayProxyEngine`. `TunInput` несёт `SocketProtector`
(`TunnelHandle.protect`, на Android — `VpnService.protect`).
Библиотеку собирает `tools/xray/native.py` из того же `tools/xray/go.mod`:
для APK — задача `:app` `xrayNative<Вариант>` (NDK из каталога, три ABI,
выравнивание 16 КБ), для хоста — шаг «Xray: мост и JNI», где тот же мост
проверяет `XrayJniTest` в JVM хоста. Всё — в одном процессе
приложения, мост fd → ядро — вход TUN Xray (D-30). Геоданные — свой
набор из dlc и DB-IP в APK, переносится в `noBackupFilesDir/geodata`,
обновляется с приложением (D-27). Объяснение решения берёт geosite и
geoip у того же набора: `XrayGeoResolver` → `XrayRuntime.geoMatch` →
`bridge.GeoMatch`, тот же сопоставитель, что у маршрутизатора Xray
(`docs/research/BACKEND_STRATEGY.md`, §7); ядро для этого не
запускается. Что на устройстве ещё не проверено — `TODO.md`.

Компилятор проверяется на хосте самим ядром (`docs/TESTING.md`,

MTU и DNS-адрес TUN записаны и в `tunnel/`, и в `XrayBackend` (`engine`
от `tunnel` не зависит) — совпадение проверяет `XrayTunnelContractTest`.

## 7. Сеть

`network/` отвечает на вопрос «что сейчас пропускает эта сеть» (D-14).

**Пробы** (`ProbePlan.STANDARD`, от дешёвого к дорогому, отечественный
ориентир раньше зарубежного): CAPTIVE, DNS, TCP к отечественному; DNS,
TCP, TLS, UDP, BULK (передача > 32 КБ) к зарубежному у сети доставки; TCP,
TLS, UDP — ко второму зарубежному у другого поставщика (D-62), вперемежку
с первым. Перехват страницей входа прекращает прогон. Доступность TCP, TLS и
UDP в оценке — лучшее из двух зарубежных ориентиров.

**Исполнитель на сокетах** (`SocketProber`, D-60; сеть — `ProbeNetwork`:
на Android — сеть под туннелем, `app/NetworkCheck`). Ориентиры
(`Landmarks`): отечественный `ya.ru`, зарубежные `speed.cloudflare.com` и
`www.google.com` (D-62).
DNS — резолвером сети (только частные, служебные, нулевые адреса —
`DNS_TAMPERED`); TCP — соединение с 443; TLS — рукопожатие с платформенной
проверкой сертификата и имени (T5); UDP — QUICv1 Initial с SNI ориентира
(`QuicInitial`, RFC 9000/9001), прошло — любой ответ на наше соединение;
BULK — HTTPS 64 КБ, ≥ 32 КБ — прошло, встало после начала — `STALLED`,
ответ не 2xx — `INCONCLUSIVE`; CAPTIVE — сведения системы
(`NET_CAPABILITY_CAPTIVE_PORTAL`), своего HTTP-запроса нет. Запуск — только
по кнопке «Проверить сеть» (экран «Проверка сети»); итог — на экран и в
журнал без адресов, в план подключения он пока не идёт (D-60).

**Замер через туннель** (D-61): `bridge.SpeedTest` → `XrayJni.nativeSpeedTest`
→ `XrayProxyEngine.speedTest` (`XraySpeed`, `SpeedReport`). Через исходящий
`proxy` ядра, одно TLS-соединение к `speed.cloudflare.com`: 10 малых запросов
(пинг — медиана, jitter — среднее модулей разностей соседних) и загрузка не
больше 25 МБ и не дольше 8 с. По кнопке на экране «Проверка сети», только с
поднятым туннелем; пока идёт замер скорости или проверка сети и 15 с
после (`network.QuietWindow`), наблюдатель сессии пробы не начинает, а
начатую не учитывает.
После замера — пауза с отсчётом на кнопке (`network.Cooldown`: 60 с, после
отказа 15 с); у проверки сети пауза — из бюджета проб (`ProbeBudget.waitForMillis`).
Время последнего байта загрузки отличает вставшие данные (L7) от медленного
канала: тишина ≥ 2 с до конца срока — «данные встали через N с».

**Бюджет** (`ProbeBudget`): к одному ориентиру — не чаще раза в 1,5 с,
всего — не больше 12 проб за 60 с. Проба, не допущенная бюджетом, —
`SKIPPED`, это не наблюдение о сети.

**Исход → доступность:** `SUCCESS` → OK; `STALLED`, `DNS_TAMPERED` →
DEGRADED; `SKIPPED`, `INCONCLUSIVE` или нет пробы → UNKNOWN; прочее →
BLOCKED. `SKIPPED` и `INCONCLUSIVE` в число проведённых проб не входят.

**Классификация** (`NetworkClassifier`; правила по порядку, первое
сработавшее решает; каждое срабатывание пишет строку в `evidence`):

| # | Условие | Класс | Уверенность |
|---|---|---|---|
| 1 | система сообщает: сети нет | `OFFLINE` | высокая |
| 2 | страница входа (по сведениям системы, D-60; в модели — HTTP перенаправлен) | `CAPTIVE` | высокая |
| 3 | отечественный ориентир не отвечает (и это известно), зарубежные DNS/TCP/TLS — ни одного OK/DEGRADED | `OFFLINE` | высокая, если зарубежные все BLOCKED, иначе средняя |
| 4 | отечественный доступен, зарубежные TCP и TLS — BLOCKED (у обоих ориентиров); DNS BLOCKED обязателен, только если зарубежный ориентир один (D-62) | `ALLOWLIST_LIKE` | высокая, если и DNS, и UDP BLOCKED, иначе средняя |
| 5 | проведено меньше 4 проб; или зарубежные TCP и TLS не проверены (пропуск бюджета — не вывод, 17.10.2026) | `UNKNOWN` | низкая |
| 6 | хотя бы один признак: зарубежный DNS не OK; TCP OK, а TLS нет; зарубежный TCP BLOCKED при живом отечественном; один зарубежный ориентир закрыт по TCP или TLS, другой открыт — закрыты адреса поставщика (L4, D-62); крупная передача остановилась; медиана задержки > 1500 мс | `DEGRADED` | высокая при ≥ 2 признаках, иначе средняя |
| 7 | иначе | `NORMAL` | средняя, если хоть одна зарубежная проба не проверена, иначе высокая |

Блокировка UDP при рабочем TCP — наблюдение (`udp = BLOCKED`), а не
класс: планировщик исключает UDP/QUIC-кандидатов, остальное работает.
Проверяется `NetworkClassifierTest` (`network/`) и корпусом условий
сети; изменение правил — изменение таблицы, тестов и корпуса вместе.

**Модель сети для тестов** (`network.simulation.SimulatedNetwork`,
тестовая фикстура `network`) — синтетические условия (`docs/TESTING.md`,
«Модель сети»), не снимки операторов.

## 8. Подключение

`ConnectionPolicy` (ориентиры первой версии, меняются по замерам):
до 4 кандидатов за подключение, пауза 2 с между попытками, проверка
здоровья — до 10 с, пауза кандидата после отказа — 30 с × 2ⁿ⁻¹, не
больше 30 мин.

`CandidatePlanner` (D-15): при `OFFLINE`/`CAPTIVE` попыток нет (вердикт
с причиной); исключаются неподдержанные ядром, неотмеченные при
`ALLOWLIST_LIKE` (D-13), UDP/QUIC при заблокированном UDP, кандидаты на
паузе. Порядок: выбор пользователя → last-known-good → здоровье (здоров,
не проверялся, отказывал) → **выученная устойчивость (D-44)** → штраф
TCP-потока, если режутся TLS или крупные передачи → приоритет → задержка,
если измерена (D-41) → id; соседние попытки — по возможности разных классов
транспорта. `HealthBook.lastGood()` — кандидат, который последним
**передал данные**, а не просто был активирован.

Задержка (D-41) — время установки TCP-соединения до сервера, только по
действию пользователя: `LatencyBook.measureAll` идёт по серверам по
одному с паузой 150 мс, тайм-аут 3 с, не больше 128 за прогон; UDP-серверы
(Hysteria2) не измеряются. `TcpLatencyProbe` (`network/`) — единственное
место вне ядра, где разрешается имя сервера; результат живёт в памяти
процесса и не сохраняется.

### 8.1. Адаптивная устойчивость (D-44)

`StabilityModel` учится на исходах попыток и проб здоровья (D-32) по паре
«грубый контекст сети, сервер» (`NetworkContext` — тип сети и класс
ограничения, без идентификаторов, T14). По каждой паре — затухающий
агрегат `StabilityStats`: надёжность Beta с априором и полураспадом
(нижняя граница доверия, пессимизм), SRTT/RTTVAR (RFC 6298), джиттер
(RFC 3550), EWMA «замерзаний», накопитель Пейджа — Хинкли (смена режима).
Оценка `0.55·надёжность + 0.25·джиттер + 0.12·задержка + 0.08·стабильность`
— устойчивость, не скорость. `TransportAdvisor` — один слой
(логистическая регрессия), переносит опыт класса транспорта на серверы
без своей истории. `CandidatePlanner` берёт оценку как сигнал порядка —
жёсткие исключения и выбор пользователя она не трогает.
`SessionSupervisor` (чистая логика) по потоку наблюдений решает
«держать/переподключиться» с гистерезисом и пределом переключений в час;
на устройстве его кормит `DPpassVpnService` пробами D-32, переподключение
не закрывает TUN. Хранение — `StabilityBook` в зашифрованном хранилище
(`adaptive/state`, D-19); повреждение — карантин (D-06).

Подтверждённая деградация (D-58) — `DPpassCore.degraded`: отказ в
`HealthBook` (сервер перестаёт быть «последним удачным» и уходит на
паузу) и ответ `Degradation` — переподключиться по плану, спросить о
замене выбранного пользователем сервера (`Ask`) или заменить его с
согласием заранее (`Switch`, тумблер «Автопереключение»). Замена —
первый кандидат плана без выбора пользователя; устройство раздачи (D-55)
и единственный сервер не заменяются.

## 9. Хранение

`BlobStore` — «ключ → байты», ключ — сегменты `[a-z0-9._-]` через `/`
(без `..`). `FileBlobStore`: временный файл → fsync → `ATOMIC_MOVE`;
без атомарной замены — отказ, а не неатомарная запись.
`EncryptingBlobStore` (D-19): `1 | nonce(12) | AES-256-GCM(данные) | тег(16)`,
дополнительные данные — ключ записи; подмена или порча записи →
`STORAGE_CORRUPTED`.

Ключ данных — `WrappedKeyProvider` (`storage/`): конверт из 32 случайных
байт, обёрнутых неизвлекаемым ключом (`KeyWrapper`; на Android —
`KeystoreKeyWrapper` в Keystore), обёрнутый ключ — записью своего
`FileBlobStore` (атомарно). Отказ ключа — не порча записи, а свой код:
`STORAGE_DATA_KEY_UNAVAILABLE` (временный: ничего не записано, следующий
вызов пробует снова) или `STORAGE_DATA_KEY_LOST` (ключ-обёртки нет,
обёрнутый ключ испорчен, или его нет при существующих записях). Новый
ключ поверх существующих записей молча не создаётся; ключ, который не
удалось сохранить, не используется.

Сохранённое не затирается непрочитанным: `ActivationService` пишет,
только когда состояние прочитано (или повреждённое отложено в
карантин); иначе активация и откат отказывают с причиной, а перед
следующей записью чтение повторяется. Выход при утрате ключа —
`DPpassCore.resetStorage()` действием пользователя (`StorageReset`):
все записи и обёрнутый ключ переносятся как есть в `lost/<время>/`,
ничего не удаляется, ключ создаётся заново.

Записи: `activation/state` — состояние активации документом
`dppass.activation` v1 (записи активной и предыдущей конфигурации,
сами конфигурации в полном виде, история до 32 записей). Нечитаемая
запись об активной или предыдущей конфигурации — состояние не цельное,
весь документ — в карантин; нечитаемая запись истории пропускается с
находкой `STORAGE_CORRUPTED` и местом; без читаемого `next_revision`
счёт ревизий продолжается после самой поздней записи, а не с 1;
`subscriptions/state` — подписки (`SubscriptionCodec`, версия 3:
источник — адрес или встроенный список, интервал автообновления,
последняя удача и отказ, признак «имя задал пользователь», D-53); `settings/policy` — политика пользователя
(`dppass.policy` v1, D-38); `settings/share` — раздача туннеля
(`dppass.share` v2, D-51, D-56: включена ли, порт, логин и пароль,
сопряжённые устройства со своими входами; версия 1 читается без них; не
читается — карантин, раздача выключена, пароль новый);
`settings/relays` — устройства раздачи (`dppass.relays` v1, D-55: имя,
адрес или шлюз, порт, логин и пароль; не читается — карантин, список
пуст);
`quarantine/<вид>-<время>.data` и `.reason` — то, что DPpass хранил и не
смог прочитать (D-06); `lost/<время>/…` — отложенное сбросом хранилища.

## 10. Диагностика

Контракт (D-22):

- `FailureKind` — категория для пользователя («что сломалось»,
  18 значений: сеть, DNS, разбор, формат, проверка, возможности ядра,
  компиляция маршрутов, проверка ядром, запуск ядра, TUN, сервер, TLS,
  аутентификация, здоровье, загрузка подписки, подписка, хранение,
  внутренняя). Набор закрыт и мал.
- `DiagCode` — стабильный код с категорией и серьёзностью по умолчанию.
  **Коды не переименовываются и не удаляются, только добавляются**: по
  именам написаны ожидания корпуса и будут написаны переводы сообщений.
- `Diagnostic` — код, серьёзность, сообщение без секретов, путь в
  документе (`$.profiles[0].port`), причины (`causes`), сводка исключения
  (`ErrorSummary`: тип и отредактированное сообщение, без стека).
- `Outcome<T>` — `Success(value, находки)` или `Failure(находки ≥ 1
  ошибки)`; `then`/`map` складывают находки шагов, ничего не теряя.

Журнал: `Logger` пишет события «имя + поля»; строковые поля проходят
`Redactor` до приёмника, `Secret` становится меткой, явно безопасное —
`Safe`. `Redactor.STANDARD` убирает UUID, пути и учётные данные ссылок,
пары «секретное имя = значение», длинные токены; `STRICT` (для отчёта,
который пользователь кому-то отдаёт) — ещё IP и хосты. Отчёт
`DiagnosticReport` собирается локально и при выводе ещё раз проходит
`STRICT` (D-12).

Журнал на устройстве (D-26): `TeeLogSink` отдаёт событие кольцу в
памяти (`LogHistory` — источник отчёта) и `FileLogSink` — файлу в
`noBackupFilesDir/log`, который пишется в фоне (очередь с пределом,
части по 1 МиБ, начало сеанса, прошлый сеанс). `CrashRecord` — запись
о падении: синхронно, мимо выключателя. `LogExport` — текст для буфера
обмена: падение, начало и хвост сеанса в пределах ~120 тыс. символов,
`STRICT`; журнал в файл выключен — текущий сеанс из кольца памяти (D-54).

## 11. Android-слой

`app/` (D-17, D-19): `AppGraph` — единственное место, где Android
встречается с ядром (хранилище в `noBackupFilesDir`, Keystore, ядро Xray —
`XrayCompiler` и `XrayProxyEngine` поверх `libdppassxray` из APK, набор
геоданных — перенос в `noBackupFilesDir/geodata`, `PlatformTraits` по версии API).
Библиотека не загрузилась или не той версии — каждый вызов ядра отвечает
`BACKEND_NOT_AVAILABLE` с причиной. `DPpassVpnService` — foreground
`specialUse`, уведомление; поднимает TUN и подключает ядро (§3.4),
останавливается действием «Остановить», при `onRevoke` и в `onDestroy`
(уборка — в области процесса `AppGraph.scope`); пока туннель поднят —
наблюдатель сессии (D-44) снимает пробу D-32 и при подтверждённой
деградации переподключает, не закрывая TUN; о сбое выбранного сервера
спрашивает `ServerSwitch` — уведомлением канала «Смена сервера» с кнопками
«Перейти» и «Остаться» (действия сервиса `SWITCH_SERVER`, `KEEP_SERVER`) и
карточкой экрана «Подключение» (`TunnelState.offer`), на заблокированном
экране — без имён и кнопок (D-58, T9). `AndroidTunnelProvider` — `TunnelSpec` → `Builder`;
адреса — `InetAddress.getByAddress` (без DNS). `MainActivity` —
интерфейс (D-34): одна `Activity` с `FLAG_SECURE`, экраны — классы
`Screen` пакета `app.ui` на встроенных Views, логика экранов без Android —
`ui/Presentation.kt` и `ui/Explain.kt` (тесты на хосте в `app/src/test`).
Экраны «почему» (этап 4): «Почему этот сервер» — план D-15 последнего
подключения с исходами попыток (сервис кладёт его в `TunnelState.plan`) и
план следующего (`DPpassCore.plan`); «Почему этот маршрут» — ответ
`DPpassCore.explain` по активной конфигурации с правилом политики по его
постоянному id (D-38), локальные сети — по `TunnelSpecBuilder.LAN`;
«История активаций» — записи D-07 с источником, суммой и шагом отказа. Окна диалогов и
нижних листов — `FLAG_SECURE` через `Ui.secure`, критичные элементы —
`filterTouchesWhenObscured` (T9, T13, D-47). Состояние туннеля
для экранов и уведомления — `TunnelState` (одно на процесс, его меняет
только сервис); выбранный сервер и автопереключение — `AppPrefs`, сервис
ставит выбранный первым в план (D-34) и заменяет его только с согласия
пользователя (D-58). Уведомление сервиса — состояние, сервер и кнопка
«Отключить»; на заблокированном экране — без имени сервера (T9). `DPpassApplication` первым делом
включает журнал устройства `DeviceLog` (D-26): файл в фоне, запись о
падении; наружу журнал уходит только кнопкой «Копировать журнал» (D-47:
автокопии нет), переключатель журнала — в оболочке. Личность установки
(`applicationId` и ярлык) у личной сборки случайна (`AppIdentity`, D-47);
пространство имён кода — всегда `com.dpsmpx.dppass`. Манифест и сетевые настройки
проверяет `check_manifest.py`; API модулей ядра — `check_android_api.py`;
собранный APK, в том числе нативный код (только `libdppassxray.so` трёх
ABI, несжатая, выровнена по 16 КБ), — `check_apk.py`.

## 12. Время, потоки, детерминизм

- Время — `Clock` (`Clock.SYSTEM` на устройстве, `ManualClock` в
  тестах и `cli`); ожидание — переданной функцией `pause`, в тестах
  она двигает `ManualClock` без сна (D-21).
- Корутины: `suspend` на границах ядра, проб, проверки здоровья и
  загрузки; `withTimeoutOrNull` для проверки здоровья; `runBlocking` —
  только в `cli`.
- Состояние активации меняется только через `commit` после успешной
  записи: что не сохранено, то не активировано.
- Планировщик, классификатор, нормализация и компилятор детерминированы:
  одинаковый вход даёт одинаковый результат (проверяется тестами).
