# Архитектура DPpass

Срез на 4 октября 2026 (начало этапа 2: компилятор Xray, D-24). Решения, на которых держится
архитектура, — `docs/direction/DECISIONS.md`; здесь — как они разложены
по модулям и как через модули идут данные.

## 1. Обзор

```
            app/ (Android)                     cli/ (JVM)
   VpnService · Keystore · оболочка     команды · модель сети · замеры
                    \                         /
                     ─────── DPpassCore ──────            connection/
                    /     │         │        \
        активация (LKG)  план   оркестратор  отчёт
           │              │         │
   ┌───────┼──────────────┼─────────┼───────────────┐
 engine/  subscriptions/  network/  tunnel/      storage/
 граница   ревизии,       пробы,    TunnelSpec   атомарно,
 ядра,     ссылки,        бюджет,                шифрование,
 mock,     метаданные     классы                 карантин
 xray
   │          │                       │
   └────── config/ ──────────────────┘
        формат, IR, проверка
              │
          routing/  маршрутизация и DNS (смысл, эталонный вычислитель)
              │
           core/    IP, CIDR, хосты, строгий JSON, Clock, SHA-256
              │
        diagnostics/ коды, Outcome, Secret, Redactor, журнал, отчёт
```

Три свойства, которые держат эту схему:

1. **Ядро не знает Android** (D-02): всё ниже `app/` — чистый
   Kotlin/JVM, собирается и проверяется на хосте; `cli` — вторая
   оболочка над тем же `DPpassCore`.
2. **Домен не знает ядро прокси** (D-04): конфигурация — собственный IR
   (D-05), ядро — за `ProxyEngine`/`BackendCompiler` с матрицей
   возможностей.
3. **Всё, что может отказать, возвращает `Outcome`** с диагностикой и
   причинами (D-22); время — через `Clock` (D-21).

Правила, которые Gradle не выражает (тоже `check_modules.py`):

- `android.*` — только в `app/`.
- Синтетическая модель сети (`network.simulation`) — инструмент тестов и
  `cli`; в основном коде `connection/` — только `SimulatedHealthChecker`
  (`Orchestrator.kt`); в `app/` — нельзя.
- Фиктивное ядро (`engine.mock`) — второй бэкенд тестов и `cli`; в
  `app/` — нельзя: приложение работает на Xray (D-25).
- Нативный код (`external fun`, `System.load*`) — только мост ядра:
  объявления JNI — `engine.xray.XrayRuntime`, загрузка — `AppGraph` и тест
  JNI на хосте (`check_forbidden_apis.py`, правило `native-load`).

Сборка: convention-плагины в `build-logic/` (`dppass.kotlin-library`,
`dppass.kotlin-application`, `dppass.test-suite`, `dppass.android-app`),
версии — `gradle/libs.versions.toml`. Байт-код — Java 17 (его принимает
D8), инструменты — JDK 21, предупреждения компилятора — ошибки. Модуль
`app` подключается, только если найден Android SDK.

## 3. Потоки данных

### 3.1. Документ → активная конфигурация

```
текст ─► ConfigLoader.load
          размер ≤ 1 МиБ → строгий JSON (глубина ≤ 32, повтор ключа — ошибка)
          → format = "dppass.config" → Migrator (до текущей версии)
          → DocumentMapper (IR; неизвестное поле — ошибка)
          → Normalizer (только то, что не меняет смысл)
          → ConfigValidator (смысл, не зависящий от ядра)
       ─► LoadedConfig(ir, sha256 исходника, версия исходника)
       ─► ActivationService.activate
          CAPABILITY (матрица ядра) → COMPILE → BACKEND_VALIDATION
          → [HEALTH_CHECK] → COMMIT (одна атомарная запись)
       ─► ActivationResult.Activated | Rejected(шаг, причины)
```

Отказ на любом шаге оставляет действующую конфигурацию (D-07);
отвергнутый импорт не сохраняется — исходник у пользователя.

### 3.2. Подписка → новая ревизия

```
SubscriptionUpdater.update
  fetch (SubscriptionFetcher) → размер ≤ maxBytes → SHA-256
  → совпала с последней удачной? → Unchanged
  → PayloadDecoder: документ DPpass | список ссылок | base64 списка
  → MetadataParser: информационные поля применяются, директивы — нет (D-11)
  → ConfigValidator.validateProfile по каждой записи (пропуск — с причиной)
  → ProfileFilter (EngineProfileFilter: матрица ядра; исключение — с причиной)
  → маршрутизация/DNS поставщика — только при RoutingBinding.PROVIDER_ROUTING
  → Ready(кандидат) | Failed (lastFailed записан, lastSuccessful не тронут)
DPpassCore.activateSubscription(base, кандидат)
  → активация (3.1) → recordSuccess только при успехе (D-08)
```

### 3.3. Подключение

```
NetworkAssessor.assess  (пробы по одной, с бюджетом) → NetworkAssessment
CandidatePlanner.plan   (детерминированно, ≤ maxAttempts, с причинами) → ConnectionPlan
ConnectionOrchestrator.connect
  для каждой попытки (пауза между попытками):
    compile → engine.validate → engine.start → HealthChecker (полезная
    нагрузка, тайм-аут) → успех: Connected | отказ: stop, backoff в HealthBook
  → ConnectionReport (каждая попытка — причина из плана и исход)
Отказ в работе («подключено, но пусто»): ActivationService.rollback → предыдущая.
```

### 3.4. Туннель

`TunnelSpecBuilder.build(ir, selfPackage, PlatformTraits)` → `TunnelSpec`
(адреса `172.19.0.1/30` и `fdfe:dcba:9876::1/126`, маршруты, исключения
или дополнение маршрутов, DNS `172.19.0.2`, MTU, политика приложений,
IPv6) → `TunnelProvider.establish` (Android: `AndroidTunnelProvider`,
один к одному в `VpnService.Builder`) → `TunnelHandle(fd)` → `TunInput`
→ `ProxyEngine.start`. На Android это делает `DPpassVpnService`
(этап 2, работа 6): TUN поднимается, затем `DPpassCore.connect` перебирает
кандидатов плана. Каждый проверяется запросом DNS через сервер профиля к
DNS-серверу конфигурации (`XrayProxyEngine.probeHealth`, D-32). Ни один
не прошёл — TUN закрывается: без ядра он «съел» бы весь трафик
устройства. Остановка — сначала ядро, потом fd TUN (D-25).

## 4. Конфигурация и IR

Формат документа — `docs/CONFIG_FORMAT.md`. IR (`config/Ir.kt`):
`ConfigIr` = имя + профили + `RoutingPolicy` + `DnsPolicy`. Профиль —
id, имя, `Endpoint`, протокол (`Vless`, `Trojan`, `Shadowsocks`,
`Hysteria2`), транспорт (`Tcp`, `WebSocket`, `Grpc`, `XHttp`,
`HttpUpgrade`, `Native`), защита (`None`, `Tls`, `Reality`) и подсказки
(`priority`, `reachableUnderAllowlist`). Класс транспорта профиля
(`TCP_STREAM`, `HTTP_CDN`, `UDP_QUIC`) выводится из протокола и
транспорта — по нему политика подбирает кандидатов под сеть.

IR не содержит полей ни одного ядра; секреты в нём — `Secret`.
Проверка в два слоя: `ConfigValidator` — смысл, общий для всех ядер
(сочетания протокола, транспорта и защиты, форматы ключей, ссылки,
пределы); `CapabilityChecker` — что умеет конкретное ядро.

## 5. Маршрутизация и DNS

Модель — D-09, D-10. Эталонный смысл — `RouteEvaluator`: приложение вне
туннеля → `DIRECT` до всяких правил; затем первое сработавшее правило;
при `domain_resolution = if_no_domain_match` — повтор по IP после
резолва; иначе — действие по умолчанию. Используется для объяснения
решений, сверки компиляторов и тестов; трафик маршрутизирует ядро.

`AppLowering` переносит **ведущие** правила «только приложения →
`direct`» в политику приложений `VpnService` (исключение из туннеля).
Правило с приложениями после правила с другими условиями перенести
нельзя (более раннее правило перестало бы действовать) — оно требует
от ядра `APP_RULES_IN_ENGINE`, иначе отказ.

`RoutingValidator` находит пустые, повторённые и затенённые правила
(достаточное условие тени: пропущенная тень — не ошибка, ложная — была
бы), и правила `proxy`/`block` для приложений вне туннеля. `DnsValidator`
проверяет ссылки на серверы, системный резолвер через туннель
(невозможно) и риск утечки (защита включена, а сервер по умолчанию —
напрямую).

## 6. Граница ядра

`EngineCapabilities` — матрица одной версии одного ядра: протоколы,
транспорты, защиты, flow, возможности (`APP_RULES_IN_ENGINE`,
`DOMAIN_RESOLUTION_IF_NO_MATCH`, `DNS_DOH`, `DNS_DOT`, `DNS_RULES`,
`GEOSITE`, `GEOIP`, `TUN_FD`, `NETWORK_CONDITION`). Смена версии ядра —
смена матрицы; `capabilityDiff` — обязательная часть обзора обновления
(D-18).

`BackendCompiler.compile(ir, CompilePlan)` → `CompiledConfig`
(содержимое с секретами не печатается, в журнале — SHA-256).
`ProxyEngine.validate` — проверка ядром без запуска; `start` → одна
`EngineSession` за раз. Фиктивное ядро: `MockBackend.FULL` (всё из IR v1)
и `MockBackend.LIMITED` (без XHTTP, Hysteria2, DoT, правил DNS и
приложений в ядре) — второй бэкенд для доказательства абстракции.

**Xray** (`engine.xray`, D-24) — первое реальное ядро, версия 26.9.30.
`XrayBackend.CAPABILITIES` — всё из IR v1, кроме `DNS_DOT`,
`APP_RULES_IN_ENGINE` и `NETWORK_CONDITION`. `XrayCompiler` строит JSON
Xray так, чтобы смысл IR сохранился, а где Xray понял бы иначе или
молча проигнорировал — отказывает с путём (D-05):

- исходящие `proxy` (профиль), `direct` (`freedom`, имя резолвит DNS
  ядра по DnsPolicy без отката к системе), `block`, с TUN — `dns-out`;
  первым стоит исходящий действия по умолчанию — его Xray берёт, когда
  ни одно правило не сработало;
- правила: перехват DNS из TUN (адрес `172.19.0.2:53` → `dns-out`),
  затем маршрут запросов каждого DNS-сервера, идущего через диспетчер
  ядра (по тегу сервера: через туннель или напрямую — до правил
  пользователя, T4), затем правила пользователя по порядку с
  `ruleTag` = id; правила, перенесённые `AppLowering` на уровень
  VpnService, в ядро не попадают;
- DNS: по записи сервера на правило DNS в порядке правил
  (`finalQuery`, `skipFallback`), сервер по умолчанию — единственный
  запасной: имя видит только сервер первого сработавшего правила;
- вход TUN с распознаванием имени только для маршрутизации
  (`routeOnly`); `domainStrategy` с TUN — всегда `AsIs` (у соединения
  из TUN всегда есть адрес);
- журнал ядра выключен (D-11); полей, выключающих проверку
  сертификата, нет (T5);
- у исходящего `proxy` нет `sockopt`: имя сервера резолвит система вне
  туннеля, а не DNS ядра (D-29).

Ядро в процессе (D-25): мост Go `tools/xray/bridge` (одно ядро на
процесс, входы — только TUN, хук `protect()` с отказом, закрывающим
путь, счётчики `proxy`) и экспорт JNI `tools/xray/jni` →
`libdppassxray.so`; в Kotlin — `XrayRuntime` (`JniXrayRuntime`) и
`XrayProxyEngine`. `TunInput` несёт `SocketProtector`
(`TunnelHandle.protect`, на Android — `VpnService.protect`).
Библиотеку собирает `tools/xray/native.py` из того же `tools/xray/go.mod`:
для APK — задача `:app` `xrayNative<Вариант>` (NDK из каталога, три ABI,
выравнивание 16 КБ), для хоста — шаг «Xray: мост и JNI», где тот же мост
проверяет `XrayJniTest` в JVM хоста. Всё — в одном процессе
приложения, мост fd → ядро — вход TUN Xray (D-30). Геоданные — свой
набор из dlc и DB-IP в APK, переносится в `noBackupFilesDir/geodata`,
обновляется с приложением (D-27). Что на устройстве ещё не проверено —
`TODO.md`.

Компилятор проверяется на хосте самим ядром (`docs/TESTING.md`,
«Эталоны Xray»): `tools/xray` — модуль Go вне сборки Gradle, собирает
upstream `xray` и `dppass-xray-probe` из `tools/xray/go.mod`.
MTU и DNS-адрес TUN записаны и в `tunnel/`, и в `XrayBackend` (`engine`
от `tunnel` не зависит) — совпадение проверяет `XrayTunnelContractTest`.

## 7. Сеть

`network/` отвечает на вопрос «что сейчас пропускает эта сеть» (D-14).

**Пробы** (`ProbePlan.STANDARD`, от дешёвого к дорогому, отечественный
ориентир раньше зарубежного): CAPTIVE, DNS, TCP к отечественному; DNS,
TCP, TLS, UDP, BULK (передача > 32 КБ) к зарубежному. Перехват страницей
входа прекращает прогон.

**Бюджет** (`ProbeBudget`): к одному ориентиру — не чаще раза в 1,5 с,
всего — не больше 12 проб за 60 с. Проба, не допущенная бюджетом, —
`SKIPPED`, это не наблюдение о сети.

**Исход → доступность:** `SUCCESS` → OK; `STALLED`, `DNS_TAMPERED` →
DEGRADED; `SKIPPED` или нет пробы → UNKNOWN; прочее → BLOCKED.

**Классификация** (`NetworkClassifier`; правила по порядку, первое
сработавшее решает; каждое срабатывание пишет строку в `evidence`):

| # | Условие | Класс | Уверенность |
|---|---|---|---|
| 1 | система сообщает: сети нет | `OFFLINE` | высокая |
| 2 | HTTP-проверка перенаправлена | `CAPTIVE` | высокая |
| 3 | отечественный ориентир не отвечает (и это известно), зарубежные DNS/TCP/TLS — ни одного OK/DEGRADED | `OFFLINE` | высокая, если зарубежные все BLOCKED, иначе средняя |
| 4 | отечественный доступен, зарубежные DNS, TCP и TLS — все BLOCKED | `ALLOWLIST_LIKE` | высокая, если и UDP BLOCKED, иначе средняя |
| 5 | проведено меньше 4 проб | `UNKNOWN` | низкая |
| 6 | хотя бы один признак: зарубежный DNS не OK; TCP OK, а TLS нет; зарубежный TCP BLOCKED при живом отечественном; крупная передача остановилась; медиана задержки > 1500 мс | `DEGRADED` | высокая при ≥ 2 признаках, иначе средняя |
| 7 | иначе | `NORMAL` | средняя, если UDP неизвестен, иначе высокая |

Блокировка UDP при рабочем TCP — наблюдение (`udp = BLOCKED`), а не
класс: планировщик исключает UDP/QUIC-кандидатов, остальное работает.
Проверяется `NetworkClassifierTest` (`network/`) и корпусом условий
сети; изменение правил — изменение таблицы, тестов и корпуса вместе.

**Модель сети для тестов** (`network.simulation.SimulatedNetwork`) —
синтетические условия (`docs/TESTING.md`, «Модель сети»), не снимки
операторов.

## 8. Подключение

`ConnectionPolicy` (ориентиры первой версии, меняются по замерам):
до 4 кандидатов за подключение, пауза 2 с между попытками, проверка
здоровья — до 10 с, пауза кандидата после отказа — 30 с × 2ⁿ⁻¹, не
больше 30 мин.

`CandidatePlanner` (D-15): при `OFFLINE`/`CAPTIVE` попыток нет (вердикт
с причиной); исключаются неподдержанные ядром, неотмеченные при
`ALLOWLIST_LIKE` (D-13), UDP/QUIC при заблокированном UDP, кандидаты на
паузе. Порядок: last-known-good → здоровье (здоров, не проверялся,
отказывал) → штраф TCP-потока, если режутся TLS или крупные передачи →
приоритет → id; соседние попытки — по возможности разных классов
транспорта. `HealthBook.lastGood()` — кандидат, который последним
**передал данные**, а не просто был активирован.

## 9. Хранение

`BlobStore` — «ключ → байты», ключ — сегменты `[a-z0-9._-]` через `/`
(без `..`). `FileBlobStore`: временный файл → fsync → `ATOMIC_MOVE`;
без атомарной замены — отказ, а не неатомарная запись.
`EncryptingBlobStore` (D-19): `1 | nonce(12) | AES-256-GCM(данные) | тег(16)`,
дополнительные данные — ключ записи; подмена или порча записи →
`STORAGE_CORRUPTED`.

Ключ данных — `WrappedKeyProvider` (`storage/`): конверт из 32 случайных
байт, обёрнутых неизвлекаемым ключом (`KeyWrapper`; на Android —
`KeystoreKeyWrapper` в Keystore), обёрнутый ключ — записью своего
`FileBlobStore` (атомарно). Отказ ключа — не порча записи, а свой код:
`STORAGE_DATA_KEY_UNAVAILABLE` (временный: ничего не записано, следующий
вызов пробует снова) или `STORAGE_DATA_KEY_LOST` (ключ-обёртки нет,
обёрнутый ключ испорчен, или его нет при существующих записях). Новый
ключ поверх существующих записей молча не создаётся; ключ, который не
удалось сохранить, не используется.

Сохранённое не затирается непрочитанным: `ActivationService` пишет,
только когда состояние прочитано (или повреждённое отложено в
карантин); иначе активация и откат отказывают с причиной, а перед
следующей записью чтение повторяется. Выход при утрате ключа —
`DPpassCore.resetStorage()` действием пользователя (`StorageReset`):
все записи и обёрнутый ключ переносятся как есть в `lost/<время>/`,
ничего не удаляется, ключ создаётся заново.

Записи: `activation/state` — состояние активации документом
`dppass.activation` v1 (записи активной и предыдущей конфигурации,
сами конфигурации в полном виде, история до 32 записей);
`quarantine/<вид>-<время>.data` и `.reason` — то, что DPpass хранил и не
смог прочитать (D-06); `lost/<время>/…` — отложенное сбросом хранилища.

## 10. Диагностика

Контракт (D-22):

- `FailureKind` — категория для пользователя («что сломалось»,
  18 значений: сеть, DNS, разбор, формат, проверка, возможности ядра,
  компиляция маршрутов, проверка ядром, запуск ядра, TUN, сервер, TLS,
  аутентификация, здоровье, загрузка подписки, подписка, хранение,
  внутренняя). Набор закрыт и мал.
- `DiagCode` — стабильный код с категорией и серьёзностью по умолчанию.
  **Коды не переименовываются и не удаляются, только добавляются**: по
  именам написаны ожидания корпуса и будут написаны переводы сообщений.
- `Diagnostic` — код, серьёзность, сообщение без секретов, путь в
  документе (`$.profiles[0].port`), причины (`causes`), сводка исключения
  (`ErrorSummary`: тип и отредактированное сообщение, без стека).
- `Outcome<T>` — `Success(value, находки)` или `Failure(находки ≥ 1
  ошибки)`; `then`/`map` складывают находки шагов, ничего не теряя.

Журнал: `Logger` пишет события «имя + поля»; строковые поля проходят
`Redactor` до приёмника, `Secret` становится меткой, явно безопасное —
`Safe`. `Redactor.STANDARD` убирает UUID, пути и учётные данные ссылок,
пары «секретное имя = значение», длинные токены; `STRICT` (для отчёта,
который пользователь кому-то отдаёт) — ещё IP и хосты. Отчёт
`DiagnosticReport` собирается локально и при выводе ещё раз проходит
`STRICT` (D-12).

Журнал на устройстве (D-26): `TeeLogSink` отдаёт событие кольцу в
памяти (`LogHistory` — источник отчёта) и `FileLogSink` — файлу в
`noBackupFilesDir/log`, который пишется в фоне (очередь с пределом,
части по 1 МиБ, начало сеанса, прошлый сеанс). `CrashRecord` — запись
о падении: синхронно, мимо выключателя. `LogExport` — текст для буфера
обмена: падение, начало и хвост сеанса в пределах ~120 тыс. символов,
`STRICT`.

## 11. Android-слой

`app/` (D-17, D-19): `AppGraph` — единственное место, где Android
встречается с ядром (хранилище в `noBackupFilesDir`, Keystore, ядро Xray —
`XrayCompiler` и `XrayProxyEngine` поверх `libdppassxray` из APK, набор
геоданных — перенос в `noBackupFilesDir/geodata`, `PlatformTraits` по версии API).
Библиотека не загрузилась или не той версии — каждый вызов ядра отвечает
`BACKEND_NOT_AVAILABLE` с причиной. `DPpassVpnService` — foreground
`specialUse`, уведомление; поднимает TUN и подключает ядро (§3.4),
останавливается действием «Остановить», при `onRevoke` и в `onDestroy`
(уборка — в области процесса `AppGraph.scope`). `AndroidTunnelProvider` — `TunnelSpec` → `Builder`;
адреса — `InetAddress.getByAddress` (без DNS). `MainActivity` —
оболочка разработки с `FLAG_SECURE`. `DPpassApplication` первым делом
включает журнал устройства `DeviceLog` (D-26): файл в фоне, запись о
падении, копия журнала в буфер обмена при уходе оболочки с экрана, при
остановке сервиса и кнопкой; переключатель журнала — в оболочке. Манифест и сетевые настройки
проверяет `check_manifest.py`; API модулей ядра — `check_android_api.py`;
собранный APK, в том числе нативный код (только `libdppassxray.so` трёх
ABI, несжатая, выровнена по 16 КБ), — `check_apk.py`.

## 12. Время, потоки, детерминизм

- Время — `Clock` (`Clock.SYSTEM` на устройстве, `ManualClock` в
  тестах и `cli`); ожидание — переданной функцией `pause`, в тестах
  она двигает `ManualClock` без сна (D-21).
- Корутины: `suspend` на границах ядра, проб, проверки здоровья и
  загрузки; `withTimeoutOrNull` для проверки здоровья; `runBlocking` —
  только в `cli`.
- Состояние активации меняется только через `commit` после успешной
  записи: что не сохранено, то не активировано.
- Планировщик, классификатор, нормализация и компилятор детерминированы:
  одинаковый вход даёт одинаковый результат (проверяется тестами).
