# Сетевая модель Android для DPpass

Дата: **4 октября 2026**. Сборка проверяется против `android.jar`
API 36 (compileSdk/targetSdk 36, minSdk 26 — D-17). Источники —
документация Android (developer.android.com: `VpnService`,
`VpnService.Builder`, типы foreground-сервисов), исходники Xray-core
v26.9.30 (`proxy/tun`), v2rayNG и sing-box-for-android (только как
факты о подходах, код не берётся).

## 1. Цепочка

```
Activity (UI)  ──команды──►  ConnectionController (domain)
                                   │
                         VpnService (foreground)
                                   │ Builder.establish()
                                   ▼
                              TUN fd (ParcelFileDescriptor)
                                   │
                  мост: TunnelBinding (fd → ядро)
                                   │
                    ProxyEngine (Xray; позже — другое ядро)
                                   │ protect(socket) — исходящие сокеты ядра
                                   ▼                     мимо туннеля
                              физическая сеть
```

Домен DPpass не знает ни про `VpnService`, ни про fd: он строит
`TunnelSpec` (адреса, маршруты, DNS, MTU, политика приложений), а
Android-слой переводит его в вызовы `Builder` (`tunnel/`, `app/`).

## 2. VpnService: что важно

| Механизм | API | Значение для DPpass |
|---|---|---|
| `VpnService.prepare()` | 14 | системный диалог согласия; без него `establish()` не работает |
| `Builder.addAddress/addRoute` | 14 | **IPv6**: если не добавить `::/0` (или не заблокировать IPv6), IPv6-трафик идёт **мимо туннеля** — утечка; политика DNS/IPv6 — в `TunnelSpec` явно |
| `Builder.excludeRoute` | 33 | исключить подсети (локальная сеть) без расчёта дополнения; ниже 33 — вычислять дополнение маршрутов |
| `addAllowedApplication` / `addDisallowedApplication` | 21 | per-app; **взаимоисключающие** в одном Builder; собственный пакет DPpass — всегда вне туннеля (иначе петля) |
| `allowBypass` | 21 | разрешить приложениям обходить VPN — по умолчанию нет |
| `setUnderlyingNetworks` | 22 | правильный учёт сети (метеред, переключение Wi-Fi/мобильная) |
| `setMetered(false)` | 29 | иначе система считает VPN лимитной сетью |
| `setHttpProxy` | 29 | локальный HTTP-прокси для приложений — возможный режим, не первый |
| `setBlocking` | 21 | блокирующий fd для моста |
| `protect(socket)` | 14 | сокеты ядра к серверу обязаны быть защищены — иначе петля через собственный туннель |
| Always-on VPN и lockdown | 24 | системная настройка; при lockdown трафик без VPN блокируется системой — DPpass должен корректно стартовать по системному запросу (`SERVICE_INTERFACE`) и после перезагрузки |
| Типы foreground-сервиса | 34 | обязателен тип: `systemExempted` разрешён VPN-приложениям, настроенным в «Настройки → Сеть → VPN»; `specialUse` требует объяснения в манифесте и проверки в Play Console. v2rayNG (октябрь 2026) объявляет `specialUse` |
| Уведомление foreground | 26+ | канал уведомлений, постоянное уведомление пока туннель поднят |

## 3. Мост fd → ядро

Варианты на октябрь 2026:

| Вариант | Как | Плюсы | Минусы |
|---|---|---|---|
| **TUN inbound Xray** | с v26.1.13 у Xray есть входящий `tun`; на Android fd передаётся переменной окружения/флагом `xray.tun.fd` (`proxy/tun/tun_android.go`), стек — gVisor | один компонент, одно ядро, нет локального SOCKS | функция молодая (январь 2026); README Xray прямо называет её инструментом для «сетевых профессионалов»; нет ICMP; поведение `connect` без реального соединения (SYN-ACK от стека) |
| hev-socks5-tunnel | C-библиотека (MIT): fd → локальный SOCKS5-вход ядра | проверена v2rayNG годами; маленькая | второй нативный компонент; локальный SOCKS-порт (надо закрыть от других приложений аутентификацией) |
| tun2socks (xjasonlyu, MIT, Go) | то же на Go | один язык с ядром | ещё одна копия рантайма Go, если не собирать вместе |
| libbox (sing-box) | собственная развитая TUN-интеграция | зрелая | **GPL-3.0+** (D-20) |

Решение для первой реальной интеграции — **эксперимент**, а не выбор
сейчас (`ROADMAP`, этап 2): сравнить TUN inbound Xray и
hev-socks5-tunnel по стабильности, памяти, батарее и утечкам. Граница
`TunnelBinding` в `tunnel/` скрывает разницу от домена — выбор
меняется без правки домена.

## 4. Процесс и жизненный цикл

- **Отдельный процесс** для сервиса туннеля (так делает v2rayNG:
  `:daemon`) изолирует падение ядра от UI и наоборот, но требует IPC.
  Граница `ConnectionController` ↔ сервис — интерфейс; один процесс
  или два — отложенное решение до первой реальной интеграции.
- **Смерть процесса.** Состояние «должен ли туннель работать» хранится
  на диске (`storage`), а не в памяти: после смерти процесса сервис,
  перезапущенный системой (`START_STICKY`/always-on), поднимает
  last-known-good, а не «пустую» конфигурацию.
- **Перезагрузка.** Always-on VPN — системный путь; собственный
  `BOOT_COMPLETED` — только как дополнение (ограничения фонового
  запуска Android 12+).
- **Оптимизация батареи / Doze.** VPN-сервис в foreground не
  усыпляется, но периодические задачи (обновление подписок) — через
  `WorkManager` с ограничениями сети; частота — политика подписки, не
  жёсткий таймер.
- **Смена сети.** `ConnectivityManager.NetworkCallback` → событие
  `NetworkChanged` → переоценка (`network/`), без немедленного
  «залпа» проверок (D-14).

## 5. DNS

- Системный «частный DNS» (DoT) действует на приложения вне туннеля;
  внутри туннеля DNS задаётся `addDnsServer` и обрабатывается ядром.
- Утечки DNS: запросы приложений, исключённых из туннеля, идут
  системным резолвером — это ожидаемо и должно быть видно в описании
  режима, а не скрыто.
- Адрес сервера прокси резолвится **до** поднятия туннеля (или
  хранится IP), иначе — циклическая зависимость.

## 6. Обнаружение VPN другими приложениями

- Любое приложение видит, что в системе есть сеть с
  `NetworkCapabilities.TRANSPORT_VPN`, перебирая `getAllNetworks()`,
  **даже если само исключено из туннеля** (`addDisallowedApplication`).
  Также виден интерфейс `tun*` в `NetworkInterface`.
- С апреля 2026 российские сервисы обязаны искать VPN у пользователей
  (`RUSSIA_NETWORK_RESTRICTIONS.md`, §1). DPpass **не может** сделать
  VpnService невидимым. Может: исключить такие приложения из туннеля
  (их трафик идёт напрямую с «домашнего» IP), дать быстрый режим
  «пауза». Режим без VpnService (только локальный прокси для
  выбранных приложений) не создаёт `TRANSPORT_VPN` — отложенная
  возможность, архитектура её допускает (`tunnel/` необязателен для
  `ConnectionController`).
- Обещать пользователю «незаметность» запрещено (`docs/SECURITY_MODEL.md`).

## 7. Резервные копии и экспорт

- `android:allowBackup="false"` и `dataExtractionRules`, исключающие
  всё: подписки и ключи не должны уезжать в облачную копию Google.
- Скриншоты экранов с секретами — `FLAG_SECURE` на этих экранах
  (решение при реализации UI).

## 8. Совместимость версий

- minSdk 26 (Android 8.0): каналы уведомлений, `java.time`; потеря —
  устройства Android 7.x (малая доля в 2026); пересматривается перед
  первым выпуском (D-17).
- targetSdk 36: требование Google Play для новых приложений и
  обновлений с 31.08.2026.
- Страницы памяти 16 КБ: нативные библиотеки ядра (Go) должны
  собираться с выравниванием 16 КБ — проверка APK в `tools/hostcheck`
  появляется вместе с первой нативной библиотекой.

## 9. Раздача: точка доступа, USB- и Bluetooth-модем

Дополнено **6 октября 2026**.

- Трафик клиентов точки доступа, USB- и Bluetooth-модема Android ведёт
  мимо `VpnService`: VPN приложения действует на приложения самого
  устройства, а у раздачи свои таблицы маршрутизации. Сторонние
  приложения поэтому раздают VPN либо с root (переписывают маршруты и
  правила — так работает VPNHotspot, «root required»:
  github.com/nekohasekai/VPNHotspot, README на 6 октября 2026), либо
  через прокси на телефоне, который клиенты указывают у себя (ShieldShare:
  «Android's native hotspot functionality lacks support for routing shared
  traffic through VPN connections», SOCKS5/HTTP между точкой доступа и
  VPN без root — corpus.lantern.io/papers/2026-edorh-shieldshare/).
  Описания подходов — только как факты, код не берётся (D-20). Проверка
  на устройстве автора — `TODO.md`.
- Включить точку доступа или модем стороннее приложение не может:
  `TetheringManager` — системный API. Список интерфейсов раздачи
  публично тоже не отдаётся. Интерфейс раздачи узнаётся так: он поднят,
  у него частный IPv4-адрес, и это **не** сеть из
  `ConnectivityManager` (сети — это Wi-Fi-клиент, мобильная связь, VPN;
  интерфейсы раздачи — «вниз по течению» и сетями не являются). Имена
  у производителей разные (`ap0`, `swlan0`, `wlan1`, `rndis0`, `ncm0`,
  `bt-pan`), поэтому по имени не узнаётся.
- Дополнено **17 октября 2026** (D-57): список раздающих интерфейсов
  приложению всё же доступен — система шлёт липкую рассылку
  `android.net.conn.TETHER_STATE_CHANGED` со списками имён `tetherArray`
  (раздают сейчас), `availableArray`, `android.net.extra.ACTIVE_LOCAL_ONLY`
  и других; отправка — `sendStickyBroadcastAsUser(…, UserHandle.ALL)`
  без разрешения (AOSP, ветка `android15-release`:
  `packages/modules/Connectivity/Tethering/src/com/android/networkstack/tethering/Tethering.java`,
  `sendTetherStateChangedBroadcast`; константы — `TetheringManager.java`
  там же, действие помечено `@Deprecated` в пользу
  `TetheringEventCallback`). Публичным `TetheringManager.registerTetheringEventCallback`
  стал в SDK 36 (Android 16, `android.jar` платформы 36). На Redmi 13
  (Android 15) признаки «не сеть и широковещательный» точку доступа не
  нашли (`TODO.md`, «На устройстве»).
- Порт, открытый на адресе интерфейса раздачи, видят и приложения на
  самом телефоне: адреса устройства для них — локальные. Это новая
  примета прокси на устройстве (§6, `RUSSIA_NETWORK_RESTRICTIONS.md`,
  §1) — пока раздача включена.
