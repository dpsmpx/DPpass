# DPpass: надёжный доступ без удалённого VPN-сервера — техническое исследование

**Дата среза:** 22 ноября 2026. **Статус:** исследование, гипотезы и план испытаний. **Код приложения не менялся.**

**Входные данные:** [сохранённый полевой журнал 10:36–10:39 UTC](field-logs/2026-11-22-1036-mobile-auto-quic-ab.md), [модель блокировок РФ](RUSSIA_NETWORK_RESTRICTIONS.md), [доступ при белых списках](ALLOWLIST_ACCESS.md), [предыдущий разбор DPI](DPI_DESYNC.md), [аналитика фейковых пакетов](FAKE_PACKETS.md), [автоадаптация](ZAPRET_ADAPTIVE_METHODS.md), [проектирование Alpine](../ALPINE_RUNTIME.md). Метки достоверности A–E — по отчёту РФ. Никаких новых сетевых экспериментов на устройстве автором этого документа не проводилось.

## 1. Главная граница постановки задачи

**Доступ к зарубежным сервисам напрямую, без удалённого прокси/сервера, технически достижим только там, где сеть всё-таки пропускает пакеты к адресу сервиса.** Локальная DPI-десинхронизация изменяет способ передачи и распознавания первого обмена; она не создаёт отсутствующий маршрут, не изменяет адрес выхода пользователя и не делает зарубежный сервис доступным, если он сам блокирует регион/IP.

Android `VpnService` — локальный захват трафика, **не удалённый VPN-сервер**. Он сам по себе не шифрует соединения; защиту данных обеспечивает исходный HTTPS/TLS сервиса. IP пользователя виден целевому сервису, а сам факт работающего Android VPN может быть виден другим приложениям. Alpine/PRoot не предоставляет `CAP_NET_ADMIN` или NFQUEUE.

| Класс препятствия | Возможности полностью локального решения | Что не следует обещать |
|---|---|---|
| DNS-подмена или перехват (L0–L1) | Защищённый DNS с проверкой сертификата, несколько доступных резолверов, контроль IPv4/IPv6 | DoH не устраняет блокировку IP и SNI; резолвер тоже может быть недоступен |
| Фильтр по TLS SNI / HTTP Host (L2) | Комбинация TLS record fragmentation, TCP splitting, корректные decoy/TTL/OOB, отбор по сети и сайту, ECH при реальной поддержке обеих сторон | Надёжность для каждого DPI/сервиса |
| QUIC Initial/SNI (часть L2) | Выбор TCP, аккуратные эксперименты с корректным QUIC и версиями, где их поддерживает сам сервер | Принудительное переключение чужого сервиса на QUICv2; универсальный эффект ложных UDP |
| Деградация после 15–20/16 КБ (L4/L7) | Диагностика точного порога; другой легитимный IP/семейство/протокол, если путь есть | Разбиение ClientHello **не** гарантирует снятие порога последующей загрузки. Нельзя прозрачно разбить зашифрованный HTTPS-ответ на независимые соединения без содействия приложения/сервера |
| Запрет IP, подсети, ASN (L3–L4) | Легитимный доступный альтернативный адрес сервиса, если имеется | Обход недостижимого IP только манипуляцией с TCP/TLS |
| Мобильный «белый список» по IP/сети, полный отказ (L9–L10) | Определить режим, не тратить трафик/батарею, сообщить предел | Доступ к чужому закрытому IP без **какого-либо достижимого посредника** невозможен |
| Геоблокировка со стороны зарубежного сервиса | Обнаружить сервисный отказ | Локальный desync не меняет внешнюю геолокацию/IP |

Сведения о классах L0–L10 и различиях мобильных операторов приведены в отчёте репозитория. На 2026 год подтверждены как минимум QUIC SNI-фильтрация (FOCI 2026), ECH-фильтрация на части инфраструктуры (FOCI 2025) и ограничения Cloudflare примерно после 16 КБ (первичный отчёт Cloudflare 26.06.2025). Последнее не является доказательством сохранения точного порога **в сети автора в ноябре 2026**.

## 2. Что действительно делают ByeByeDPI, ByeDPI и Zapret2

**[ByeByeDPI Android](https://github.com/romanvht/ByeByeDPI)** (проверенный опубликованный релиз v1.8.2 от 02.10.2026) запускает локальный [ByeDPI](https://github.com/hufrea/byedpi) и перенаправляет трафик через Android VpnService/hev-socks5-tunnel либо локальный прокси. Удалённый VPN-сервер не нужен; адрес выхода не меняется. Движок ByeDPI (релиз v0.17.3 от 22.09.2025) реализует многочастное разбиение по позициям SNI/Host, `disorder`, `fake`, `oob`/`disoob`, отдельное разбиение **TLS-записи** `tlsrec`, подделку TTL/MD5 при поддержке платформы, фальшивые UDP-датаграммы и `--auto` по событиям `torst`/`ssl_err`/`redirect`. Плюс подхода — работа на собственных TCP-сокетах без root; минус — нет гарантии, что TCP-сегменты на физическом интерфейсе выглядят так, как предполагает приложение, а фальшивая отправка может нарушить соединение.

**[Zapret2](https://github.com/bol-van/zapret2)** (проверен релиз **v1.0.7 от 05.11.2026**) использует пакетные адаптеры NFQUEUE в Linux / WinDivert в Windows и Lua-сценарии `nfqws2`. Это не просто набор TTL: сценарии умеют обрабатывать направление и состояние потока, реконструкцию, `multisplit`/`fakedsplit`, подделки TLS/QUIC, sequence/ACK и TCP-опции, профильные hostlist/ipset, срабатывания по ретрансляции/RST/UDP-тишине и оркестраторы стратегий. Пакетные полномочия дают возможности, которых у приложения Android без root нет. `blockcheck2` годится для ограниченного исследовательского стенда, но массовый непрерывный перебор на мобильном телефоне опасен нагрузкой, ложными выводами и остаточной блокировкой DPI.

**Не следует смешивать эти механизмы:** ByeByeDPI использует собственные исходящие прокси-сокеты; Zapret2 `nfqws2` обрабатывает пакеты на уровне ОС; DPpass Alpine сейчас лишь запускает собственный Go-планировщик через Unix-сокет. Наличие архива upstream nfqws2 в APK/Alpine не означает, что его Lua-сценарии работают на обычном Android без root.

| Свойство | ByeDPI / ByeByeDPI | Zapret2 nfqws2 | DPpass без root на 22.11.2026 |
|---|---|---|---|
| Захват чужих Android-приложений | VpnService → локальный SOCKS | Только отдельная ОС-пакетная интеграция | VpnService → Xray TUN |
| Полноценные raw-пакетные стратегии | Нет | Да, при доступе к NFQUEUE/WinDivert | Нет |
| TCP strategy set | split, disorder, fake, OOB, TLS-record, др. | расширяемые Lua-методы, включая пакетные | `split-1`, `split`, `fake-3`, `fake-5`, `disorder` |
| QUIC | UDP fake; эффект зависит от сети | парсинг/реассемблинг и Lua на пакетном уровне | распознавание v1/v2 Initial, 6 dummy UDP с TTL |
| Выбор по ошибке подключения | `--auto`: timeout/RST/TLS error/redirect | Lua детекторы + оркестраторы | циклический выбор новых сокетов, предпочтение по объёму полученных байт |
| Изоляция опыта по сети и функциональный успех целевого сервиса | ограничения реализации | зависит от конфигурации Lua | сброс при смене сети; **нет проверки успешности YouTube** |

## 3. Критические ограничения текущего экспериментального DPpass (обнаружены чтением исходников)

1. `tools/xray/zapret2/plan.go`: одна позиция TCP разбиения, выбранная в середине обнаруженного SNI/Host, либо первый байт. Нет комбинированного TCP + TLS-record splitting, OOB, многочастного разбиения, условных ретрансляций и packet-level Lua.
2. `tools/xray/zapret2/packet.go`: `FakeQUICInitial` копирует исходный Initial и случайно меняет байты начиная с 64-го; комментарий прямо говорит, что результат — **невалидное QUIC-рукопожатие**. Это не эквивалент корректно зашифрованного QUIC Initial с альтернативным SNI. DPI, способный разбирать/дешифровать Initial, не обязан ошибочно принять его за легитимный запрос.
3. `tools/xray/bridge/desync.go`: десинхронизация TCP принимается по первой записи (`sync.Once`). Если ClientHello приходит несколькими маленькими вызовами `Write` и начальный вызов недостаточен для распознавания, текущий метод может пропустить рукопожатие. Требуется лабораторная проверка фрагментированного ввода и физической отправки сегментов до решения о правке.
4. `tools/xray/bridge/adaptive_zapret2.go`: стратегии оцениваются по 128 КиБ входящего трафика либо по трём ответам от 12 КиБ. Это **зашифрованные транспортные байты**, а не HTTP-статус, успешное обновление ленты или видео. Ограничение в 16 КБ способно дать ложный признак успеха, а ошибку на конкретном приложении алгоритм пока не знает.
5. QUIC в текущем протоколе адаптации идентифицируется по IP защищённого UDP-сокета, а не подтверждённому имени; разные HTTPS-сервисы на общем IP могут смешивать результаты. Хостлисты, DNS/CDN, IPv4 и IPv6 требуют раздельной оценки.
6. `quic_force_tcp=true` намеренно исключает все QUIC-пробы; алгоритм не должен молча менять сохранённый переключатель. В логе `quic_trials_enabled=true` подтверждает только разрешение испытаний QUIC, **не успешность** какой-либо стратегии.
7. PRoot/Alpine — дополнительный процесс и IPC на каждый план, но не средство обойти ограничения прав Android. Его ценность — тестируемое пространство исполняемых компонентов/сценариев, а не преимущество над сетевым контролем ядра.

## 5. Рекомендуемая архитектура: сначала диагностировать препятствие, затем выбирать средство

Проектировать **не один новый «волшебный» fake**, а ограниченный последовательный контур:

1. **NetworkClassifier**: тип физической сети; доступность контрольных внутренних/внешних адресов; DNS; TCP connect; TLS handshake; первый ответ; объём до остановки и длительность; QUIC, IPv4/IPv6. Обнаруживать режимы L0/L2/L3/L4/L7/L9 с пометкой уверенности и альтернативных причин (потеря связи, MTU, авария сайта). Проверки вне VPN и через VPN хранить и показывать **раздельно**.
2. **FlowOutcomeDetector**: различать dial failure, TLS alert/RST, TCP stall, первые 16/32/128 КиБ, полезное завершение только для собственных HTTPS-проб к разрешённым тестовым ресурсам. Из общего зашифрованного TLS неизвестно, показал ли YouTube видео. Никаких URL или пользовательского содержимого в логах.
3. **StrategyCatalogue**: безопасные в Android без root кандидаты `plain`, TCP split, TLS-record split, **оба вместе**, SNI-relative multi-split, тщательно испытанные OOB/TTL-fake, и TCP-first вместо QUIC по выбору пользователя. Не переносить пакетно-привилегированные методы nfqws2 в обычный Android под видом поддерживаемых.
4. **AdaptivePolicy**: ключ из сети + назначения/суффикса + транспорта/семейства IP; повторный опыт с давностью, гистерезисом и доверительными оценками. Не присваивать «победу» по одному TLS ServerHello или случайному большому потоку. Новый выбор только для новых соединений; предельное число испытаний, пауза после неудачи (QUIC 4-tuple residual block был измерен до 420 с в FOCI 2026), запрет на фоновые залпы.
5. **TransportAdapter**: Xray/TUN и Android `VpnService.protect` остаются единственным владельцем защищённых сокетов; для root — отдельный явный NFQUEUE backend. Alpine-планировщик не отвечает за привилегированный пакетный ввод-вывод.
6. **Explainability**: показывать «DNS/доступный IP/рукопожатие/ответ/прерывание после N байт», активную стратегию, уверенность и пределы. Пользователю важно знать, когда локальный обход технически невозможен.

**Современные технологии — не готовые универсальные обходы.**
- TLS 1.3 + ECH скрывает внутренний SNI **только если клиент и целевой frontend поддерживают ECH**; внешнее имя/ECH extension и адрес остаются видимыми. В РФ измерена блокировка некоторых ECH к Cloudflare. Использовать как кандидат там, где технология поддерживается, но не как безусловный дефолт.
- QUICv2 на трёх исследованных точках в РФ в марте–апреле 2026 не блокировался тем же QUICv1-фильтром; это гипотеза для контролируемых испытаний на **сервисах, действительно поддерживающих v2**, не универсальный переключатель для YouTube.
- DoH/DoT защищают DNS только до доступного резолвера; сами по себе не скрывают TLS SNI или IP.
- MASQUE, REALITY, VLESS, XHTTP, Tor, Snowflake, CDN-туннели предполагают достижимую удалённую точку или инфраструктуру третьей стороны, поэтому **не удовлетворяют строгому условию «никакого удалённого посредника»** при доступе к произвольному заблокированному адресу. Различать «без своего сервера» и «совсем без удалённого сервера».

## 6. Порядок последующих работ — без изменения кода сейчас

**P0 — лабораторная модель блокировок и эталон метрик.** Воспроизвести внутри контролируемой сети: SNI-drop, TCP RST, молчаливый stall после 16/32 КиБ, QUIC Initial censorship, частичный IPv6, отсутствие маршрута. Проверять, что диагностика не путает их с неисправной сетью, MTU и отказом DNS. Записать baseline без обхода.

**P1 — A/B на реальном Android с воспроизводимыми действиями.** На одной физической сети последовательно: прямой трафик без desync; AUTO с QUIC; AUTO с TCP-only; прицельная обработка 7 доменов; возврат к baseline. Каждый вариант проверяет отдельно обновление ленты YouTube, миниатюры, комментарии и воспроизведение не менее нескольких минут. Фиксировать реальные пользовательские результаты и агрегатные счётчики per-flow/per-outbound без сайтов/URL. Контроль Wi-Fi/другой мобильный оператор, несколько времён суток. Избегать интенсивных повторов QUIC на одной 4-ке адресов/портов из-за возможного 420-секундного эффекта.

**P2 — сравнить новые *локальные* стратегии только после P0/P1.** Наиболее обоснованный кандидат — комбинированное разбиение TLS-записи и TCP-сегментов (FOCI 2025) и контроль сегментации первого ClientHello. Далее — экспериментальные стратегии ByeDPI: OOB, многочастный SNI-split и fake/TTL с соблюдением прав Android; тестировать совместимость с TLS1.3/ECH, IPv6, HTTP/2. Отдельно решить судьбу некорректного fake QUIC Initial — не считать его эквивалентом nfqws2. Ни один новый метод не включать глобально без негативных тестов.

**P3 — реальная адаптация по причине отказа.** Режим «кандидат в этой сети/для этого сервиса/для этого протокола» вместо циклического выбора по общему количеству downstream. Метрики успеха для авторизованных тестовых HTTPS-объектов: статус и проверенный объём ответа, а не только открытие TCP.

**P4 — привилегированный вариант как отдельное семейство.** Если есть root/NFQUEUE, тестировать настоящие upstream nfqws2 Lua и пакетную обработку. Для массового Android без root — использовать только реализуемые варианты на собственных сокетах; PRoot не является заменой root.

**P5 — строгая приёмка перед обещаниями пользователям.** Работа со сценариями DNS, SNI, RST, заморозка после ~16 КБ, IPv6, QUIC, мобильная↔Wi-Fi, батарея, отсутствие утечек/коррупции TLS, нормальная работа разрешённых сайтов и отсутствие regressions при выключении функции. Функциональная проверка YouTube обязательна на телефоне автора: CI и DoH-probe не закрывают задачу.

## 7. Первичные внешние источники и уровни уверенности

- [hufrea/byedpi, README и параметры](https://github.com/hufrea/byedpi), MIT, `--auto` / `--tlsrec` / `--oob` / `--fake` — исходная документация к механизму.
- [romanvht/ByeByeDPI](https://github.com/romanvht/ByeByeDPI), README и релиз v1.8.2 — исходная документация Android-обвязки.
- [bol-van/zapret2](https://github.com/bol-van/zapret2), [manual](https://github.com/bol-van/zapret2/blob/master/docs/manual.en.md), Lua `zapret-auto.lua` и `zapret-antidpi.lua`, релиз v1.0.7 — первичный код и документация.
- [FOCI 2025: Encrypted Client Hello (ECH) in Censorship Circumvention](https://petsymposium.org/foci/2025/foci-2025-0016.php) — сочетание TLS-record и TCP fragmentation, наблюдение блокировки ECH.
- [FOCI 2026: On Russia's Early Introduction of QUIC SNI Censorship](https://www.petsymposium.org/foci/2026/foci-2026-0010.php) — QUIC Initial SNI, остаточная блокировка, QUICv2 в точках измерения.
- [Cloudflare, 26.06.2025: Russian Internet users are unable to access the open Internet](https://blog.cloudflare.com/russian-internet-users-are-unable-to-access-the-open-internet/) — первичное наблюдение лимита около 16 КБ у части ISP.
- [Коммерсантъ, 05.08.2026](https://www.kommersant.ru/doc/8862389) — срез Vigo по белым спискам и доле доступных сессий, вторичные данные.
- [RFC 9849 — TLS Encrypted Client Hello](https://www.rfc-editor.org/rfc/rfc9849.html) — спецификация, не доказательство обхода.
- Внутренние измерения DPpass в `RUSSIA_NETWORK_RESTRICTIONS.md` (17–18.10.2026) и сегодняшнем `field-logs` — отдельные полевые точки, не репрезентативная статистика по РФ.

**Вывод:** сильный продукт без удалённого сервера — диагностируемый локальный инструмент против **части** DNS/SNI/протокольных блокировок, с воспроизводимым выбором TCP/TLS стратегий, честным определением недоступности IP/белого списка и доказуемыми тестами. Универсальный и гарантированный доступ ко всем зарубежным сервисам при IP/allowlist-блокировке без достижимого посредника **невозможен**.
