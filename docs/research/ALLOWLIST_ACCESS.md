# Доступ под белым списком без своего сервера

Дата среза: **17 октября 2026**. Вопрос из отложенных
(`docs/direction/DECISIONS.md`, «Отложено»): может ли DPpass под белым
списком мобильной сети (L9, `docs/research/RUSSIA_NETWORK_RESTRICTIONS.md`,
§2) открыть сайты и сервисы вне списка, в том числе обновление
приложений, **без подключения к удалённому серверу**. Цель — автора
(17.10.2026). Документ описывает, что проверяет список и что
клиент может против каждого варианта. Это свойства и границы, а не
обещания: «обходит белые списки» недопустимо (D-13,
`docs/direction/RESEARCH_SCOPE.md`, §3).

Метки источников A–E — как в `docs/research/RUSSIA_NETWORK_RESTRICTIONS.md`, §0.
Рецензируемых измерений белого списка (A) на дату среза не найдено.
Всё ниже — наблюдения сообщества (C), одиночные и противоречивые, и
сообщения СМИ (D).

**Что из этого следует на дату среза.** Вариант «только по имени» описан
один раз, в сентябре 2025, у одного оператора. Позже несколько независимых
участников (C) описывают список по адресу или подсети, местами вместе с
проверкой имени. Собственный замер DPpass от 17.10.2026 — отказ на
соединении, до имени: так ведёт себя список по адресу. Списки различаются
по операторам и регионам и меняются неделями. Это наблюдения, а не факт
уровня A.

## 2. Что может клиент без сервера — по вариантам списка

| Что проверяет список | Без сервера | С точкой внутри списка |
|---|---|---|
| **адрес (IP, подсеть)** | ничего: пакет к адресу вне списка не проходит, и протокол этого не меняет (#579). Нет маршрута — нет и пути (L9) | работает только кандидат на разрешённом адресе, который пересылает трафик дальше. Это сервер: свой, чужой или в облаке из списка |
| **только имя (SNI, Host)** при открытом адресе | в принципе — приёмы десинхронизации DPI, которые показывают фильтру разрешённое имя. В DPpass их нет: это отдельная функция, она отложена («Локальная DPI-десинхронизация» в «Отложено»). Приёмам с доступом к пакетам до ядра сети нужен root (`docs/research/ZAPRET_ADAPTIVE_METHODS.md`), приёмам локального прокси на собственных сокетах — нет: byedpi — локальный SOCKS-прокси с разбиением, перестановкой, поддельной частью с малым TTL и OOB (README hufrea/byedpi, MIT, прочитан 17.10.2026); пакетов чужих сокетов он не перехватывает. Против списка по имени ни те, ни другие не измерены. Если список закрывает всё нераспознанное, спрятанное имя не поможет, нужно подставить разрешённое. Целевой сервис при этом должен принять соединение. Существует ли сейчас такой вариант списка, не известно (§1) | сервер с разрешённым именем (Reality и т. п.) — 4 из 28 по одному отчёту (#650) |
| **адрес и имя** | ничего | сервер на разрешённом адресе и с разрешённым именем; разделение пулов (2026-01, 2026-08) сужает и это |
| **DNS** | не барьер: имена резолвятся (#516, Habr, замер DPpass). И не путь: туннель через DNS упирается в закрытый зарубежный DNS и запросы ~66 байт (#516) | — |

**Чужая инфраструктура внутри списка** (облака из списка, звонки
разрешённых сервисов, сервисы, которые сами загружают чужое содержимое) —
это тоже сервер, только чужой. Пользоваться чужим сервисом как каналом в
обход его назначения и условий DPpass не будет: исследования не обходят
защиту чужих сервисов (`docs/direction/RESEARCH_SCOPE.md`, §4), а
поставщик, по сообщениям, может потерять место в списке за обслуживание
пользователей с VPN (D: «Коммерсант» через SecurityLab, 2026).

## 3. Обновление приложений под белым списком

- **RuStore** — в перечне доступных при ограничениях мобильного интернета
  у МТС (B: media.mts.ru, 01.06.2026) и в обзорах (D: hi-tech.mail.ru,
  bothelp.io, май 2026). Приложения, которые там есть, обновляются без
  туннеля. **Google Play** в этих перечнях не найден (поиск 17.10.2026).
- **Wi-Fi и проводной интернет** — по заявлениям Минцифры и «Ростелекома»
  (D, март 2026), без белых списков: обновление через Wi-Fi не упирается в
  L9.
- **Устройство раздачи** (D-55): телефон в сети без белого списка, то есть
  своё устройство, а не удалённый сервер. Через него идёт весь трафик,
  в том числе обновления. Нужно второе устройство в другой сети — это
  граница, а не обход.

## 4. Выводы для DPpass

1. В общем виде цель «все сайты без удалённого сервера» на дату среза
   клиент не достигает. При списке по адресу — а по наблюдениям §1 и по
   собственному замеру так и есть — нужна точка внутри списка, которая
   пересылает трафик. Протокол, отпечаток и приёмы на телефоне маршрута не
   создают. Это граница L9, а не недоработка; обещаний нет (D-13).
2. Что DPpass делает или может делать честно:
   - распознаёт режим (D-60, D-62) и запоминает его, не залипая (D-64);
     под списком первым ставит кандидата, который под ним работал;
   - может прямо сказать, что под белым списком нужен кандидат на
     разрешённом адресе, а без него соединения не будет. Пути без туннеля:
     Wi-Fi, устройство раздачи (D-55), магазины из списка — подсказкой,
     без рекламы конкретного сервиса;
   - может измерить, проверяет ли список у автора только имя. Для этого
     пробы TLS к **своему** серверу автора с разрешённым и своим именем.
     Чужая инфраструктура не зондируется (`docs/direction/RESEARCH_SCOPE.md`,
     §4); нужно согласие автора, это задача в `TODO.md`. Если имя окажется
     единственной проверкой, вопрос о локальной десинхронизации
     пересматривается отдельным решением.
3. Пересмотр — при новом измерении уровня A или C, где список по имени
   подтверждён вторым источником, или при собственном замере из п. 2.
