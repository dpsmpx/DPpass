# Локальный Zapret2 в DPpass — статус и проверка

> Историческая документация существующих реализаций. С 24 ноября 2026
> целевая архитектура 0.9 описана в [плане единого ядра](direction/LOCAL_DPI_ENGINE.md).
> RC6 — сохранённый эталон; отдельные движки пока не удаляются.

**Текущий этап: alpha для испытаний, не проверенный финальный выпуск.**
Разработка идёт в [PR #35](https://github.com/dpsmpx/DPpass/pull/35), который
продолжает PR #34. Бинарник ещё не проверен на реальном Android с root и без root.

## Три независимых варианта подключения

1. **Подписки**: исходный Xray-сервер и политика пользователя; при выборе
   «Выключено (подписки)» новый локальный режим не вмешивается.
2. **Zapret2 / root**: оригинальный `nfqws2` v1.0.7 с Lua-стратегиями
   по умолчанию upstream (HTTP/TLS/QUIC). Запуск через `su`; требуется
   NFQUEUE на устройстве, рабочий iptables/ip6tables и право выполнить
   бинарник из root-каталога. Создаются **только** правила OUTPUT TCP
   80/443 и UDP 443, пакеты с меткой nfqws2 исключены из повторной
   очереди. При остановке и гибели процесса cleanup/watchdog снимает
   свои правила и завершает процесс; `--queue-bypass` страхует сбой
   демона. Правила касаются всего устройства, а не только приложений
   списка VpnService.
3. **Локальный VpnService (без root)**: Android TUN -> локальное ядро Xray
   для непосредственного выхода в Интернет, **без прокси-сервера**.
   Выходные сокеты защищены `VpnService.protect`; отдельный Go-dialer
   использует низкий TTL, обходные TCP-приёмы для TLS ClientHello и HTTP
   Host и экспериментальные UDP/QUIC ложные пакеты. Пользовательская
   подписка не требуется. Режим не запускает оригинальный `nfqws2`,
   поскольку обычному Android VpnService недоступен NFQUEUE. Это
   **не полная реализация всех Lua-стратегий Zapret2**, а ограниченный
   безrootовый совместимый режим. Его эффективность зависит от сети
   и конкретного DPI.

## Параметры локальных режимов (после дополнения к PR #35)

- **Root:** в «Настройках → Zapret2» можно включать/выключать обработку
  QUIC (UDP 443) и задавать общий для двух режимов список DNS-доменов
  по одному на строку.
  Пустой список означает обработку всех сайтов на поддерживаемых портах.
  Введённые домены канонизируются и проверяются; произвольные аргументы
  shell или nfqws2 из интерфейса не принимаются. Список передаётся
  оригинальному nfqws2 v1.0.7 через `--hostlist` внутри каждого профиля.
  При смене списка или QUIC сервис переподключается с очисткой прежних
  NFQUEUE-правил. Файлы остаются в частном каталоге приложения и
  недоступной обычным приложениям root-папке `/data/adb/dppass-zapret2`.
- **VpnService без root:** в том же разделе выбирается локальный TCP-приём:
  подделка с TTL 3, TTL 5 или перестановка с TTL 1. Подделка с TTL
  дополнительно пытается послать фальшпакеты QUIC. Это собственный Go
  dialer в составе DPpass, не нативный NFQUEUE nfqws2. Если задан список
  доменов, только они маршрутизируются через прямой выход с приёмом,
  остальной трафик идёт напрямую; для списка действует лимит маршрутизатора
  `SplitSites` в 200 записей (для root — до 2048). Для выбранных
  доменов QUIC отправляется на локальный fake-dialer, только если выбран
  приём Fake; при других TCP-приёмах и выключенном «QUIC → TCP» UDP/443 идёт напрямую (без QUIC-подделки). При включённом «QUIC → TCP» UDP/443 блокируется для всех режимов.
  При пустом списке локальный приём применяется к всем исходящим TCP
  соединениям, а экспериментальная UDP-подделка — к QUIC Initial.
- **Подписки:** `Zapret2Backend.OFF` оставляет существующий Xray-путь
  без модификаций; конфигурация root не вмешивается в подписки.

## Оставшиеся критерии, которые нельзя закрыть CI

- Настоящие испытания на Android с root: поддержка NFQUEUE,
  корректность Lua-приёмов против DPI, IPv6, QUIC, очистка правил
  после остановки приложения и аварии процесса.
- Испытания без root: доступность сайтов в сетях с DPI, сохранение
  DNS/IPv6, работа QUIC v1/v2 и возврат к прямым соединениям при
  несовместимости приёма; переключение Wi-Fi/LTE.
- GUI пока не предоставляет полного редактора произвольных Lua
  стратегий, автосписков и сетевого механизма `nftables`.
  В рамках этого изменения добавлена безопасная конфигурация
  доменов и вариантов работы, а не обещана совместимость
  со всеми возможностями исходного Zapret2.

## Медиа и CDN: варианты для Android VpnService (D-119)

После наблюдения, что YouTube загружает названия, но не превью и видео,
добавлен независимый переключатель **«QUIC → TCP»**. В режиме Zapret2
VpnService он по умолчанию включён: Xray закрывает исходящие UDP/443 из TUN,
чтобы клиенты, умеющие TCP, повторили соединение по TLS. Это не фильтр DNS
и не обход IP-блокировки; DNS и другой UDP остаются доступными. Правило
намеренно не зависит от hostlist, потому что имя QUIC Initial не всегда
доступно для маршрутизации. Если приложению нужен только QUIC — выключить
переключатель; для варианта Fake TTL снова используется экспериментальная
UDP-подделка. Это выбор, а не гарантированная починка YouTube.

Добавлен **«Разделение SNI / Host на две TCP-части»** — иной вариант
начала соединения, без подделки TCP сегментов и смены TTL. Он полезен
для сравнений с Fake TTL 3/5 и Disorder TTL 1. Это не nfqws2 `multisplit`:
тот умеет намного больше приёмов на уровне пакетов.

**Испытание A/B:** в одном Wi-Fi/мобильном соединении открыть YouTube,
проверить отдельно миниатюры `ytimg.com`, видео `googlevideo.com`,
получение ответа по TCP и UDP/443; для каждого теста отметить включён ли
«QUIC → TCP» и какой TCP-приём выбран. После изменения настроек — новое
соединение и повторная загрузка приложения. При непустом hostlist добавить
в него соответствующие суффиксы (как минимум `youtube.com`,
`googlevideo.com`, `ytimg.com`, `ggpht.com`, `youtubei.googleapis.com`)
или оставить список пустым, чтобы пробовать все сайты. Проверить качество,
стабильность 5–10 минут, IPv6, альтернативную сеть, отсутствие утечек DNS.

## Недостающие испытания и ограничения

- Root: запуск Magisk/KernelSU, SELinux, NFQUEUE, перенаправление IPv4/IPv6,
  QUIC, действия с несколькими приложениями, очистка правил после принудительной
  остановки и перезагрузки, смена сети и реальная блокировка.
- VpnService: TLS HTTP/2, HTTP/1.1, QUIC v1/v2, IPv6, DNS, переход Wi‑Fi/LTE,
  конфликт с другим VPN, аварийное восстановление и тесты успешного/неуспешного
  обхода реального DPI. UDP-фальшпакеты не являются эквивалентом полного
  nfqws2 и не обязаны помогать в каждой сети.
- Полный редактор произвольных Lua-стратегий и автосписков всё ещё не реализован:
  root использует фиксированные стратегии с настраиваемым
  hostlist и выключателем QUIC; безrootовый вариант — три TCP-приёма
  и тот же список доменов через маршрутизацию Xray.
  Это остаётся открытым объёмом.
- Реальный финальный релиз и закрытие задачи — **только после этих испытаний**
  и проверки всех режимов, не по одному успешному статусу GitHub Actions.

## Эксперимент с YouTube CDN (21.11.2026)

По обратной связи с Android: метаданные YouTube загружаются, но превью и видео — нет. Это не доказывает, что причина только в QUIC: запросы к `*.googlevideo.com`, `*.ytimg.com` и `*.ggpht.com` могут блокироваться отдельно, а IPv6, DNS и HTTP/3 требуют самостоятельной проверки. В безrootовом мосте вместо прежних шести 620-байтных UDP-пакетов с неверным типом QUIC теперь посылаются шесть низко-TTL пакетов с формой настоящего QUIC Initial v1/v2 (с сохранением длинного заголовка и рандомизацией тела), затем — исходный пакет без изменений. Это **не** полная подмена QUIC `nfqws2`, не гарантия обхода и не замена испытаний на устройстве. Проверка: загрузка превью `ytimg.com`, сегментов `googlevideo.com`, отдельно IPv4/IPv6 и QUIC/TCP, с записью причин отказа без пользовательских данных.

## Полевой отчёт: Android 15 / мобильная сеть / 21.11.2026

Пользователь подтвердил запуск `v0.7.54-alpha.4`, `api=35`,
`underlying_network=MOBILE`. В режиме Zapret2 VpnService соединение
в журнале помечалось `connected`, но главная YouTube, комментарии и
видеосегменты не загружались. Попытки `disorder`, `split`, `fake-5`
выполнялись с `n=7`, `rest=direct`, `quic_force_tcp=true`.
Это воспроизводимая **функциональная неудача YouTube**, независимо от
успешного запуска TUN и DoH.

Полный А/Б-прогон (`14:49:56–14:56:16Z`) — **89/90**, один отказ
`fake-8` (`ENDPOINT_UNREACHABLE`), остальные варианты по 10/10.
`plain` также 10/10; это тесты TLS до выбранного **сервера подписки**
без активного VPN, а не запросы к API YouTube или его CDN. Поэтому A/B
не доказывает исправление блокировок YouTube. Первый прогон был завершён
раньше 90 попыток, его результат не учитывать за полный.

### Изменения, требующие новой полевой проверки

- Для локального VpnService добавлена настройка обработки **всего TCP
  443**, когда сервер CDN/YouTube определился только по IP или при TLS ECH.
  По умолчанию включена и применяется **только в выбранном режиме Zapret2
  VpnService**. Трафик TCP/443 за пределами списка доменов тоже проходит
  через локальный desync-выход, но не через внешние серверы. Выключение
  настройки возвращает прежнюю строгую маршрутизацию по hostlist.
- Добавлен вариант `split-1`: первый байт TLS ClientHello отправляется
  отдельно от остального; читабельный SNI не требуется. Это безопасная
  TCP-фрагментация без подмены данных (не полная реализация
  `nfqws2 multisplit`). Проверка не-TLS трафика и точного сохранения
  ClientHello выполняется в Go-тесте.
- Переключатель `QUIC → TCP` остаётся самостоятельным: текущий
  `true` блокирует UDP/443. Для оценки QUIC-подделки следует отдельно
  проверить `false`, чтобы не приписывать эффект TCP-режиму.

**Приёмочный критерий на мобильной сети:** страница YouTube обновляется,
комментарии загружаются, превью отображаются, реальный видеопоток
начинается и продолжает играть несколько минут. Отдельно проверять
`googlevideo.com`, `ytimg.com`, `youtubei.googleapis.com` и
отмечать влияние QUIC, IPv4/IPv6 и TCP-приёма. Пройденная
`go test`/Gradle/Android emulator проверка не заменяет этот критерий.

### Исправление переключателя QUIC

До изменения `splitQuicTag` в локальном `compileServerless` для
`disorder`/`split`/`split-1` **всегда** отправлял QUIC доменов
hostlist в `blackhole` — даже когда пользователь выключал «QUIC → TCP».
Теперь этот переключатель действительно действует: при `false` QUIC
без UDP fake идёт напрямую, при `true` всё UDP/443 блокируется; у
`fake-N` и `false` поток hostlist получает экспериментальную UDP
подделку. Это устраняет логическую ошибку, но само по себе не
подтверждает воспроизведение YouTube.

### Дополнение к обработке CDN с неизвестным IP/именем

При включённом переключателе HTTPS/QUIC без определения домена,
выключенном `QUIC → TCP` и выбранном `fake-3`/`fake-5` (или другом
Fake TTL) безrootовый VPN отправляет также **UDP/443 без распознанного
домена** через локальный QUIC-десинхронизатор. Он отправляет ложные
пакеты **только** при распознанном QUIC Initial; остальная UDP-нагрузка
передаётся без подделки. Это нужно, когда CDN YouTube использует адрес IP,
а Xray не обнаружил SNI. При `QUIC → TCP=true` по-прежнему действует
глобальная блокировка UDP/443; при других TCP-стратегиях QUIC идёт
напрямую. Функциональную загрузку видео требуется проверять на мобильной
сети, успешная компиляция не доказывает работу.

## Полевой отчёт YouTube — мобильная сеть, 21.11.2026

Автор проверил **обе** подписанные APK `v0.7.54-alpha.3` и `v0.7.54-alpha.4`
на Android API 35 (arm64, мобильная сеть). Метаданные и некоторые миниатюры
поступают, но перезагрузка главной страницы, комментарии и воспроизведение
видео не работают ни при одном из испробованных переключателей локального
Zapret2 VpnService. Статус `connected` — только успешный запуск туннеля,
**не приёмка YouTube**. Проблема остаётся открытой.

Журнал второго полноценного А/Б-цикла: **89/90**, одна ошибка
`fake-8`: `ENDPOINT_UNREACHABLE` (8.011 с); 10/10 попыток `plain`
тоже успешны, поэтому испытание не подтверждает обход DPI именно для
`youtube.com`, `youtubei.googleapis.com` и `googlevideo.com`.
Первый цикл был остановлен до 90 попыток (`finished by=done` после
15 событий). Эти тесты сохраняем как реальные измерения; повторно
запрашивать их у автора не нужно.

Исправление после отчёта: при TCP TLS ClientHello без читаемого SNI
(например, ECH или IP-only CDN) варианты `Fake TTL`, `Disorder` и
`Split SNI` больше не пропускают всё соединение без обработки —
применяют безопасное разделение **первого байта TLS** и передают
остальные исходные байты без модификаций. Покрыто тестами Go на настоящем
ClientHello без SNI. Безrootовый путь по-прежнему **не** содержит
полного ядра оригинального `nfqws2`, а доступность YouTube на
мобильном операторе остаётся **неподтверждённой** до нового полевого
испытания конкретных запросов, а не только общей доступности TCP.

## Полевой отчёт Alpine: сеть NORMAL, YouTube не работает, скорость PAYLOAD_STALLED (22.11.2026)

С Android 15 по мобильной сети получено **подтверждение запуска Alpine**:
`zapret2_alpine_ready status=socket_probed process_alive=true`,
`zapret2_planner mode=alpine status=selected`; Xray сообщил
`connected ... zapret2_planner=alpine`. Настройки испытания:
`local_desync=fake-3`, `quic_force_tcp=true`, пустой hostlist.
YouTube не загрузился; HTTPS-замер скорости завершился
`PAYLOAD_STALLED` / `context deadline exceeded`.

Важное различие: кнопка **«Проверка сети»** вызывает
`NetworkCheck.run` и `SocketProber` на физической underlying-сети.
Её успехи `CAPTIVE/DNS/TCP/TLS/UDP/BULK` показывают доступность
тестовых ориентиров **через мобильную сеть, не через путь Zapret2**.
`NORMAL/HIGH` не означает, что CDN YouTube доступны через VPN.
Кнопка **«Замер скорости»** использует другой механизм:
`bridge.SpeedTest` → исходящий `proxy` Xray → локальная стратегия
Zapret2 → HTTPS `speed.cloudflare.com/__down`. Данные этого
конкретного маршрута не пришли в срок; ошибка не определяет сама по
себе, заблокирован ли весь IP, TLS или только HTTP-поток.

Для следующего теста добавлены **поэтапные безопасные причины** в
диагностику: `speed_stage=outbound_dial|tls_handshake|latency_http|download_headers|download_body`,
`completed_pings=N`, `download_bytes=N`. Если TLS ClientHello не
получил полноценного ответа, результат теперь `TLS_HANDSHAKE_FAILED`,
а не ошибочное `PAYLOAD_STALLED` только потому, что пришли отдельные
TLS-байты. Сообщение больше не утверждает, что существует удалённый
«сервер профиля»: для локального Zapret2 это прямой Xray-маршрут.
Счётчики `speed_desync_counters scope=process_delta applied=… skipped=…`
показывают изменения **общих счётчиков процесса** на время замера;
одновременно работающие приложения тоже могут влиять на разницу.
В журнал не добавляются имена посещаемых пользователем сайтов или
содержимое пакетов.

Ни один из этих диагностических шагов **не доказывает или не обещает**
исправление YouTube, скорость и прохождение DPI: требуется отдельная
проверка содержимого YouTube, `googlevideo.com` и `ytimg.com` на
реальном устройстве. Основные алгоритмы desync не подменяются
невидимым обходом или прямой сетью при ошибках.

## Автоматическая адаптация VPN-соединений (22.11.2026)

Журнал мобильного Android 15 подтвердил частичное улучшение YouTube
(названия видео начали появляться), но лента и видео по-прежнему не
загружались полноценно даже при ручной смене `fake-3`, `fake-5`,
`disorder`, `split` и `split-1`. Все пробы `NetworkCheck` относятся к
**физической сети вне VPN**, поэтому не проверяют доступность YouTube.
Записи `connected` и `zapret2_alpine_ready` подтверждают только
VPN/Alpine readiness, не успешность конкретного сайта. Строка
`ACTIVATION_REJECTED: активация выполняется: восстановление отложено`
устранена из ошибки запуска: Android теперь асинхронно ждёт завершения
импорта/активации вместо конфликтующего повторного чтения состояния.

В настройках локального VPN добавлен **«Автоподбор для каждого
TCP-соединения»**. Защищённый Go-адаптер Xray выбирает одну из пяти
реализованных стратегий для **нового** TCP-соединения. Решение остаётся
фиксированным на весь сокет; использует тот же Alpine `PlanFor`, а не
второй набор разрозненных смещений или прямой выход при неудаче.
Кандидаты ведутся раздельно по SNI/HTTP Host, а при отсутствии имени —
по IP назначения. Достаточным сигналом в пользу кандидата считается
получение хотя бы 128 КиБ ответных данных; открытый TCP, ServerHello
или немного метаданных **не считаются** подтверждением успешной работы
YouTube. Два последующих слабых завершения ранее выбранного кандидата
снимают предпочтение и возвращают перебор на новых соединениях.
Состояния ограничены 1024 адресами, живут только в процессе и
сбрасываются на перезапуске VPN/смене физической сети.

В экране **«Соединения»** открытие карточки позволяет явно включить
или выключить адресный автоподбор для конкретного домена либо IPv4:
он действует на следующие подключения к этому адресу даже при
глобально выбранной ручной стратегии. Выбор пользователя хранится
только в приватных настройках приложения; пассивная история открываемых
сайтов для автоподбора не сохраняется. Доменное правило действует
также на поддомены по границе DNS-метки. Для автоматического режима с
выключенным `quic_force_tcp` новые QUIC Initial используют отдельный
перебор `fake-3` / `fake-5` по IP назначения (QUIC SNI в этом
транспорте недоступен без дешифрования). При включённом
`quic_force_tcp` UDP/443 остаётся заблокированным для перехода
приложений на TCP.

**Пределы метода.** Трафик не дублируется и не отправляется на
сторонний диагностический сервер. Продукт не вмешивается посередине
установленного TCP/QUIC-соединения и не гарантирует, что приложение
переподключится при остановке CDN. Полученные байты не всегда означают
воспроизведение видео или доступность всех доменов YouTube; реальные
испытания названий, миниатюр, комментариев, ленты, видео и перехода
MOBILE↔Wi-Fi остаются **открытыми**. Не закрывать PR до полевых
результатов.

## 2026-11-22: Feed-aware adaptive mode and field diagnostics

The Android 0.7.54-dev Alpine-enabled device log showed a running planner and
a successful Xray DNS health probe while YouTube loaded some titles but not the
next feed page. A `connected` event is **transport-ready**, not evidence that
YouTube feed pagination, thumbnails, comments or media playback succeeded.
The new event records `content_verified=false`; every 30 seconds
`zapret2_transfer_window` records aggregate uplink/downlink byte deltas and
cumulative applied/skipped strategy counts. No domain, full URL, cookie, token
or remote address is written by this event.

New local-VpnService settings default to `AUTO` if no explicit strategy was
previously stored. New AUTO configurations do not force UDP/443 to TCP by
default; the user's explicitly saved `QUIC → TCP` choice is respected.
The five shared TCP choices remain split-1, split, fake-3, fake-5 and disorder.
For protected QUIC flows the two selectable low-TTL fake modes remain fake-3
and fake-5. Explicit domains/IP addresses from the Connections screen are
adaptive even when a manual global TCP mode is selected (QUIC IP selection
also takes effect; encrypted QUIC destinations cannot in general be mapped
back to a selected hostname without more data).

The selector still does not inspect decrypted application content. A
128-KiB received payload confirms substantial transport progress and pins
the successful mode **before the long-lived connection closes**. Three
separate responses of at least 12 KiB each can weakly prefer the same
strategy for smaller feed/API traffic; one TLS handshake is not sufficient.
Two short closing flows remove an earlier preference, allowing rotation.
Learning is scoped to the active underlying network: generation-tagged
observations from old connections are ignored after network change or
selection change. Existing live TCP/QUIC streams are not modified mid-flight.

These are *heuristics*, not an assertion that YouTube has been unblocked.
Field acceptance must separately verify: feed scroll/pagination, images,
comments, video playback, Wi-Fi ↔ mobile transitions, explicit target
selection and force-TCP on/off, with the 30-second transport summaries.
The `work_finished reason=activity_stop` event in the supplied log is an
Activity work lifecycle event and does not itself prove that the VPN died.
The prior activation restore race was handled separately by a blocking
`restoreAwaitingActivation()` call and an informational busy status.


## Полевой журнал 22.11.2026 09:09–09:10 UTC: AUTO на мобильной сети

С устройства Android API 35 получены два последовательных сеанса
экспериментальной Alpine APK в VpnService, оба на мобильной сети.
В первом список сайтов был пуст (`rest=split`, `n=0`), во втором
пользователь применил набор YouTube/CDN из семи доменов
(`rest=direct`, `n=7`, `https_unmatched=true`).
Оба сеанса достигли `zapret2_alpine_ready` и `connected`, но
`content_verified=false` означает, что доступность конкретных
сайтов, ленты и видеопотока не измерена.

- `all_tcp=true selected=0` означает автоподбор для всех *новых*
  TCP-соединений и отсутствие отдельно выбранных вручную адресов.
  Нулевое `selected` не означает отключение AUTO.
- `quic_force_tcp=true` закрывает UDP/443, поэтому ни один QUIC
  кандидат не участвует в подборе. Это отдельный сохранённый
  пользовательский выбор, и приложение не меняет его молча
  при активации AUTO. Для сравнения с UDP/QUIC необходимо отключить
  **«QUIC → TCP»** и переподключить VPN.
- За первое окно сообщено 166862 исходящих и 55041 входящих байт,
  за второе — 461414 исходящих и 35990 входящих байт. Это статистика
  переноса, а не байты видео или доказательство успешной загрузки.
  `applied_total`/`skipped_total` — накопленные счётчики
  процесса и не должны сравниваться напрямую с байтами одного окна.
- `ACTIVATION_REJECTED` с уровнем INFO и сообщением об отложенном
  восстановлении не является отказом туннеля; `activity_stop`
  относится к жизненному циклу Activity.

После этого отчёта добавлены
`zapret2_auto_quic_blocked reason=force_tcp_enabled` и
`quic_trials_enabled` в диагностике, а в `zapret2_transfer_window`
появились `applied_delta` и `skipped_delta` за интервал.
Счётчики desync привязаны к началу текущего сеанса, чтобы
не считать старые попытки за новые. В интерфейсе показывается
пояснение, если одновременно выбраны AUTO и «QUIC → TCP».
Эти изменения улучшают интерпретацию полевого лога,
**не являются доказанным исправлением YouTube**.

Для приёмки требуются отдельные испытания при
`quic_force_tcp=true` и `false`, с открытием ленты,
миниатюр и реального видео на одном и том же операторе;
отметить, продолжает ли счётчик входящих байт расти
во время фактического просмотра. При существенных замедлениях
в новой сборке прислать полный журнал и указать, какие именно
действия выполнялись с YouTube в каждом окне.


## Безrootовый комбинированный TLS-record + TCP split (22.11.2026)

В PR #37 добавлен экспериментальный **`tlsrec-split`** для локального
Zapret2 VpnService / Alpine. Он следует из исследования
`docs/research/SERVERLESS_DPI_FEASIBILITY_2026-11-22.md`:
некоторые измерения фильтрации в РФ показали разницу между обычным TCP
split, разделением TLS-записей и **комбинацией** обоих методов.

- Обработка выполняется для полного начального TLS ClientHello,
  когда он помещается в одну исходную TLS-запись. Общий планировщик
  `tools/xray/zapret2` создаёт **две корректные handshake TLS-записи**
  с неизменённым содержимым ClientHello; защищённый Android TCP-сокет
  отправляет их двумя отдельными `Write` с коротким интервалом.
  TLS-ключи, имя сервера, сертификаты и приложение не изменяются.
- При отсутствии полного ClientHello для нового режима используется
  существующий первый-байтный TCP split, **не подделка и не повреждение
  данных**. Не-TLS трафик идёт без этого приёма.
- Новый ручной пункт добавлен **в конец** списка настроек, чтобы не
  менять прежние варианты; для `AUTO` он шестой кандидат после
  `split-1`, `split`, `fake-3`, `fake-5`, `disorder`.
  QUIC-`AUTO` остаётся отдельно с вариантами `fake-3` и `fake-5`;
  переключатель «QUIC → TCP» сохраняет выбранное пользователем значение.
- Обрабатываются только исходящие TCP-сокеты локального эксперимента
  с тегом `dppass:exp-*`; обычные подписки, root `nfqws2`,
  правила приложений и DNS не затрагиваются. Alpine / PRoot не выдаёт
  прав NFQUEUE и остаётся единственным авторитетом планирования, если
  включён в экспериментальный APK.
- Границы метода: TLS-записи должны соответствовать RFC, но отправка в
  двух вызовах `Write` не гарантирует двух физических TCP-сегментов
  на каждом модеме. Требуются испытания на Android / реальном операторе.
  Данный приём не обходит IP/ASN-блокировку, доступность через белые
  списки, лимит ~16 КиБ на ответ или геоблокировку сам по себе.

**Проверки CI:** восстановление исходных байтов ClientHello из двух
TLS-записей, сохранение последующих записей, отказ от модификации
неполного и не-TLS ввода, реальный TLS/HTTP ответ через защищаемый
TCP-адаптер, порядок кандидатов AUTO. Эти тесты не доказывают обход
DPI или работу YouTube на мобильной сети.

**Полевое сравнение:** сначала сохранить `QUIC → TCP=true` и
проверить вручную `split`, `tlsrec-split`, `AUTO` при одинаковых
действиях (лента, миниатюры, комментарии, реальное видео); затем
отдельно проверить `QUIC → TCP=false`. Собирать результаты работы
содержимого и агрегатные счётчики, не пользовательские URL.
