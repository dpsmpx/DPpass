# Модель безопасности DPpass

Срез на 6 октября 2026 (версия 0.5.0: адаптивная устойчивость D-44,
автосплит D-45, защита от обнаружения VPN D-46 и анализа на устройстве
D-47). Угрозы пронумерованы (T1…); код и документы
ссылаются на номер, `docs.refs` DP Verify (`tools/dpverify.toml`) проверяет, что он
здесь определён. Номер не переиспользуется.

## 1. Что защищается

| Актив | Почему важен |
|---|---|
| Учётные данные серверов (UUID VLESS, пароли, short_id REALITY) | дают доступ к серверу пользователя; утечка — чужой трафик на его счёт или блокировка сервера |
| Адрес подписки | обычно содержит токен доступа ко всем серверам поставщика |
| Конфигурация и маршрутизация | показывают, какие сервисы пользователь пускает через туннель |
| Трафик и DNS-запросы приложений в туннеле | то, ради чего туннель существует |
| Сам факт и параметры использования | идентификаторы устройства, история подключений |

## 2. Границы доверия

- **Пользователь** доверен: это его устройство и его конфигурация. Он
  видит и контролирует всё, что DPpass делает (D-11).
- **Поставщик подписки** доверен в выборе серверов (сервер видит
  трафик — от этого клиент не защищает), но **не доверен** в управлении
  клиентом: он не может менять поведение клиента без согласия
  пользователя.
- **Сеть** (оператор, Wi-Fi, системы фильтрации) не доверена: может
  читать, подменять, резать и зондировать.
- **Другие приложения на устройстве** не доверены: не должны получать
  секреты, локальные входы ядра, экспортированные компоненты.
- **Ядро прокси** (Xray, этап 2) доверено как исполнитель, но
  получает только скомпилированную конфигурацию и обновляется по
  чек-листу (D-18).
- **Цепочка поставки** (зависимости, Gradle) не доверена по
  умолчанию: каждая часть записана, закреплена и проверяется.

Вне модели: устройство с root или вредоносной прошивкой, физический
доступ к разблокированному устройству, скомпрометированный сервер
пользователя.

## 3. Метаданные подписки

Поставщик передаёт метаданные заголовками ответа и строками
`#ключ: значение` в теле. DPpass делит их на два класса
(`subscriptions/Metadata.kt`):

**Информационные — применяются** (показываются, поведение клиента не
меняют):

| Ключ | Что | Ограничения |
|---|---|---|
| `profile-title` | название | ≤ 64 символов, без управляющих; `base64:` — декодируется |
| `profile-update-interval` | интервал обновления, часы | 1…720 |
| `subscription-userinfo` | трафик и срок (`upload`, `download`, `total`, `expire`) | неотрицательные целые |
| `support-url`, `profile-web-page-url` | ссылки поддержки | только `https://`, ≤ 512 символов |
| `announce` | объявление | обрезается до 200 символов |

Пустое значение — «не задано» (панели присылают незаполненные поля
пустыми заголовками). Неверное значение — предупреждение `SUBSCRIPTION_METADATA_INVALID`,
поле не применяется.

**Управляющие — не применяются никогда**: смена адреса подписки
(`new-url`, `new-domain`, `fallback-*`), скрытие настроек (`hide-*`),
маршрутизация, DNS, списки приложений, TUN, mux, фрагментация, «шумы»,
пользовательские ядра, автозапуск, идентификаторы (`hwid`,
`provider-id`) и прочее. Найденные — одно предупреждение
`SUBSCRIPTION_DIRECTIVE_IGNORED` со **списком имён** (значения в
сообщения не попадают: в них бывают адреса и токены). Прочие
HTTP-заголовки (`content-type` и т. п.) не рассматриваются; в теле
отмечается любой неинформационный ключ. Заголовок важнее строки тела.

**Маршрутизация и DNS поставщика** (подписка — документ DPpass)
применяются, только если пользователь явно привязал к ним подписку
(`RoutingBinding.PROVIDER_ROUTING`); иначе — предупреждение и
маршрутизация пользователя.

## 4. Угрозы

### T1 — Подменённая или скомпрометированная подписка

Подмена ответа в сети, взлом поставщика, «внезапно другое» содержимое.
**Меры:** загрузка только по HTTPS с системными CA (этап 3,
`check_manifest.py` запрещает открытый HTTP); адрес подписки не
меняется по указанию подписки (§3); каждая ревизия — с контрольной
суммой; содержимое проходит разбор, проверку и фильтр по возможностям
ядра; активация транзакционна, неудача не трогает действующую
конфигурацию (D-07, D-08). **Остаётся:** поставщик выбирает серверы, а
сервер видит трафик — от честно выданного «плохого» сервера клиент не
защищает.

### T2 — Подписка управляет клиентом

Директивы поставщика, меняющие поведение без согласия пользователя.
**Меры:** §3 — применяются только информационные метаданные;
маршрутизация и DNS поставщика — только по явной привязке (D-11).
**Проверка:** `MetadataParserTest`, корпус
`tests/data/subscriptions/links-with-directives`, `native-document`.

### T3 — Утечка секретов через журнал, отчёт, ошибки, экспорт

**Меры:** тип `Secret` (`toString()` — метка, `reveal()` — только в
разрешённых местах, `code.forbidden`, правило `secret-reveal`); `Redactor` для каждой
строки журнала; отчёт при выводе ещё раз проходит строгий уровень;
сообщения разбора — без цитаты входа; исключения — тип и
отредактированное сообщение, без стека (запись о падении в журнале
устройства — ещё кадры стека: класс, метод, строка, без данных);
журнал устройства (D-26) пишет только отредактированные события, а
наружу уходит через буфер обмена после `STRICT` (без IP и имён хостов — и
в ссылках, и в тексте ошибок ядра) и с
пометкой «чувствительное» на Android 13+ (с выключенным журналом — те же
события кольца памяти, что в локальном отчёте, D-54); `CompiledConfig` не печатает
содержимое; экспорт по умолчанию — с метками вместо секретов, такой
документ не активируется (в приложении — «Сохранить» и «Поделиться без
секретов»; с секретами — только в файл, через системный выбор файла и
после предупреждения, документ в памяти до записи); журнал Xray выключен в самой конфигурации
ядра (его журнал доступа пишет адреса назначения мимо `Redactor`).
**Проверка:** `SecretLeakTest`, `RedactorTest`,
`LoggerTest`, `XrayCompilerTest.xrayLogIsOff`, корпус `invalid-redacted-export`,
`LogExportTest`, `CrashRecordTest`, `ExportTest`.

### T4 — Трафик мимо туннеля

IPv6 без маршрута, DNS-запросы в обход, петля собственного трафика,
резолв имени системным резолвером. **Меры:** IPv6 всегда маршрутизуется
в туннель (`TunnelSpec`); предупреждение `DNS_LEAK_RISK`, если
сервер DNS по умолчанию идёт мимо туннеля при включённой защите;
собственный пакет DPpass всегда вне туннеля; каждый исходящий сокет
ядра до соединения проходит через `protect()` (мост ядра, D-25: хук
Xray на сокеты; отказ защитника — сокет подменяется непригодным, путь
закрыт, а не уходит петлёй в туннель; TUN без защитника — отказ
запуска); адреса — без DNS (`getByName` запрещён,
`code.forbidden`, правило `dns-resolve`; разрешён резолв имени сервера для
замера задержки, D-41, и имён ориентиров для проверки сети — по кнопке и после смены сети, D-60, D-67, на ПК — D-79, D-80:
это пробы самой сети, а не трафик приложений; на ПК имена ориентиров резолвит резолвер
моста с меткой, а сокеты проб несут ту же метку `SO_MARK`, что сокеты ядра, — без метки
проба отказывает, а не идёт в туннель, D-79). Приложения, исключённые из туннеля,
резолвят через систему — это свойство режима, оно показывается, а не
скрывается. В конфигурации Xray (D-24): DNS-запросы приложений к
адресу TUN перехватывает ядро и отвечает по DnsPolicy; запросы каждого
DNS-сервера маршрутизируются по его `route` правилом раньше правил
пользователя («всё напрямую» не уведёт туннельный DNS мимо туннеля);
имя из правила DNS не уходит к запасному серверу, если его сервер не
ответил; прямой исходящий резолвит имя DNS ядра без отката к
системному резолверу; DNS-over-TLS, которого в Xray нет, отвергается,
а не заменяется открытым DNS. **Имя сервера профиля** (D-29) резолвит
система вне туннеля: у исходящего `proxy` нет `sockopt`, Xray отдаёт имя
системному dialer, Go на Android спрашивает системную библиотеку, а
пакет DPpass вне туннеля — петли нет. Мимо туннеля уходят только имена
серверов, не имена назначений; с «Частным DNS» Android — через
DNS-over-TLS, без него — открыто в DNS сети. Это свойство показывается,
а не скрывается; профиль с адресом IP не резолвится. Так же — проверка
задержки (D-41): только по действию пользователя, имена только
серверов, через систему вне туннеля (`TcpLatencyProbe` — единственное
разрешённое место в `network/`). Режим «Российское напрямую» (D-38)
отдаёт имена российских сайтов системному резолверу и сами соединения
— мимо сервера: это назначение режима, оно написано рядом с
переключателем. Список «Напрямую с разбиением» (D-72) ведёт соединения
к выбранным сайтам мимо сервера, имя назначения резолвит DNS ядра по
DnsPolicy, как у `direct`; это назначение списка, оно написано у поля
ввода; подписка его не задаёт и не меняет (D-11). Без сервера (D-73)
туннеля к серверу нет: имена спрашиваются напрямую — DoH из «DNS»
(мимо резолвера оператора) или системным резолвером, по выбору у
настройки; DNS через туннель в этом режиме — отказ компиляции, а не
молчаливая замена. Пустой список «только эти приложения» — отказ
`APP_POLICY_CONFLICT`, а не туннель для всех (иначе выбор пользователя
молча расширился бы). **Проверка:** `TunnelSpecBuilderTest`,
`TunnelAppPolicyTest.emptyOnlyAppsIsRejectedNotWidenedToAll`, `PolicyBuilderTest`,
`DnsValidatorTest`, `XrayCompilerTest.dnsQueriesFollowTheirRouteBeforeUserRules`,
`XrayCompilerTest.dnsRulesFirstMatchWinsWithoutFallback`,
`XrayCompilerTest.splitSitesGoDirectThroughFragmentAndQuicIsBlocked`,
`XrayCompilerTest.serverlessDialsOnlyDirectOutbounds`,
`XrayCompilerTest.serverNameIsLeftToTheSystemResolver`, `XrayTunnelContractTest`,
эталоны Xray (`docs/TESTING.md`, «Эталоны Xray»), `go test` моста и
`XrayJniTest` (защитник видит каждый сокет ядра, отказ и исключение в
нём закрывают путь, `docs/TESTING.md`, «Мост Xray и JNI»); на
устройстве — этап 2.

**На Linux (D-74).** `VpnService` нет: сокеты ядра выводятся из туннеля
меткой `SO_MARK`, правило метки стоит раньше правил туннеля; не вышло —
сокет отравляется, как на Android. DNS на порт 53 любого адреса уходит
в туннель отдельной таблицей без исключений, ядро перехватывает его на
любой адрес — запрос к резолверу роутера не уходит мимо туннеля при
«локальная сеть напрямую». Имена серверов профилей резолвит резолвер Go
моста с той же меткой — мимо туннеля, открыто в DNS сети (как на
Android без «Частного DNS»). Политика приложений не выражается — отказ,
а не туннель для всех. После смерти процесса правила остаются, но
таблицы пусты (TUN исчез вместе с маршрутами): трафик идёт как без
DPpass, а не в никуда и не петлёй; при следующем запуске правила
убираются. **Проверка:** `LinuxRoutesTest`,
`XrayCompilerTest.dnsHijackAnyAddressOnLinux`, `go test` моста,
`tools/desktop/netns_check.py`; на ПК — этап 6.

### T5 — Подмена TLS

**Меры:** отключение проверки сертификата не принимается ни в документе
(`INSECURE_TLS_REJECTED`), ни в ссылке; приложение доверяет только
системным CA; свои `TrustManager`/`HostnameVerifier` запрещены
(`code.forbidden`, правило `trust-override`). Компилятор Xray не пишет полей, которые
ослабляют проверку (`pinnedPeerCertSha256`, `verifyPeerCertByName`,
`disableSystemRoot`); `allowInsecure` в Xray 26.9.30 и сам — ошибка
сборки конфигурации. Проба здоровья через сервер DoH (D-32) проверяет
его сертификат системными корнями; настройки, которая бы это выключила,
нет. **Проверка:** корпус
`invalid-allow-insecure`, `ShareLinkParserTest.insecureIsRejected`,
`XrayCompilerTest.certificateCheckCannotBeDisabled`, `go test` моста
(`TestProbeVerifiesDoHCertificate`).

### T6 — Вредоносный вход

Документ, тело подписки или ссылка, рассчитанные на падение, зависание
или исчерпание памяти. **Меры:** пределы до разбора вглубь (размер,
глубина, длина строк, число профилей, правил и значений); строгий JSON
без рекурсии сверх предела; разбор не бросает исключений; проверка
правил — не хуже квадрата их числа (предел 4096 правил укладывается в
тайм-аут fuzz). **Проверка:**
`FuzzTest` (каждый прогон, фиксированное зерно, тайм-аут на вход),
`ConfigLoaderTest.limitsAreEnforcedBeforeParsing`.

### T7 — Доступ к данным на устройстве

Другие приложения, облачная резервная копия, перенос на другое
устройство, копия файлов без root. **Меры:** данные в
`noBackupFilesDir` (и журнал устройства — `noBackupFilesDir/log`,
D-26); AES-256-GCM, ключ данных обёрнут неизвлекаемым
ключом Android Keystore; резервные копии и перенос выключены (D-19).
Встроенный список своих серверов (D-42) хранится в той же
зашифрованной записи подписок и в памяти — `Secret`.
Сбой или утрата ключа не превращаются в порчу записей и не затирают
сохранённое молча; сброс — действием пользователя, с отложенной копией.
**Проверка:** `StorageTest`, `DataKeyTest`, `StorageKeyLossTest`,
`check_manifest.py`; на устройстве — этап 3.

**На Linux (D-74)** Keystore нет: данные и ключ данных — в
`$XDG_DATA_HOME/dppass`, каталоги 0700, файлы 0600. От других
пользователей ПК защищают права файлов; от программ того же
пользователя ключ не защищён — это свойство оболочки, оно записано, а
не скрыто. **Проверка:** `DesktopStorageTest`.

### T8 — Обнаружение VPN другими приложениями

Любое приложение видит сеть `TRANSPORT_VPN` и интерфейс `tun*`, даже
исключённое из туннеля (`docs/research/ANDROID_NETWORK_MODEL.md`, §6);
методика выявления VPN приложениями ищет именно это, а также службы
VpnService в `dumpsys`, host-route `/32`, аномалию MTU и несовпадение IP
по геолокации/ASN (`docs/research/RUSSIA_NETWORK_RESTRICTIONS.md`, §1).
**DPpass скрыть сам факт VPN не может и не обещает** (D-13, D-46).
**Меры (D-46), не ломающие работу:** раздельный маршрут (D-45) уводит
трафик отечественных сервисов и собственного пакета DPpass мимо туннеля
(D-17) — у них домашний IP, и проверка «underlying network»/exit-IP для
них не срабатывает; локальных входов и экспортируемых внутренностей нет
(T11, T13) — проверка портов прокси и API ядра ничего не находит, пока
пользователь не включил раздачу (D-51: тогда порт с паролем открыт на
адресе раздачи, и это сказано на её экране);
быстрая пауза кнопкой и плиткой (D-40); имя пакета и ярлык случайны и без
слова «VPN» (D-47) — приложение не выделяется в списке по имени. Режим
без `VpnService` (локальный прокси) не создаёт `TRANSPORT_VPN` —
отложенное решение. **Проверка:** `PolicyBuilderTest`,
`TunnelSpecBuilderTest`, `check_manifest.py`, `go test` моста (T11).

### T9 — Секреты на экране

Снимки и запись экрана, миниатюры в «Недавних», наложение чужого окна.
**Меры:** `FLAG_SECURE` на всём интерфейсе (одна `Activity`, D-34) и на
окнах диалогов и нижних листов (`Ui.secure`, D-47: у `AlertDialog` своё
окно, флаг активности его не закрывает); критичные элементы (кнопка
подключения, подтверждение импорта) не принимают касания через наложение
(`filterTouchesWhenObscured`, tapjacking); уведомление туннеля на
заблокированном экране — без имени сервера (`VISIBILITY_PRIVATE` с
публичной версией): имя часто называет страну и поставщика; вопрос о
смене сервера (D-58) там же — без имён и без кнопок, выбор — после
разблокировки; напоминание о конце подписки (D-76) там же — без имени
подписки (оно часто называет поставщика), кнопки будильника «Закрыть» и
«Отложить» ничего не раскрывают. **Проверка:**
обзор кода (`Ui.secure`, `filterTouchesWhenObscured`), на устройстве
(`TODO.md`).

### T10 — Цепочка поставки

Подменённая или изменившая лицензию зависимость, подменённый Gradle,
подменённое ядро прокси или его модули, сторонний код в инфраструктуре
проверок. **Меры:** версии закреплены в
одном каталоге, каждая — в матрице лицензий и PROVENANCE
(`provenance.deps`, `check_dependencies.py`); SHA-256 дистрибутива и wrapper Gradle сверены
с services.gradle.org и записаны; репозитории — только Google и Maven
Central (и портал плагинов для сборки); Xray — только upstream, его
версия и каждый модуль Go — в матрице и PROVENANCE с суммой из
`go.sum`, директивы `replace` запрещены, сборка — с `-mod=readonly` и
сверкой sum.golang.org, а с выключенной сверкой шаг «Xray» не
запускается (D-24); библиотека ядра в APK собирается из того же
`go.mod` тем же способом (`tools/xray/native.py`, D-25), NDK — версии
из каталога, другой не используется; в APK — только она
(`check_apk.py`: нативный код, экспорт JNI). Геоданные (D-27) — только
из первичных источников с известной лицензией (dlc, DB-IP; GeoLite2 —
запрещён), закреплённых в каталоге с SHA-256 и собранных своим кодом;
клиент их не скачивает — обновляются вместе с приложением. CI нет — проверки идут
локально, сторонних действий GitHub Actions в цепочке нет (D-23;
`docs/PROCESS.md`, «Перед слиянием»).

### T11 — Локальные входы ядра

SOCKS/HTTP-вход ядра на `127.0.0.1` доступен любому приложению на
устройстве. **Меры:** локальных входов нет — мост ядра (D-25)
проверяет собранную конфигурацию (protobuf, а не JSON) и запускает
только вход TUN; службы ядра — только журнал, DNS,
маршрутизация, политики, счётчики (без API gRPC, метрик HTTP и
прочего). Тестовый вход на loopback допускается только в сборке моста
для хоста (тег `dppass_testinbound`), в библиотеке для APK его нет.
Мост fd → ядро — вход TUN Xray (D-30): локальный вход не нужен.
**Правило:** локальный вход — только с аутентификацией и случайным
портом; вход без аутентификации — запрещён.

**Раздача (D-51)** — единственное исключение, по этому правилу и только
по выбору пользователя: вход SOCKS5 (он же HTTP-прокси) с логином и
паролем, случайный порт от 20000, только на частных IPv4-адресах
интерфейсов раздачи (не `0.0.0.0`, не loopback, не Wi-Fi-клиент и не
мобильная сеть — интерфейс раздачи не должен быть сетью
`ConnectivityManager`; не удалось узнать сети — входа нет). Мост
пропускает такой вход, только если у него тег раздачи компилятора,
пароль, частный IPv4 и порт от 1024. Первое правило маршрутизации
пускает на входы раздачи только клиентов из подсетей раздачи и не с
адресов самого телефона: приложение телефона, даже знающее пароль, не
обходит через прокси политику приложений (D-38). «Напрямую» клиент
раздачи ходит через свой исходящий с `finalRules`, закрытый для
loopback и «нуля» телефона (`127.0.0.0/8`, `0.0.0.0/8`, `::1`, `::`):
службы, которые слушают только 127.0.0.1, из сети раздачи не видны.
Ядро, запущенное посреди проверки здоровья, при остановке тоже
останавливается: вход раздачи не живёт без туннеля и со сменённым
паролем. Логин и пароль —
случайные, в зашифрованном хранилище (D-19), видны только на экране
раздачи (`FLAG_SECURE`, T9), в буфер — с пометкой «чувствительное».

**Раздача на ПК (D-84)** — те же вход, правила и настройки, но интерфейсы
раздачи называет NetworkManager: только активные соединения с
`ipv4.method shared` (точка доступа ПК), не интерфейс маршрута по
умолчанию; нет `nmcli`, отказ или непонятный ответ — входа нет. Ответы
входа гостям — мимо туннеля правилом к подсети раздачи (D-84), а не
меткой: программы ПК идут к входу с адреса самого ПК и отсекаются тем же
первым правилом, что и приложения телефона. **Ограничения:** запрета
снимка экрана на ПК нет — пароль на вкладке «Раздача» скрыт, пока его не
показали; пометки «чувствительное» у буфера обмена X11 и Wayland через
AWT нет — скопированный пароль может остаться в истории буфера.
**Остаётся:** пока раздача включена, открытый порт видят приложения
телефона и устройства в раздаче (T8).

**Проверка:** `go test` моста (`TestPolicyAllowsOnlyTunInbound`,
`TestPolicyAllowsOnlyAuthenticatedShareInbound`),
`XrayJniTest.foreignInboundIsRejectedByBridgePolicy`,
`XrayJniTest.shareInboundPassesBridgePolicy`,
`XrayCompilerTest.shareInboundsListenOnlyOnTetherAddressesWithAuth`,
`TetherInterfacesTest`, `ShareSettingsTest`.

### T12 — Телеметрия и идентификаторы

**Меры:** ничего не отправляется о пользователе и устройстве (D-12):
нет SDK аналитики и отчётов о падениях (матрица лицензий; в собранном
APK — только код из утверждённых корней пакетов, `check_apk.py`),
идентификаторов системы и железа нет в запросах подписки, отчёт —
только локальный. Поставщику с лимитом устройств (Remnawave) уходит
`x-hwid` — только если пользователь включил его для этой подписки: это
128 случайных бит, свои у каждой подписки и не связанные с устройством;
модель и ОС не отправляются (D-33). Ответ «нужен идентификатор» или
«лимит исчерпан» называется кодом, его заглушка не загружается. Журнал устройства
и запись о падении (D-26) остаются на устройстве: наружу — только по явной
кнопке «Копировать журнал» (D-47: автокопии при уходе с экрана больше нет,
буфер обмена видят другие приложения); идентификаторов устройства в журнале
нет (версия приложения, уровень API и ABI — да; модель и серийный номер — нет).
Адаптивная модель устойчивости (D-44) тоже не содержит идентификаторов и
трафика — только числовые агрегаты по грубому контексту сети (T14).
Проба IPv6 через сервер (D-66) — запрос «. NS» к открытым резолверам
Cloudflare и Google через сервер профиля, раз за сессию: они видят адрес
сервера, а не телефона, и ничего о пользователе.

### T13 — Экспортированные компоненты Android

Чужое приложение запускает Activity или связывается с сервисом.
**Меры:** экспортированы только `MainActivity` (запуск и «Поделиться»
текстом и картинкой), `DPpassVpnService` под `BIND_VPN_SERVICE`, плитка
`DPpassTileService` под `BIND_QUICK_SETTINGS_TILE` и задание
`SubscriptionJobService` под `BIND_JOB_SERVICE` — сервисы связывает
только система; у экспортированного сервиса всегда есть разрешение, а
у фильтров Activity — только `MAIN`/`LAUNCHER`, `SEND text/plain` и
`SEND image/*` (D-65), без
схем и адресов (`check_manifest.py`; в итоговом манифесте APK, где
зависимость могла бы добавить свой компонент, — `check_apk.py`).
Текст «Поделиться», буфера обмена и файла — данные чужого приложения:
не больше 1 МиБ, распознаётся без сети и записи, применяется только
после подтверждения на экране (D-42); `http://`-подписка — отказ.
Картинка с QR (выбор файла или «Поделиться», D-65) — тоже чужие данные:
читается не больше 32 МиБ, разбирается системным декодером с уменьшением
до 2048² пикселей, QR распознаёт ZXing только над пикселями. Текст кода
дальше — тем же путём, с подтверждением; ни картинка, ни текст не
сохраняются и не пишутся в журнал.
QR камерой (D-71) — разрешение `CAMERA` только по нажатию «QR-код
камерой»; камера открыта, лишь пока экран сканирования виден, в фоне
DPpass её не держит. Кадры разбираются в памяти (ZXing над яркостью
кадра), не сохраняются, из процесса не уходят; первый найденный код —
тем же путём, с подтверждением. Превью — в окне с `FLAG_SECURE` (T9).
Камера для приложения необязательна (`uses-feature required="false"`,
`check_manifest.py`).
Приёмники напоминания о конце подписки (D-76) не экспортированы: будильник
и кнопки — свои `PendingIntent`, загрузку и выданное разрешение на точный
будильник шлёт система; приёмник загрузки выключен, пока напоминание
выключено (`check_manifest.py`).
Плитка только включает и выключает туннель, как кнопка на экране: не
меняет ни сервер, ни настройки. Видимость пакетов (`<queries>`) —
только приложения с ярлыком запуска, для выбора приложений туннеля;
список не покидает устройство.

### T14 — Отравление адаптивной модели

Ошибочные или кратковременные сбои сети не должны превращаться в
постоянный плохой выбор кандидата, а наблюдения — нести чувствительное
(D-44). **Меры:** одно наблюдение не истина — априор Beta, затухание по
полураспаду, гистерезис переключения (несколько подтверждённых отказов);
обнаружение смены режима ускоряет вывод, но тоже забывается. В модель
кладёт наблюдения только сам клиент по своим попыткам — не сеть и не
подписка. Свои замеры (скорость D-61, проверка сети D-60 — и после смены сети, D-67) — не
наблюдения о сервере: во время них и 15 с после наблюдатель сессии пробу
не начинает, а начатую не учитывает (`QuietWindow`). Режим сети по
проверке (D-64) — только порядок: сеть, изображающая белый список,
поднимет CDN-кандидатов выше, но никого не исключит; память — в процессе,
30 минут и до смены сети. Проверка после смены сети (D-67) — не чаще 4 раз
в час и выключается: ориентиры видят адрес телефона в каждой новой сети, о
пользователе в пробах ничего нет (D-12). Контекст грубый (тип сети и класс ограничения, без SSID, BSSID,
адресов, оператора и идентификатора устройства, D-12), записей не больше
предела, агрегаты — в зашифрованном хранилище (D-19); ни доменов, ни
адресов назначения, ни payload, ни секретов. Историческая модель меняет
только **порядок** годных кандидатов — не жёсткие исключения D-15 (белый
список, UDP, backoff) и не явные правила пользователя. **Ограничение:**
пороги и веса не выверены на настоящих сетях (этап 3) и не считаются
статистически оптимальными. **Проверка:** `StabilityModelTest` (априор,
гистерезис, устойчивость к одиночному сбою, затухание), `StabilityBookTest`
(нет секретов и идентификаторов в хранимом),
`CandidatePlannerTest.learnedStabilityOrdersViableCandidates`,
`QuietWindowTest` (окно тишины после своих замеров), `RegimeTest` (режим сети — только порядок, отдельный опыт).

### T15 — Подключение через устройство раздачи

Через другой DPpass (D-55) трафик идёт по SOCKS5 с паролем без
шифрования прокси: логин, пароль и адреса назначения видны на канале
раздачи. Чужое «устройство» в сети или подписка могли бы увести трафик
пользователя через себя, а поиск устройства — выдать телефон в сети.
**Меры:** адрес — только частный IPv4 своей сети (RFC 1918), в
интернет такой профиль не пускается (`RELAY_ADDRESS_NOT_LOCAL`); в
документе и подписке протокола нет — устройство добавляет только
пользователь, вручную или ссылкой с подтверждением (D-11, D-42);
список и пароли — в зашифрованном хранилище (D-19), значения — только
на экране под `FLAG_SECURE` (T9), в причинах отказа их нет (T3); поиск
ничего не объявляет — спрашивается только шлюз своих сетей, и отвечает
лишь вход, знающий логин и пароль; подключение идёт только через
выбранное устройство — другие серверы молча не подставляются (D-05).
**Ограничение:** без шифрования на канале раздачи безопасна только
своя сеть — точка доступа с паролем, Bluetooth, USB; это сказано на
экране. **Проверка:** `RelayTest`,
`ProfileValidationTest.relayDeviceIsOnlyPrivateIpv4WithPasswordOverPlainTcp`,
`ProfileValidationTest.documentCannotCarryRelayDevice`.

### T16 — Сопряжение устройства раздачи

Сопряжение (D-56) выдаёт вход раздачи по сети: тот, кто вклинится между
телефонами или постучится на порт сопряжения, мог бы получить вход, а
открытый порт — выдать телефон. **Меры:** ключи P-256 с обязательством
хозяина и 6-значным кодом, который пользователь сравнивает на обоих
экранах (подмена даёт разные коды; угадать — 1 из 10⁶ за попытку); вход
создаётся и отправляется, только когда подтвердили оба, — зашифрованным
AES-256-GCM ключом из ECDH; порт открыт только по нажатию, не дольше
двух минут, только на адресах раздачи и для одного соединения; у
каждого сопряжённого — свой вход, который отзывается отдельно; без
своих TrustManager (T5). **Ограничение:** защита держится на том, что
человек сравнил код. **Проверка:** `PairingTest`,
`ShareSettingsTest.pairedDevicesHaveOwnLoginAndCanBeRevoked`.

### T17 — Права процесса на ПК (Linux)

Процесс приложения на Linux держит `CAP_NET_ADMIN` (D-74): ошибка в нём
или чужой код в нём могли бы менять сеть всего ПК; запуск с правами —
путь к повышению прав. **Меры:** процесс — от имени пользователя, а не
root, с одной возможностью (`setpriv`, ограничивающий набор — только
`net_admin`, окружение чистое — только проверенные переменные окна и
рабочего стола); процессы того же пользователя не
подключаются к нему отладчиком и не читают его память (у цели больше
возможностей); скрипт запуска и действие polkit — только из пакета в
`/usr`, не из домашнего каталога; команды `ip` и `nmcli` (D-84) — по
абсолютному пути, без shell, аргументы списком из `TunnelSpec` и констант,
с пределом времени; без `CAP_NET_ADMIN` подключение —
отказ с причиной. **Ограничение:** пароль администратора при каждом
запуске (кеш polkit — несколько минут). **Проверка:**
`DesktopLaunchTest`, `LinuxRoutesTest`, `SystemCommandTest`.

## 5. Чего DPpass не обещает

- «Работает гарантированно», «незаметен», «обходит белые списки» —
  этого клиент обещать не может (D-13, `docs/direction/RESEARCH_SCOPE.md`, §3).
- Защиты от сервера, которому пользователь сам отдал трафик.
- Защиты на устройстве с root или вредоносной прошивкой.
- Скрытия факта использования VPN от приложений на том же устройстве
  (T8).
