# DPpass 0.9 — единое локальное адаптивное ядро

Решение автора 24 ноября 2026. Рабочая ветка feature/dppass-0.8.3,
PR #59. Переход выполняется поэтапно; RC6 (162) — неподвижный
контрольный выпуск. Это направление не означает готовность 0.9.

## Цели и границы

- Один локальный режим AUTO вместо ручного выбора Zapret2/ByeDPI.
  Отдельно остаётся VPN подписки; его маршрутизация, DNS, учёт и выбор
  серверов не меняются.
- Общая библиотека методов с неизменяемыми идентификаторами и
  версионированным контрактом возможностей; повторяющиеся алгоритмы
  реализуются один раз. Выбор исполнителя и стратегии — на новое
  соединение, без перезапуска VPN ради одного потока.
- Перенос исходных компонентов, а не запуск сторонних CLI; предпочтение
  собственной библиотеке/собственному helper, собранному CI.
  Привилегированный helper ROOT при необходимости остаётся отдельным
  процессом DPpass, а не чужим готовым бинарником.
- ROOT требует явного согласия пользователя и проверяемых возможностей
  ядра. VpnService не обещает эквивалентность пакетным методам ROOT.
  PRoot не даёт привилегий ядра. Отказ в ROOT не должен незаметно
  переключать или разрывать пользовательские соединения.
- Все измерения и обучение локальны, без телеметрии и расшифровки TLS.
  Не менять активную стратегию посреди соединения, не повторять
  прикладные запросы без явной безопасной семантики.
- Нет гарантий доступности при недоступном маршруте или белом списке.

## Базовая архитектура

1. Каталог методов: стабильный ID, семейство происхождения, транспорт,
   необходимые возможности, поддержка исполнителем, статус проверки.
   Один источник истины вместо повторяющихся списков.
2. Планировщик: допустимость методов, ограниченный бюджет экспериментов,
   проверка совместимости, единый контроллер AUTO. Нейросеть ранжирует
   только доступные действия; детерминированный контроллер ограничивает
   риск и обрабатывает отсутствие доказательств.
3. Исполнители: защищённые сокеты/TUN без ROOT; собственный
   привилегированный пакетный/сокетный helper для ROOT.
4. Обратная связь: транспорт, проверенный прикладной ответ, качество,
   тайм-аут, отмена и недоступность маршрута — отдельные категории.
   Нулевое закрытие не равно отрицательному обучению; наблюдения
   привязаны к поколению сети и исполнителю.
5. Хранилище: только актуальный формат модели; при изменении архитектуры
   старые веса/наблюдения отбрасываются без миграции. Отдельный контекст
   ROOT/VpnService. Автоподбор серверов остаётся независимым.
6. DPTS: общий каталог и воспроизводимые тестовые пресеты, без
   размножения экранов и кнопок.

## A3 — первый контракт исполнителей и наблюдений

`tools/xray/localdpi/contract.go` задаёт версию контракта, тип исполнителя,
явно зарегистрированные пары метод/транспорт, запрет неподдерживаемых
методов и ROOT без подтверждённого разрешения. Порядок кандидатов остаётся
порядком каталога. FlowIdentity отделяет поколения сети и исполнители;
не содержит адресов, доменов и прикладных данных. Это контракт для будущих
адаптеров, а не новая реализация ROOT или проверка фактических прав ОС.

TCP/UDP в существующем Go-мосте используют общую классификацию закрытия
и тайм-аута; политика обучения RC6 сохранена. Нулевое закрытие нейтрально,
положительные байты — транспортное наблюдение, а не проверенный контент.
Новые тесты проверяют порядок, явные возможности, отказ по умолчанию,
изоляцию поколений и классификацию. A2 и A3 остаются открыты: полноценные
адаптеры, миграция модели и физические проверки ещё не выполнены.

## A4.3 — Go/C и сравнительные проверки

Подключён экспериментальный `localdpi_native` build tag: Go-планировщик
сохраняет выбор позиции, а кодировщик может использовать ограниченный

исходники C не включаются в APK. Нативный модуль компилируется из единого
канонического источника, без отдельного процесса. При отсутствии cgo
работает прежняя реализация. Добавлены побайтовые сравнительные тесты,
сохранение остатка потока и Android ARM64 cross-link отдельного теста.
Для tagged CI принудительная пересборка (-a) нужна из-за C includes
вне Go package. Тест Android cross-link не запускается на устройстве.
Новые CI результаты ожидаются; переключатель рабочего AUTO не менялся.
Перед включением в дистрибутив обязательны MIT notices и проверка APK.

## A4.4 — проверка интеграции в полной JNI-библиотеке

Отдельный CI режим native.py android --experimental-localdpi-native собирает полную libdppassxray.so с C-кодировщиком, проверяет фактическую зависимость localdpi/native, Android ELF/16 KiB и соответствие JNI. Дополнительный allowlist действует только для этого явного режима; обычная сборка и Gradle inputs не изменяются. В обоих вариантах проверяются зависимости также для целевого Android ABI. CI собирает эксперимент в RUNNER_TEMP, не в APK, без публикации. Принудительная пересборка исключает устаревший cache включаемых C-файлов. Это сборочная проверка, не физическое испытание. Полный перенос ByeDPI, ROOT и включение C-кода в APK остаются открытыми.

## A3 — общий вход транспортных наблюдений

Read и Close существующего TCP/UDP исполнителя теперь используют один вход transport evidence; перед обновлением selector проверяется допустимость пары протокол/метод и категории наблюдения. Нулевые закрытия, неподтверждённый контент и неподдерживаемые методы не передаются в обучение; поколение по-прежнему сверяется под lock selector. Существующее отдельное сохранение первого plain reply не является обучением и не менялось. ROOT потребует отдельного контекста исполнителя; новый код не подключает ROOT. Добавлены тесты отказа по протоколу и категории.

## A2/A3 — изоляция исполнителей и аудит границ

Добавлен immutable ExecutorSet: допустимые методы выбираются в явно указанном executor, отсутствующий исполнитель не заменяется другим; Admit проверяет executor/transport/method/network generation. Это нейтральный контракт будущей интеграции, пока не подключённый к ROOT runtime. Отдельная read-side классификация SocketDownstream не смешивает получение данных с закрытием. Тесты фиксируют отказ при несовпадении поколения/исполнителя и незарегистрированном методе. В инвентаризации уточнены native dependencies Zapret2 и отдельный provenance blocker checksum.c; никаких непроверенных upstream файлов не импортировано.

## A4.5 — отдельный Android debug APK

Добавлен opt-in Gradle property dppass.localDpiNativeDebug=true (требует Alpine). Только debug variant получает экспериментальный JNI с C-кодировщиком; release всегда использует штатный режим. Отдельный applicationId com.dpsmpx.dppass.alpine.localdpi не заменяет основной установленный APK или обычный Alpine debug. Gradle отслеживает tag и исходники C/Go, APK содержит полный MIT LICENSE и источник модуля. CI после загрузки обычных APK собирает отдельный debug artifact только в рабочей ветке, сверяет identity, лицензию, отличие JNI и неизменность reference assets. Это подготовка к физической проверке; не доказывает, что C encoder используется при внешнем Alpine planner, не включает ROOT и не удаляет ciadpi/nfqws2. Новый CI ожидается.

## A4.6 — явная диспетчеризация нативного TLS-метода

Только сборка localdpi_native+cgo использует встроенный кодировщик для уже существующего TCP tlsrec-split даже при выбранном Alpine planner. Это заранее определённая маршрутизация одного метода, не fallback после отказа IPC. Остальные методы и штатный APK сохраняют прежнюю логику fail-closed. ### Ёмкость разреженных весов серверной модели V4

Шесть контекстов делят до 4096 хранимых весов поровну с точностью до одной записи. При меньшем бюджете квота равна числу доступных индексов контекста. Когда квота заполнена, новый обучаемый индекс вытесняет давно не обновлявшийся вес того же контекста. Порядок вытеснения обновляется только при обучении. Модель сохраняет этот порядок по числовым индексам в `sparse_recency`. Если у профиля есть несколько записей в отчёте, для обучения берётся первая запись с подтверждённым результатом проверки.

Ранее созданные модели V4 читаются с прежними индексами и весами. При первом сохранении с разреженным обучением из контекста сверх квоты убираются веса с наименьшим модулем. При равном модуле первыми убираются меньшие индексы. Последующие сохранения используют порядок обновлений. Чтение файла с `sparse_recency` требует сборки с поддержкой этого поля. Для моделей V3 по-прежнему нужна генерация модели V4.

### Полевые измерения автовыбора сервера

Локальный журнал добавляет `server_auto_outcome` для каждого контекста в завершённом плане, принятом существующей проверкой. Исходы разбиты на подтверждённые успехи, измеренные отказы и записи без измерения. Повторы учитываются один раз на кандидата по первому допущенному исходу. `first_attempt` показывает исход первой записи отчёта и имеет значение `null` в остальных контекстах. `first_moved=true` означает, что модель сместила первого испробованного кандидата относительно исходного плана.

`model_scored=false` обозначает штатный план без пригодной модели, `observations_before=null` в таком случае. При наличии модели поле показывает число наблюдений в соответствующем контексте до попыток. События содержат агрегированные счётчики и фиксированные категории. Их можно искать в «Журнале» DPpass по имени события и экспортировать существующей кнопкой копирования.

Долю подтверждённых успехов среди измеренных первых попыток считают по `first_attempt=VERIFIED_SUCCESS` и `first_attempt=MEASURED_FAILURE`. Количество первых попыток без измерения (`first_attempt=NONE`) учитывают отдельно. Для оценки эффекта перестановок нужны сопоставимые серии в одной сети и с тем же набором кандидатов.

Утилита `tools/device/summarize_server_auto.py` строит таблицу по локальной копии журнала DPpass в UTF-8. Можно использовать один экспорт, содержащий обе серии, или взять штатные события из первого файла, а события V4 из указанного через `--scored-log`.

```sh
python3 tools/device/summarize_server_auto.py dppass-log.txt
python3 tools/device/summarize_server_auto.py planner-log.txt --scored-log v4-log.txt
```

При ротации или обрезке экспорта сводка использует сохранённый хвост текущего сеанса. Ограничения источника и обнаруженные потери строк указываются под таблицей. В таблицу попадают только агрегаты, включая долю подтверждённых успехов, разницу в процентных пунктах при наличии обеих выборок и отдельный итог по первым кандидатам, перемещённым V4. Код выхода `0` означает, что сводка построена, `1` — что в выбранном фрагменте нет событий, `2` — что вход не удалось прочитать или проверить. Сводка описывает зафиксированные попытки и служит основой для сравнения сопоставимых серий.

### Режимы для сравнения на устройстве

В разделе «Локальная модель выбора сервера» строка «Режим автовыбора сервера» задаёт поведение очередного автоматического подключения по подписке. Режим сохраняется в настройках приложения.

- **V4 с обучением** — режим по умолчанию. Модель оценивает подходящих кандидатов и обновляет сохранённые веса по подтверждённым исходам.
- **Штатный план** — выполняется порядок планировщика. Уже сохранённая модель доступна для следующего сравнения.
- **V4 с фиксированными весами** — модель оценивает кандидатов из сохранённого снимка. Каждая попытка сохраняет этот снимок в исходном виде.

Режим фиксируется при подготовке плана подключения. Штатные ограничения по сети, ручному выбору и порядку допустимых кандидатов действуют в обеих сериях. При отсутствии пригодной V4 используется штатный план. Событие `server_auto_model` указывает выбранный режим, а `server_auto_outcome` показывает, использовалась ли оценка фактически. Для сравнения сохраните журналы двух серий «Штатный план» и «V4 с фиксированными весами» с теми же кандидатами в той же сети. Само состояние планировщика, включая сведения о свежем здоровье серверов, продолжает обновляться.

## A8 — independent installed APK verification via ADB

After installing a candidate using the app updater or the Android package installer, a host can verify the actual installed base APK without replacing the package or accessing its private data. Download NATIVE_CANDIDATE.txt and UPDATE_VERSION.txt from the trusted signed prerelease. With adb, apksigner and aapt on PATH (or explicit executable paths), run:

```sh
python3 tools/device/verify_installed_candidate.py NATIVE_CANDIDATE.txt UPDATE_VERSION.txt
```

Use --serial only if selecting a particular connected device. The tool checks a single base APK, a bounded file size, unchanged package path during collection, the exact candidate APK and ARM64 JNI SHA-256, the pinned release certificate, and the actual package/version reported by aapt. It uses a temporary directory and does not print device identifiers, installed paths or external command output. It never installs, uninstalls, clears data, invokes root, or reads subscriptions. Exit 0 confirms installed candidate identity only; exit 1 is mismatch, exit 2 is a tool/input/connection error. This can complement the DPTS report verifier. It cannot establish whether installation was initiated by the in-app updater or whether user data survived; those remain explicit device acceptance checks. Fake-command and archive fixtures run in CI; physical testing remains pending.

## A3/A6 — one terminal socket observation per flow

TCP and UDP now share a serialized evidence gate. The first coherent terminal observation (explicit first-reply timeout or downstream evidence) consumes the flow's learning allowance; later reads and close cannot train again or reinstate a plain preference from the same timed-out flow. Neutral close seals the gate without training. UDP serializes reads and disqualifies both positive and negative learning after ambiguous pre-Initial traffic, while continuing to deliver and count subsequent bytes. Generation, cache-incarnation, executor and selected-plan checks still apply. No packet strategy, model format or provider VPN changes. Unit tests cover concurrent claims, invalid/neutral observations and both socket transports with a real local timeout followed by late data; targeted bridge race checks are included in CI. Physical effectiveness remains unverified.
