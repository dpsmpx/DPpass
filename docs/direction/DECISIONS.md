# Решения DPpass

Журнал архитектурных решений. Код и документы ссылаются на них по номеру
(`D-05`); `tools/hostcheck/check_docs.py` проверяет, что каждый номер,
упомянутый в репозитории, здесь определён.

Правила журнала:

- Номер не переиспользуется и не меняется. Новое решение — следующий
  свободный номер (сейчас — **67**).
- Решение не переписывается задним числом: если оно меняется, старое
  получает статус «заменено D-NN», новое объясняет, что изменилось и
  почему.
- У каждого решения есть **проверка** — тест или шаг hostcheck, который
  ловит отступление от него. Решение без проверки — пожелание.
- Довод «так сделано у X» не принимается (`CLAUDE.md`, «Оригинальность»);
  довод — свойство, нужное пользователю, или факт из исследования
  (`docs/research/`).

Все решения ниже приняты **4 октября 2026**: D-01…D-23 — на этапе 1,
D-24…D-30 — на этапе 2 (`docs/direction/ROADMAP/README.md`).

## Принятые

### D-01 — Название и облик — свои

**Решение.** DPpass — рабочее название. Облик (название, значки,
формулировки, схема ссылок) создаётся с нуля и не воспроизводит чужие
продукты, в первую очередь Happ (`docs/research/HAPP_SOURCE_AUDIT.md`, §4).
Окончательное название и `applicationId` фиксируются перед первым
выпуском: после выпуска `applicationId` не сменить.

**Следствия.** Значок — векторная заглушка собственного рисунка; схема
`happ://` не поддерживается как своя.

**Проверка.** Обзор при выпуске (этап 5); ресурсы приложения — только
XML без чужих изображений (`docs/PROVENANCE.md`, двоичные файлы).

### D-02 — Android прежде всего; ядро — чистый Kotlin/JVM

**Решение.** Первая платформа — Android. Вся логика (разбор,
проверка, маршрутизация, подписки, активация, политика подключения)
живёт в модулях на чистом Kotlin/JVM без Android SDK. Android-модуль
`app/` — тонкая оболочка над `DPpassCore`: сборка зависимостей,
`VpnService`, Keystore, интерфейс.

**Следствия.** Ядро собирается и тестируется на любом JDK 21 без
эмулятора; `cli` — вторая оболочка над тем же ядром.

**Проверка.** `tools/hostcheck/check_modules.py` (`android.*` только в
`app/`); `tools/hostcheck/check_android_api.py` (API ядра ≤ minSdk).

### D-03 — Первое реальное ядро — Xray-core; до него — фиктивное

**Решение.** Вариант A из `docs/research/BACKEND_STRATEGY.md`: одно
реальное ядро — Xray-core (MPL-2.0), подключаемое на этапе 2. До этого
работает фиктивное ядро `MockProxyEngine` с двумя наборами
возможностей; туннель с фиктивным ядром не поднимается (иначе он
отрезал бы устройство от сети).

**Следствия.** `AppGraph` — единственное место приложения, где
появляется `engine.mock`; сервис туннеля честно останавливается с
`BACKEND_NOT_AVAILABLE`.

**Проверка.** `check_modules.py` (разрешённые места `engine.mock`).

### D-04 — Граница ядра: ProxyEngine, BackendCompiler, матрица возможностей

**Решение.** Домен не знает, какое ядро работает. Граница — интерфейсы
`ProxyEngine` (проверка и запуск), `BackendCompiler` (IR → конфигурация
ядра) и `EngineCapabilities` (матрица: протоколы, транспорты, защиты,
flow, возможности) одной версии ядра. Абстракцию доказывает второй
бэкенд — фиктивный, с другой матрицей (`mock-limited`). Второе
реальное ядро — отдельным решением (см. «Отложено»).

**Проверка.** `CapabilityCheckerTest`, `MockBackendTest`, корпус `tests/data/configs/limited-backend-*`
и `tests/data/dns/dot-on-limited-backend` — отказ неподдержанного с путём.

### D-05 — Собственный IR; смысл не меняется молча

**Решение.** Конфигурация описывается собственной моделью (Config IR),
не полями Xray или sing-box. Конвейер «документ → IR»: размер → строгий
JSON → маркер → миграции → IR → нормализация → проверка смысла.
Всё, что нельзя выразить без потери смысла, — ошибка с путём
(`$.profiles[0].transport`), а не «ближайшее похожее». Приблизительная
замена допустима только как явная находка `SEMANTIC_FALLBACK`.

**Следствия.** Строгий JSON свой (повторный ключ — ошибка, глубина
ограничена до разбора, сообщение без цитаты входа); ссылки с
неизвестными параметрами непригодны; IDN — только punycode.

**Проверка.** `ConfigLoaderTest`, `JsonTest`, корпус `tests/data/configs/`, fuzz.

### D-06 — Собственный формат документа: версия и явные миграции

**Решение.** У документа DPpass свой маркер (`dppass.config`) и своя
версия формата, не связанная с версиями ядер, геоданных и приложения
(`docs/CONFIG_FORMAT.md`). Неизвестное поле — ошибка. Версия новее
текущей — ошибка «создано более новой версией». Миграции — только
явные, между соседними версиями, над деревом JSON, каждая с тестом.
Отвергнутый документ не заменяется конфигурацией по умолчанию: то, что
DPpass хранил сам и не смог прочитать, уходит в карантин как есть, с
причиной.

**Следствия.** До первого выпуска для посторонних производственных
миграций нет: черновые версии формата отвергаются, механизм проверен
синтетической цепочкой.

**Проверка.** `MigrationTest` (цепочка миграций, отказы), `StorageTest`
(карантин), корпус `invalid-newer-version`, `invalid-unknown-field`.

### D-07 — Активация — транзакция; last-known-good

**Решение.** Любая смена конфигурации проходит шаги: возможности ядра →
компиляция → проверка ядром → (проверка здоровья) → фиксация одной
атомарной записью. Новая конфигурация становится активной только при
полном успехе; при отказе на любом шаге действующая остаётся, отказ
записывается в историю с шагом и причиной. Предыдущая активная — цель
отката, если новая в работе не передаёт данных.

**Проверка.** `ActivationServiceTest` (отказ не трогает действующую,
откат, восстановление после перезапуска), `RollbackTest`.

### D-08 — Подписка — версионированный объект

**Решение.** Подписка неизменяема: обновление создаёт новый объект
целиком (новая ревизия), хранилище заменяет его атомарно. Конвейер:
загрузка → целостность (размер, пустота, контрольная сумма) → разбор →
проверка записей → фильтр по возможностям ядра → кандидат на
активацию. Подписка получает новую удачную ревизию только после
успешной активации; неудача записывается рядом, не затирая удачную.

**Проверка.** `SubscriptionUpdaterTest`, `SubscriptionActivationTest`, корпус
`tests/data/subscriptions/`.

### D-09 — Семантическая модель маршрутизации

**Решение.** Маршрутизация — три действия (`direct`, `proxy`, `block`)
и восемь видов условий (домены, подсети, geosite, geoip, приложения,
протокол, порт, вид сети); поля условия соединяются через И, значения
внутри поля — через ИЛИ; первое сработавшее правило решает. Смысл
задаёт эталонный вычислитель `RouteEvaluator`; компиляторы ядер обязаны
его сохранить или отказать. Ведущие правила «приложения → direct»
переносятся на уровень `VpnService` (исключение из туннеля), остальные
правила с приложениями требуют возможности ядра.

**Проверка.** `RouteEvaluatorTest`, `RoutingValidatorTest`, `AppLoweringTest`,
корпус `tests/data/routing/`, `TunnelSpecBuilderTest`.

### D-10 — DNS — отдельная подсистема

**Решение.** DNS описывается отдельно от маршрутизации: серверы
(UDP, TCP, DoH, DoT, системный), маршрут запроса (через туннель или
напрямую), правила «какие имена — какому серверу», стратегия адресов,
защита от утечек. Кеш и резолвер — дело ядра; DPpass задаёт смысл и
проверяет, что ядро его выполнит.

**Проверка.** `DnsValidatorTest`, корпус `tests/data/dns/`.

### D-11 — Пользователь видит и контролирует свою конфигурацию; секреты защищены по умолчанию

**Решение.**
- Секреты (UUID, пароли, short_id, адрес подписки) — тип `Secret`:
  `toString()` не показывает значение, `reveal()` разрешён в немногих
  местах. Каждая строка журнала и отчёта проходит `Redactor`.
- Экспорт по умолчанию — с отредактированными секретами; такой документ
  нельзя активировать.
- Отключение проверки сертификата (`allow_insecure`, `allowInsecure=1`)
  не принимается.
- Подписка не управляет клиентом: применяются только информационные
  метаданные; директивы поставщика (смена адреса подписки, скрытие
  настроек, DNS, маршрутизация, списки приложений…) отмечаются и не
  применяются. Маршрутизация и DNS поставщика — только если пользователь
  явно привязал к ним подписку.
- Зашифрованные «чтобы пользователь не видел» ссылки не поддерживаются.

**Проверка.** `RedactorTest`, `LoggerTest`, `SecretLeakTest.noSecretsInLogsReportsDiagnosticsOrDisk`,
`ExportTest` (экспорт в приложении, этап 4),
`MetadataParserTest`, `ShareLinkParserTest`, `code.forbidden` — правило `secret-reveal`
(`reveal()`; до D-50 — `check_forbidden_apis.py`).

### D-12 — Без телеметрии и идентификаторов устройства

**Решение.** DPpass ничего не отправляет о пользователе и устройстве:
нет аналитики, отчётов о падениях, push-токенов, HWID. В запрос
подписки идентификатор устройства не добавляется даже по просьбе
поставщика. Диагностический отчёт собирается на устройстве и уходит
наружу только действием пользователя. То же для сборки: инструменты не
отправляют данных (`org.gradle.welcome=never`, без сканов сборки).

**Проверка.** `check_dependencies.py` (зависимости только из матрицы —
SDK аналитики туда не попадает), `check_manifest.py` (утверждённые
разрешения).

**Уточнение (17 октября 2026, сборка).** Инструменты проверены на деле.
- **Сеть.** Полная пересборка под `strace` соединялась только с 127.0.0.1
  (`docs/PROCESS.md`, «Перед слиянием»).
- **Плагин Kotlin.** Сам он ничего не отправляет, но писал статистику
  сборки (FUS) в `~/.gradle/kotlin-profile`: 1363 файла за две недели, в
  каждом — путь проекта и версия ОС. Их забирает статистика IDE, если её
  включили. Запись выключена: `kotlin.internal.collectFUSMetrics=false`
  в `gradle.properties` и `build-logic/gradle.properties`. Профили ещё
  пишут служебные сборки accessors `build-logic` — только когда те
  перегенерируются; свойства проекта до них не доходят. Свойство
  внутреннее: при настройке сборки плагин предупреждает «Usage of
  Internal Kotlin Gradle Plugin Properties», и это ожидаемо. Другой
  выключатель — пустое `kotlin.session.logger.root.path` — молчит, но
  в плагине помечен «только для тестов», и 17 октября при проверке он
  записал профили в каталог проекта (`dppass/kotlin-profile/`).
  Поэтому он отвергнут: внутреннее свойство хотя бы прямо названо, а
  его действие видно.
- **AGP.** Статистику отправляет только при согласии, данном в Android
  Studio (`analytics.settings`, `hasOptedIn`); выключателя в проекте нет.
  Согласие на машине сборки — ошибка проверки.

Всё это держит `check_build_telemetry.py` (`project.telemetry`).

**Состояние.** В части «идентификатора в запросе подписки» заменено
D-33: случайный идентификатор подписки — только с согласия
пользователя; остальное действует.

### D-13 — Честные пределы

**Решение.** DPpass не обещает того, чего клиент не может: «работает
гарантированно», «незаметен», «обходит белый список». Клиент не создаёт
путь, которого нет в сети: при режиме, похожем на белый список, он
использует только кандидатов, отмеченных как доступные из такой сети
(`allowlist_reachable`), а без них прямо говорит, что нужна точка входа,
доступная из этой сети. Отметку DPpass не проверяет заранее и не
обещает.

**Проверка.** `CandidatePlannerTest.allowlistWithoutReachableCandidateExplainsLimit`,
корпус `tests/data/network/conditions.json` (`ALLOWLIST_LIKE`).

### D-14 — Сеть определяется по наблюдениям, с бюджетом проб

**Решение.** Модуль `network/` отвечает на вопрос «что сейчас
пропускает эта сеть» по пробам (DNS, TCP, TLS, UDP, страница входа,
крупная передача) к отечественному и зарубежному ориентирам. Пробы идут
по одной, с паузой к одному ориентиру и пределом за окно: залпы
рукопожатий сами вызывают ограничения (L7,
`docs/research/RUSSIA_NETWORK_RESTRICTIONS.md`). Результат — эвристика
с уверенностью и доказательствами, не знание о политике оператора; имя
оператора и регион не используются.

**Проверка.** `ProbeBudgetTest` (без залпов), `NetworkClassifierTest` (таблица
классификации), корпус
условий сети.

### D-15 — Политика подключения: упорядоченный, ограниченный, объяснимый план

**Решение.** План кандидатов детерминирован (одинаковые вход и время →
одинаковый план) и ограничен (`maxAttempts`). Порядок: последний
удачный → здоровье → штраф класса транспорта по наблюдениям сети →
приоритет → id; соседние попытки — по возможности разных классов
(TCP-поток, HTTP/CDN, UDP/QUIC). Каждая попытка и каждое исключение —
с причиной. Отказ ставит кандидата на экспоненциальную паузу; между
попытками — пауза без залпов. Здоровье — по полезной нагрузке, а не по
рукопожатию.

**Проверка.** `CandidatePlannerTest`, `OrchestratorTest`, корпус условий сети.

### D-16 — Первый набор протоколов (IR v1)

**Решение.** То, что одно зрелое ядро (Xray) покрывает в трёх классах
транспорта (`docs/research/TRANSPORT_COMPARISON.md`, §5):
- TCP/TLS: VLESS + REALITY/TLS (+ Vision), Trojan + TLS,
  Shadowsocks-2022 (только методы `2022-blake3-*`);
- HTTP/CDN: VLESS/Trojan + XHTTP, WebSocket, gRPC, HTTPUpgrade;
- UDP/QUIC: Hysteria2.

Старые AEAD Shadowsocks (без защиты от повтора), VMess и прочее — не в
IR v1 (см. «Отложено»).

**Проверка.** `ConfigValidator` и корпус (`invalid-ss-key-length`,
`invalid-vision-ws`); `CapabilityChecker`.

### D-17 — Android: VpnService, minSdk 26, targetSdk 36; спецификация TUN вне Android

**Решение.** Туннель — `VpnService`. compileSdk/targetSdk 36 (требование
Google Play с 31.08.2026), minSdk 26 (пересматривается перед выпуском).
Что должен сделать `VpnService.Builder` (адреса, маршруты, исключения,
DNS, MTU, политика приложений, IPv6), решает `tunnel/` в виде
`TunnelSpec`; Android-слой переводит его в вызовы Builder один к одному.
Собственный пакет DPpass всегда вне туннеля; IPv6 всегда маршрутизуется
в туннель (иначе утечка). Foreground-сервис — тип `specialUse`.

**Проверка.** `TunnelSpecBuilderTest`, `check_manifest.py`, `check_android_api.py`,
Android Lint (`warningsAsErrors`).

### D-18 — Обновления — по чек-листу, версии закреплены

**Решение.** Версии всех зависимостей и ядра закреплены в одном месте
(`gradle/libs.versions.toml`; ядро — с этапа 2). Обновление делается
не «потому что вышло», а по чек-листу (`docs/PROCESS.md`, «Зависимости»):
причина, журнал изменений, лицензия, разница матриц возможностей ядра
(`capabilityDiff`), полный прогон корпуса и hostcheck, запись в
матрице лицензий и PROVENANCE.

**Проверка.** `tools/provenance/check_dependencies.py`; содержимое
артефактов Gradle — суммы SHA-256 в `gradle/verification-metadata.xml`
(с 6 октября 2026, аудит A-7).

### D-19 — Хранение: атомарно, зашифровано, без резервных копий

**Решение.** Состояние — записи «ключ → байты»: запись атомарна
(временный файл, fsync, атомарное переименование). На устройстве всё
шифруется AES-256-GCM со случайным nonce и ключом записи как
дополнительными данными (запись нельзя переложить под другой ключ);
ключ данных хранится обёрнутым ключом Android Keystore. Данные — в
`noBackupFilesDir`; резервные копии и перенос на другое устройство
выключены.

**Проверка.** `StorageTest`, `check_manifest.py`; на устройстве — этап 3
(`TODO.md`, «На устройстве»).

### D-20 — Лицензии и происхождение

**Решение.** DPpass пишет свой код. Чужой код, тексты и данные не
копируются, даже если лицензия позволяет (если когда-нибудь это
понадобится — отдельным решением с записью в PROVENANCE). Компоненты —
только из `docs/legal/THIRD_PARTY_MATRIX.md` со статусом «разрешён».
Копилефт в одном процессе с приложением (GPL: sing-box/libbox, v2rayNG,
NekoBox, Hiddify) не используется: это решение о модели распространения
DPpass (Apache-2.0), а не инженерное. Происхождение неизвестного кода —
запрет (`docs/PROVENANCE.md`).

**Проверка.** `check_dependencies.py`, `check_secrets.py` (нет чужих
ключей и серверов), обзор PR.

### D-21 — Проверяемость на хосте; детерминизм

**Решение.** Всё, что можно проверить без устройства, проверяется на
хосте и в CI: ядро — на JVM, весь конвейер — через `cli` и
межмодульные тесты на модели сети. Время — только через `Clock`
(в тестах `ManualClock`, без сна), случайность — только с явным зерном
(fuzz) или криптографическая; одинаковый вход даёт одинаковый результат.

**Проверка.** `check_forbidden_apis.py` (`wall-clock`, `weak-random`,
`blocking`), hostcheck, CI.

**Состояние.** В части CI заменено D-23: CI нет, «на хосте и в CI»
читается как «на хосте»; остальное действует.

### D-22 — Диагностика: стабильные коды, сохранённые причины

**Решение.** Ожидаемые отказы — значения (`Outcome`), а не исключения.
Каждая находка — стабильный код `DiagCode` (категория `FailureKind`),
серьёзность, сообщение без секретов, путь и **цепочка причин**:
«не активировано» несёт «ядро отвергло», а то — исходную ошибку ядра.
Коды — публичный контракт: не переименовываются и не удаляются, только

Принято 4 октября 2026, в начале этапа 2.

### D-25 — Ядро в процессе приложения: своя обёртка Go с JNI, одно ядро на процесс

Принято 4 октября 2026, этап 2 (работа 4). Факты о Xray 26.9.30, на
которые оно опирается, — `docs/research/BACKEND_STRATEGY.md`, §6.

**Решение.**
- Xray встраивается в процесс приложения библиотекой
  `libdppassxray.so` из собственного кода Go — `tools/xray/bridge`
  (жизненный цикл ядра) и `tools/xray/jni` (экспорт JNI через cgo) — и
  того же `tools/xray/go.mod`, по которому шаг «Xray» проверяет
  компилятор: ядро в APK и ядро в проверке — один набор модулей одной
  версии (D-24). Ни libXray, ни gomobile:
  - libXray (MIT) несёт то, что DPpass делает сам или не должен
    поручать ядру (разбор ссылок, пинг со своими соединениями, правка
    геоданных), и выпускается не в такт с ядром;
  - gomobile кладёт в APK свою среду Java (`go.Seq`) и генерируемые
    классы, без которых `app` не компилируется, а в JVM хоста эти
    привязки не загрузить — мост оставался бы непроверенным до
    устройства.
  С JNI объявления `external` в `engine` компилируются без библиотеки,
  а тот же код моста, собранный для Linux, загружается в JVM хоста и
  проверяется тестом JNI на хосте (`XrayJniTest`).
- Граница: `XrayRuntime` (`engine.xray`) — версия, проверка, запуск,
  остановка, счётчики; `XrayProxyEngine` — `ProxyEngine` поверх неё.
  Отказ моста — вид (конфигурация, запуск, уже запущено, нарушение
  договора) и текст ядра; текст проходит `Redactor` и становится
  причиной диагностики (D-22), а не её сообщением. Библиотека другой
  версии, чем `XrayBackend.VERSION`, не используется
  (`BACKEND_NOT_AVAILABLE`): компилятор пишет конфигурацию для одной
  версии (D-18).
- **Одно ядро на процесс.** У Xray глобальны хуки сокетов, fd TUN
  (переменная окружения `xray.tun.fd`) и системный dialer, который
  `core.New` переназначает на новый экземпляр. Поэтому второй запуск без
  остановки — `BACKEND_ALREADY_RUNNING`, а проверка при работающем ядре
  — только сборка конфигурации и политика входов, без `core.New`: иначе
  работающее ядро на время проверки резолвило бы имена прямых
  соединений DNS-клиентом проверяемой конфигурации. Полная проверка
  тогда — при запуске; неполная отмечается находкой
  `BACKEND_VALIDATION_PARTIAL`, а не молчанием.
- **`protect()`.** Мост ставит хук на каждый исходящий сокет ядра
  (`internet.RegisterDialerController`) и вызывает защитника из
  `TunInput` (на Android — `VpnService.protect`). Ошибку хука Xray
  только журналирует, поэтому отказ закрывает путь сам мост: сокет,
  который не удалось защитить, подменяется (`dup3`) сокетом, на котором
  `connect` и `bind` к адресу IP невозможны, — соединение не
  устанавливается, а не уходит петлёй в туннель (T4). TUN без
  защитника — отказ запуска.
- **Входов, кроме TUN, нет (T11).** Политика моста проверяется на
  собранной конфигурации (protobuf, которую получает `core.New`), а не
  на JSON (в Go имена полей JSON сопоставляются без учёта регистра):
  службы — только журнал, DNS, маршрутизация, политики, счётчики и
  служебные диспетчер и менеджеры входов/выходов; вход — не больше
  одного, TUN. Вход TUN есть тогда и только тогда, когда передан fd, и
  его MTU равен `TunInput.mtu`. Тестовый вход на loopback
  (`dokodemo-door`) политика допускает только в сборке моста для тестов
  на хосте (тег Go `dppass_testinbound`); код обработчика в библиотеке
  для APK есть (его тянет разбор JSON Xray), но политика его отвергает.
- **fd TUN принадлежит платформе** (`TunnelHandle`): ядро его не
  закрывает; порядок — остановить ядро, затем закрыть TUN. Какой мост
  fd → ядро лучше (вход TUN Xray или hev-socks5-tunnel) — по-прежнему
  эксперимент (работа 5, «Отложено»); сейчас — вход TUN Xray,
  единственный в 26.9.30 путь без локального входа.
- **Сборка** (`tools/xray/native.py`): `go build -buildmode=c-shared
  -trimpath` с той же сверкой модулей, что у шага «Xray» (T10); для
  Android — NDK версии из `gradle/libs.versions.toml` (`android-ndk`),
  ABI `arm64-v8a`, `armeabi-v7a`, `x86_64`, сегменты ELF выровнены по
  16 КБ; для Android компоновщику нужен `-checklinkname=0` (модуль
  `wlynxg/anet` ссылается на внутреннее `net` через `go:linkname`,
  `docs/PROVENANCE.md`). Библиотеки не коммитятся: `:app` собирает их задачей
  `xrayNative` вместе с APK. Без Go или NDK APK не собирается: без ядра
  он бесполезен, а собранный молча без ядра скрыл бы это.
- **Счётчики** — трафик исходящего `proxy` (компилятор включает `stats`
  и `policy.system.statsOutbound*`): `TrafficStats` — трафик через
  сервер, а не всего устройства.

**Следствия.** Приложение работает на `XrayProxyEngine`;
`MockProxyEngine` остаётся вторым бэкендом в тестах, а в `app/` больше
не допускается (`check_modules.py`, критерий выхода этапа 2). libXray —
«отклонён» в матрице лицензий. Сервис туннеля ещё не поднимает TUN —
работа 6; в отдельный процесс ядро пока не выносится (там же).

**Проверка.** `go test` моста (шаг hostcheck «Xray: мост и JNI»):
политика входов, отказ `protect` закрывает соединение, один экземпляр,
неполная проверка при работе; тест JNI на хосте (`XrayJniTest`) — тот же мост через JNI в
JVM хоста: версия, проверка, запуск и остановка, вызов `protect` и
отказ при его неудаче, счётчики; `XrayProxyEngineTest`; `check_apk.py`
(в APK — `libdppassxray.so` трёх ABI, выровненная по 16 КБ, и ничего
больше из нативного кода); `check_modules.py` (`engine.mock` вне тестов).

**Состояние.** Частично заменено D-51 — в части «входов, кроме TUN, нет;
вход — не больше одного, TUN»: мост пропускает и входы раздачи — SOCKS с
тегом компилятора, логином и паролем, на частном IPv4 и с портом от
1024; остальное — по-прежнему отказ (T11). Остальное действует.

### D-26 — Журнал на устройстве: фоновая запись в файл, копия в буфер обмена по завершении работы

Принято 4 октября 2026, этап 2, по просьбе автора: журнал устроен так
же, как в его игре Galdhold (фоновая запись, наружу — через буфер
обмена при уходе из приложения). Код DPpass свой.

**Решение.**
- Каждое событие `Logger` (уже отредактированное, D-11) идёт и в кольцо
  памяти для локального отчёта, и в файл: `FileLogSink` пишет строки
  **в фоне** — отдельный поток, очередь с пределом; переполнение не
  блокирует вызывающего, а оставляет в файле строку о пропущенном.
  Файл — в `noBackupFilesDir/log` (T7: не уходит в резервную копию).
- Объём ограничен: сеанс (запуск процесса) — части по 1 МиБ, на диске
  только две последние и начало сеанса (первые 32 КиБ); прошлый сеанс
  при старте переезжает в `previous`, позапрошлый удаляется.
- Наружу журнал уходит **только через буфер обмена**, ничего не
  отправляется (D-12). Текст для буфера — начало и хвост в пределах
  ~120 тыс. символов с отметкой о пропущенной середине, ещё раз через
  `Redactor` уровня `STRICT` (как локальный отчёт: без IP и имён хостов)
  и с пометкой «чувствительное» (Android 13+: система не показывает
  предпросмотр). Копия делается при уходе из оболочки (`onStop`), при
  остановке сервиса туннеля и кнопкой «Копировать журнал».
- Журнал выключается переключателем в оболочке. По умолчанию — **включён
  в отладочной сборке** и выключен в релизной (вопрос о релизе — к
  этапу 5). Выключенный журнал не пишет файл и не копируется сам; кнопка
  копирует то, что есть.
- **Падение записывается всегда**, мимо выключателя: тип исключения,
  отредактированное сообщение и кадры стека (класс, метод, строка) —
  синхронно в `crash.log`, затем управление прежнему обработчику.
  Выключить журнал — значит отказаться от рутинных строк, а не от
  единственного способа узнать причину падения. Запись о падении
  входит в следующую копию журнала и удаляется после неё.
- Время строк — `Clock` (D-21), в UTC ISO-8601. В журнал не пишутся
  идентификаторы устройства (D-12): версия приложения, уровень API и
  ABI — да; модель, серийный номер, ANDROID_ID — нет.

**Следствия.** `Core.report` берёт кольцо через `LogHistory`, а не
через `MemoryLogSink` напрямую. В оболочке — кнопки журнала. Порог
объёма и поведение на устройстве (буфер обмена из фона, Android 10+) —
проверки «На устройстве» (`TODO.md`).

**Проверка.** `FileLogSinkTest` (фон, порядок строк, предел очереди,
части и начало сеанса, прошлый сеанс), `LogExportTest` (начало и хвост,
предел, `STRICT`, запись о падении), `CrashRecordTest` (сообщение
редактируется, кадры есть); `check_forbidden_apis.py` (время — только
`Clock`, без `android.util.Log`).

### D-27 — Геоданные: свой набор из открытых источников в APK, обновление — с приложением

Принято 4 октября 2026, этап 2. Это отдельное решение о чужих данных,
которого требует D-20; факты о лицензиях проверены в тот же день
(`docs/legal/THIRD_PARTY_MATRIX.md`, §2 и §4).

**Решение.**
- **Источники.**
  - `geosite` — `v2fly/domain-list-community` (MIT): списки доменов с
    атрибутами, в том числе `category-ru` и `category-gov-ru`;
    закреплённый коммит.
  - `geoip` — DB-IP «IP to Country Lite» (CC BY 4.0): страны, выпуск раз
    в месяц; закреплённый месяц. Условие лицензии — атрибуция «IP
    Geolocation by DB-IP» со ссылкой на https://db-ip.com: в файле
    рядом с данными и на экране лицензий (этап 5).
  - `geoip:private` — своя таблица специальных диапазонов адресов
    (реестры IANA, RFC 6890), а не страна из чужой базы.
  - GeoLite2 (MaxMind) — **запрещён**: лицензия разрешает передавать
    данные третьим лицам только с согласия MaxMind (§6.1) и требует
    уничтожать устаревшие версии (§6.3) — с данными в APK у
    пользователей это несовместимо.
  - Готовые `geoip.dat`/`geosite.dat` других проектов не берутся: набор
    собирается своим кодом из первичных источников, и состав и
    лицензия каждого его байта известны (D-20, T10).
- **Сборка.** Свой инструмент на Go из того же `tools/xray/go.mod`
  пишет файлы в формате закреплённой версии Xray (`common/geodata`) —
  как синтетический набор шага «Xray» (`dppass-xray-probe geodata`).
  Источники закреплены в каталоге версий, их SHA-256 — в PROVENANCE
  (D-18). Сборка детерминирована: из тех же источников получаются те же
  байты.
- **Состав и доставка.** В набор входят все списки dlc и все страны
  DB-IP. Набор лежит в APK сжатым ресурсом. При первом запуске новой
  версии приложения он переносится в `noBackupFilesDir/geodata`
  атомарно и со сверкой SHA-256 (D-19). Замер 4 октября 2026 (DB-IP
  2026-10): 1 382 972 подсети; `geoip` занимает около 20 МиБ на диске и
  около 4,3 МиБ в сжатом виде. `geosite` замеряется при сборке набора.
- **Обновление — только вместе с приложением.** Клиент не скачивает
  геоданные:
  - это новая связь со сторонним сервером (D-12);
  - это звено цепочки поставки вне сверки сборки (T10);
  - подписка и сервер не меняют правила маршрутизации без пользователя
    (D-11).
  Обновление источников идёт по чек-листу D-18; DB-IP выходит раз в
  месяц. Отчёт (`Core.report`) показывает, из чего собран набор: коммит
  dlc и месяц DB-IP.
- **Кода нет в наборе — отказ с путём.** Такое условие не превращается
  в условие, которое молча никогда не выполняется (D-05). Ядро
  отвергает такую конфигурацию при проверке. Компилятор сверяет коды с
  оглавлением набора и называет путь правила; для этого при реализации
  добавляется новый код диагностики.
- **Объяснение решений на устройстве** (`RouteEvaluator`, D-09) берёт
  `GeoResolver` из тех же файлов, поэтому объяснение не расходится с
  ядром.

**Следствия.** До реализации (`TODO.md`) каталог геоданных пуст, и
конфигурации с `geoip`/`geosite` на устройстве отвергаются — явно, а не
молча. Свой набор от пользователя и обновление без выпуска приложения —
в «Отложено». Предел размера APK (D-28) пересматривается вместе с
замером набора. В матрице лицензий dlc и DB-IP — «запланирован»,
GeoLite2 — «запрещён».

**Проверка.**
- `go test` моста, `TestGeodataUnknownCodeIsRejected`: кода нет в
  наборе — отказ `CONFIG`, есть — конфигурация принята.
- `XrayJniTest.geodataWithoutAssetsIsRejected`: без набора — отказ.
- Шаг «Xray»: маршрутизация ядра на синтетическом наборе совпадает с
  `RouteEvaluator`.
- `check_apk.py`: набор в APK сжат, совпадает со своим оглавлением и с
  набором шага «Xray: геоданные» по SHA-256; `check_dependencies.py`:
  источники есть в каталоге, матрице и PROVENANCE (D-31).
- `XrayCompilerTest.geoCodesAreCheckedAgainstTheInstalledSet`: кода,
  атрибута или сочетания атрибутов нет в наборе — отказ
  `GEO_CODE_UNKNOWN` с путём правила, набора нет — `GEODATA_UNAVAILABLE`.
- `go test` сборщика, `TestManifestAttrSetsAreWhatXrayMatches`:

### D-28 — Выпуск: отдельный APK на каждый ABI, универсального нет

Принято 4 октября 2026, этап 2. Действует с релизной сборкой (этап 5).

**Решение.**
- Большая часть размера — ядро (D-25). Замер 4 октября 2026:
  - `libdppassxray.so` — 33,1–36,6 МиБ на ABI; она хранится несжатой,
    потому что загружается прямо из APK;
  - APK с тремя ABI — 105,7 МиБ, с одним — 34,9–38,3 МиБ.
  Пользователю незачем скачивать и хранить ядра чужих ABI.
- В релиз идёт отдельный APK на каждый ABI из D-25 (`arm64-v8a`,
  `armeabi-v7a`, `x86_64`), с ABI в имени файла; универсального APK нет.
  AAB собирается, только если его потребует канал распространения.
  Каналы — в «Отложено» (этап 5), и формат пакета их не предрешает.
  Схема `versionCode` по ABI выбирается вместе с каналом.
- Отладочная сборка остаётся одним APK с тремя ABI: её ставят на
  эмулятор и разные устройства разработки, а `check_apk.py` проверяет
  по ней все три библиотеки сразу.
- Бюджет считается для APK одного ABI: предел — 40 МиБ (замер плюс
  запас, `docs/PERFORMANCE_BUDGET.md`, §4). Новое значение
  устанавливается только с замером; геоданные (D-27) его поднимут.
  Поднят 5 октября 2026 до 46 МиБ: набор геоданных добавил 5,9 МиБ,
  APK одного ABI — 40,8…44,2 МиБ (§4 бюджета).

**Следствия.** Разделение (`splits.abi` в `app/build.gradle.kts`)
включается вместе с подписью и R8 релизной сборки (этап 5,
`docs/direction/ROADMAP/05-release.md`). Тогда `check_apk.py` будет
проверять каждый APK отдельно. До этапа 5 релизные сборки не
публикуются (`CLAUDE.md`).

**Проверка.** `check_apk.py`:
- APK одного ABI (отладочный APK без библиотек других ABI) не
  превышает предел;
- в APK есть библиотека ядра для каждого из трёх ABI (D-25).

### D-29 — Имя сервера профиля резолвит система вне туннеля

Принято 4 октября 2026, этап 2. Факты взяты из исходников Xray 26.9.30
(`transport/internet/dialer.go`, `DialSystem`) и Go 1.27.1
(`net/conf.go`).

**Решение.**
- Если `server` профиля — имя, его резолвит системный резолвер
  устройства, вне туннеля. Цепочка такая:
  - у исходящего `proxy` нет ни `sockopt.domainStrategy`, ни
    `dialerProxy`, поэтому Xray передаёт имя системному dialer;
  - Go на Android резолвит имя через системную библиотеку (cgo,
    `getaddrinfo`);
  - пакет DPpass всегда вне туннеля (`TunnelSpecBuilder`), поэтому
    запрос уходит в сеть устройства, а не петлёй в TUN.
- Почему не DNS ядра:
  - серверы DnsPolicy сами могут ходить через `proxy`, и чтобы узнать
    адрес сервера, понадобился бы сам сервер;
  - DNS-клиент системного dialer глобален, и его переназначает каждый
    `core.New` (D-25).
  Системный резолвер не зависит от DnsPolicy, поэтому ошибка в DNS
  конфигурации не отрезает соединение с сервером.
- **Что уходит мимо туннеля** — только имена серверов профилей, но не
  имена назначений приложений. Система резолвит их так, как настроил
  пользователь: если включён «Частный DNS» Android (DNS-over-TLS) —
  через него, иначе через DNS сети, открыто. Стратегия адресов
  DnsPolicy к имени сервера не применяется. Профиль с IP-адресом не
  резолвится вовсе.
- Это свойство не скрывается: оно описано в модели угроз (T4), а в
  интерфейсе (этап 4) профиль с именем сервера помечается.

**Следствия.** Зашифрованный резолв имени сервера в обход системы (свой
DoH напрямую) — в «Отложено». К нему стоит вернуться, когда появятся
данные о подмене имён серверов (пробы сети, этап 3).

**Проверка.**
- `XrayCompilerTest.serverNameIsLeftToTheSystemResolver`: у `proxy` нет
  `sockopt`, адрес совпадает с профилем, в корпусе есть серверы по
  имени.
- `TunnelSpecBuilderTest.ownPackageIsAlwaysOutsideAndAppRulesAreLowered`:
  пакет DPpass вне туннеля.
- На устройстве — вместе с сервисом туннеля: имя сервера резолвится
  вне туннеля (`TODO.md`, «Следующее (этап 2)»).

### D-30 — Туннель в процессе приложения; мост fd → ядро — вход TUN Xray

Принято 4 октября 2026, этап 2. Закрывает два отложенных вопроса —
работы 5 и 6 этапа 2 (`docs/direction/ROADMAP/02-xray-backend.md`).

**Решение.**
- **Один процесс.** Сервис туннеля, ядро и оболочка работают в процессе
  приложения; `android:process` нет ни у одного компонента.
  - Отдельный процесс дал бы изоляцию: система могла бы выгрузить
    оболочку, а её падение не обрывало бы туннель.
  - Цена — IPC между процессами (Binder) и второй экземпляр всего, что
    сейчас рассчитано на один процесс: хранилища (атомарная замена
    файла, D-19, не защищает от записи из двух процессов), журнала
    (один писатель файла сеанса, D-26), `DPpassCore` и состояния
    активации.
  - Ядро и так одно на процесс (D-25).
  - Выигрыш пока не измерен. Пороги памяти ставит замер на устройстве
    (`docs/PERFORMANCE_BUDGET.md`, §4, этап 3), а падения оболочки
    станут заметны с интерфейсом продукта (этап 4); сейчас оболочка —
    несколько кнопок разработки. Пересмотр — только новым решением с
    этими данными.
- **Мост fd → ядро — вход TUN Xray** (как уже сделано в D-25): fd от
  `VpnService` передаётся ядру, локальных входов нет.
  - hev-socks5-tunnel передаёт трафик ядру через его вход SOCKS. Это
    второй вход, который политика моста запрещает (D-25, T11).
  - Кроме того, это ещё одна нативная библиотека в APK (D-18, D-20).
  - Вместо эксперимента «какой мост лучше» выбранный путь замеряется на
    устройстве (этап 3): стабильность, память, батарея, утечки. Если
    вход TUN Xray их не выдержит — новое решение с этими замерами.

**Следствия.** Работа 6 этапа 2 — сервис туннеля в том же процессе:
`DPpassVpnService` → `AndroidTunnelProvider.establish` → `toTunInput()`
→ `DPpassCore.connect`. Правило T11 о локальном входе с
аутентификацией остаётся на случай пересмотра.

**Проверка.**
- `check_manifest.py` и `check_apk.py`: `android:process` нет ни в
  исходном, ни в итоговом манифесте.
- `go test` моста (`TestPolicyAllowsOnlyTunInbound`) и
  `XrayJniTest.foreignInboundIsRejectedByBridgePolicy`: любой вход,
  кроме TUN, — отказ.

### D-31 — Источники геоданных: DB-IP — в репозитории, dlc — Go-модулем; private — по реестрам IANA

Принято 5 октября 2026, этап 2. Уточняет D-27: где лежат закреплённые
источники и как собираются коды, которых нет в источниках.

**Решение.**
- **DB-IP — файл выпуска в репозитории** (`tools/xray/geodata/sources/`,
  без изменений, SHA-256 — в PROVENANCE, §4).
  - Замер 5 октября 2026: на download.db-ip.com доступны выпуски
    2026-08, 2026-09 и 2026-10, а 2026-07 и старше — уже нет (404).
    Закреплённый месяц через квартал не скачать, и сборка старого
    коммита перестала бы повторяться.
  - Цена — около 4,3 МиБ истории git на каждое обновление выпуска. Выпуск
    обновляется по чек-листу D-18, а не каждый месяц.
  - Сборка не ходит на сторонний сервер за данными, поэтому подмена
    выпуска на сайте мимо записанной суммы невозможна (T10).
- **dlc — Go-модуль `github.com/v2fly/domain-list-community`** той версии,
  что в каталоге. Его отдаёт proxy.golang.org: архивы там неизменны, сумма
  сверяется с журналом sum.golang.org, как у модулей ядра (`goenv.py`).
  Сумма `h1:` записана в PROVENANCE и сверяется при каждой сборке. В
  `tools/xray/go.mod` модуль не входит: это данные, а не код сборки.
- **Разбор — свой и строгий** (D-05, D-20), по описанию формата в README
  dlc. Непонятная строка, неизвестный список в `include`, `include` по
  кругу, строка DB-IP не по формату или вне порядка — ошибка сборки с
  файлом и строкой, а не пропуск. Имена доменов в dlc приводятся к
  нижнему регистру: DNS не различает регистр, смысл не меняется.
  Одинаковые правила с разными атрибутами не сливаются: слияние
  расширило бы выборку `geosite:список@a@b`.
- **`ZZ` DB-IP не входит в набор**: это пометка «без страны»
  (зарезервированные и частные диапазоны), а не страна.
- **`private` — своя таблица** (`tools/xray/geodata/private.go`). В неё
  входят блоки реестров особых адресов IANA для IPv4 и IPv6 (RFC 6890),
  которые реестр прямо называет недостижимыми глобально («Globally
  Reachable: False»). Внутри блока решает самый узкий блок реестра:
  например, 192.0.0.9/32 достижим, хотя 192.0.0.0/24 — нет. Блоки «N/A»
  и без ответа в `private` не входят. Кроме того, в таблицу входят
  групповые адреса (RFC 5771, RFC 4291): они не адресуют один узел.
  Реестры сверены 5 октября 2026.

**Следствия.** Сборщик набора — `tools/xray/geodata` (Go) и
`tools/xray/geodata.py`. Набор собирается и целиком проверяется ядром
на хосте. Задача сборки APK, перенос на устройстве и сверка
конфигурации с оглавлением — оставшиеся работы D-27 (`TODO.md`).

**Проверка.**
- `check_dependencies.py`: версии каталога — в матрице и PROVENANCE,
  файл выпуска DB-IP на месте и с записанной суммой, других файлов в
  `sources/` нет.
- `geodata.py`: суммы обоих источников совпадают с PROVENANCE, иначе
  сборка не идёт.
- `go test` сборщика (`TestDbipRejectsWhatItCannotRead`,
  `TestDlcRejectsWhatItCannotRead`,
  `TestPrivateFollowsTheNarrowestRegistryBlock`,
  `TestBuildIsDeterministicAndManifestDescribesFiles`).
- Шаг hostcheck «Xray: геоданные»: ядро Xray 26.9.30 загружает каждый
  код собранного набора.

### D-32 — Проверка здоровья на устройстве: запрос DNS через сервер профиля к DNS-серверу конфигурации

Принято 5 октября 2026, этап 2; вариант выбран автором из трёх. Уточняет
D-15 («здоровье — по полезной нагрузке») для ядра Xray на устройстве.

**Решение.**
- После запуска кандидата мост делает один запрос DNS «`. NS`» к
  DNS-серверу конфигурации через исходящий `proxy`, в обход правил
  маршрутизации. Если ответ на этот запрос пришёл, данные прошли через
  сервер профиля туда и обратно.
- Сервер для пробы — сервер DNS по умолчанию, если он идёт через
  туннель, иначе первый такой в списке. Годятся DoH, UDP и TCP; DoT ядро
  не умеет.
- Новых связей со сторонними серверами нет (D-12): сервер DNS выбрал
  пользователь, и туннель всё равно будет к нему обращаться. Запрос
  «`. NS`» ничего не говорит о пользователе.
- Сертификат сервера DoH проверяется системными корнями; выключить
  проверку нельзя (T5).
- Исходы пробы различаются, у каждого свой код:
  - через сервер не пришло ни байта — `ENDPOINT_UNREACHABLE`;
  - TLS с сервером DoH не установлен — `TLS_HANDSHAKE_FAILED`;
  - байты шли, но ответа за срок нет — `PAYLOAD_STALLED`;
  - пришёл не ответ DNS — `HEALTH_CHECK_FAILED`.
- Почему исходящий proxy закрыл соединение, проба сама не видит: ей
  достаётся только закрытый канал («io: read/write on closed pipe»).
  Ошибку исходящего ядро передаёт тому, кто открыл соединение
  (`session.TrackedConnectionError`, так же — наблюдатель самого Xray);
  она идёт в причину пробы перед текстом самой пробы, через `Redactor`
  (уточнено 6 октября 2026 после проверки на телефоне).
- Срок пробы на 2 с меньше срока проверки здоровья плана
  (`ConnectionPolicy.healthTimeoutMillis`): вызов ядра блокирующий, и
  отмена корутины его не прерывает.
- Если в конфигурации нет DNS через туннель, проверять не через что.
  Тогда подключение не отвергается, но и не считается проверенным:
  предупреждение `HEALTH_CHECK_SKIPPED` — в журнале и в отчёте.

**Чем не является.**
- Передача маленькая (сотни байт), поэтому обрыв после 16–20 КБ (L7)
  она не ловит. Его ловят пробы сети этапа 3 (D-14, «крупная передача»).
- Фиксированный внешний ориентир (загрузка больше 32 КБ) отклонён: это
  постоянная связь со сторонним сервером при каждом подключении (D-12) и
  отдельный выбор сервера. Вариант «без проверки» отклонён, потому что
  противоречит D-15.

**Следствия.** Сервис туннеля (работа 6 этапа 2) подключает ядро:
`DPpassVpnService` → `AndroidTunnelProvider.establish` → `toTunInput()`
→ `DPpassCore.connect` с этой проверкой. Конфигурация с синтетическими
серверами (пример оболочки) на устройстве не подключится. Это честный
отказ с причиной, а не ошибка.

**Проверка.**
- `go test` моста:
  - `TestProbeGoesThroughProxyPastRules` — проба через proxy и
    защитника, хотя правило уводит адрес в `block`;
  - `TestProbeVerifiesDoHCertificate`;
  - `TestProbeTellsBadAnswerFromSilence`, `TestProbeStallsAfterHandshake`.
- `XrayJniTest.dnsProbeGoesThroughProxyAndProtector` — то же через JNI.
- `XrayHealthTest` — выбор сервера и пропуск с предупреждением.
- `XrayProxyEngineTest.healthProbeGoesToTunnelDnsServerAndMapsOutcomes`
  — коды исходов; личный путь DoH в диагностику не попадает.

### D-33 — Лимит устройств у поставщика: случайный идентификатор подписки, только с согласия

Принято 5 октября 2026, этап 2. Частично заменяет D-12. Факты —
`docs/research/REMNAWAVE_SUBSCRIPTIONS.md`.

**Почему.** Панели Remnawave с включённым лимитом устройств без заголовка
`x-hwid` отдают не серверы, а заглушку «App not supported». Так
отвечает и подписка автора DPpass. По D-12 такую подписку DPpass не
загрузил бы никогда. По документации Remnawave `x-hwid` — непрозрачная
строка, которую выбирает клиент (10–64 символа `[A-Za-z0-9=-]`); модель
и ОС устройства (`x-device-os`, `x-ver-os`, `x-device-model`) не
обязательны.

**Решение.**
- **По умолчанию идентификатор не отправляется** (D-12 действует).
  Пользователь включает его сам для одной подписки. Подписка включить
  его не может (D-11): заголовки поставщика — повод подсказать, а не
  включить.
- **Значение — случайное, не из устройства.** При включении DPpass
  создаёт 128 случайных бит (`SecureRandom`, D-21) — 32 шестнадцатеричные
  цифры. Идентификаторы системы и железа (`ANDROID_ID`, серийный номер,
  IMEI, MAC, `Build.*`) DPpass не читает, как и раньше.
- **На каждую подписку — свой.** Поставщики не могут связать
  подписки одного пользователя. Сброс создаёт новое значение. Для
  поставщика это новое устройство, а старое остаётся в его списке, пока
  его там не удалят.
- **Отправляется только `x-hwid`** и только в запросах к адресу этой
  подписки. Модель, ОС и их версии не отправляются; `User-Agent` —
  собственный и одинаковый у всех установок одной версии
  (`DPpass/<версия>`).
- **Идентификатор — секрет** (`Secret`): он не попадает в журнал и
  отчёт, хранится вместе с подпиской в зашифрованном хранилище (D-19).
- **Отказ поставщика называется прямо, заглушка не загружается.**
  - `x-hwid-not-supported: true` — `SUBSCRIPTION_DEVICE_ID_REQUIRED`:
    поставщик требует идентификатор устройства.
  - `x-hwid-max-devices-reached: true` —
    `SUBSCRIPTION_DEVICE_LIMIT_REACHED`: лимит устройств исчерпан,
    устройство нужно удалить у поставщика.
  В обоих случаях тело ответа — заглушка, а не серверы. Удачная ревизия
  подписки остаётся прежней (D-08).

**Следствия.** Загрузка по HTTPS (этап 3, работа 2) отправляет ровно те
заголовки, что строит `SubscriptionRequest`. Переключатель и показ
идентификатора — интерфейс этапа 4; до него идентификатор задаётся в
модели подписки.

**Проверка.**
- `SubscriptionUpdaterTest.requestHasNoDeviceIdUnlessEnabled` — без
  согласия идентификатора в запросе нет, а в запросе нет ничего, кроме
  адреса, `User-Agent` и идентификатора подписки;
- `SubscriptionUpdaterTest.deviceIdsAreRandomPerSubscription` — значения
  случайные и разные у подписок;
- `SubscriptionUpdaterTest.deviceRefusalsAreNamedAndPlaceholderIsNotImported`
  — отказы с кодом, заглушка не разбирается, удачная ревизия не тронута.

Корпус: `tests/data/subscriptions/remnawave-device-id-required`,
`remnawave-device-limit-reached`.

сейчас.

**Решение.**
- **Фреймворк — встроенные `android.view`/`android.widget`, без
  AndroidX и библиотек Material.**
  - В цепочке поставки ничего не прибавляется (D-20, T10):
    `check_apk.py` пропускает в APK только утверждённые корни пакетов.
  - Размер не растёт: APK одного ABI уже около 42 из 46 МиБ бюджета (D-28).
  - Compose отклонён: десятки артефактов AndroidX и несколько МиБ в
    APK ради того, что выражается платформой.
- **Своя система дизайна** (`app/src/main/res/values*`, пакет
  `com.dpsmpx.dppass.app.ui`):
  - цвета — токенами для светлой и тёмной темы (`values-night`), контраст
    текста не ниже WCAG AA;
  - шкала шрифтов в `sp` (растёт с системным размером);
  - отступы — шаг 4 dp, касаемая область — не меньше 48 dp;
  - формы — своими рисунками XML; значки — векторные XML собственного
    рисунка (D-01).
- **Устройство.**
  - Одна `Activity`, экраны — представления (`Screen`), переключаемые
    нижней панелью: «Подключение», «Серверы», «Подписки», «Журнал».
  - Логика экранов — в простых классах без Android там, где её можно
    проверить на хосте.
  - Тексты — ресурсы на русском и английском; сообщения диагностики —
    из кодов `DiagCode` (D-22).
  - Подписи для TalkBack у всех значимых элементов.
- **Выбор сервера пользователем — часть плана (D-15).**
  - Выбранный сервер идёт первым, раньше «последнего удачного».
  - Пауза после отказа на него не действует: пользователь сам просит
    попробовать.
  - Остальные кандидаты — запасные по прежним правилам D-15.
  - Исключения по возможностям ядра и по сети действуют и для него.
- **Экраны с конфигурацией защищены от снимков** (`FLAG_SECURE`, T9) —
  как и оболочка раньше.

**Следствия.** Этап 4 — «в работе» параллельно с этапами 2 и 3; его
критерии выхода не меняются. Оболочка разработки заменяется
интерфейсом; журнал устройства (D-26) остаётся на экране «Журнал».

**Проверка.**
- `check_apk.py` — корни пакетов кода без изменений;
- Lint (`warningsAsErrors`);
- `CandidatePlannerTest.userChoiceGoesFirstAndIgnoresBackoff`;
- `check_contrast.py` (`project.contrast`, с 18 октября 2026) — контраст
  токенов обеих тем: текст не ниже 4,5:1, граница и состояние элемента
  управления — не ниже 3:1 (WCAG 2.2 AA).

### D-35 — Подпись тестовых сборок: ключ разработчика у автора, APK — в ветке `apk`

Принято 5 октября 2026 по решению автора.

**Почему.** Отладочный ключ у каждого контейнера свой. APK из разных
сессий не ставятся друг поверх друга, и каждый раз приходилось удалять
приложение вместе с данными.

**Решение.**
- **Ключ разработчика** — RSA 4096 в хранилище PKCS12, алиас
  `dppass-dev`. Создаётся в сессии по просьбе автора и передаётся ему,
  копия в контейнере удаляется. В репозиторий ключ и пароли не попадают
  никогда: `.gitignore` и `check_secrets.py`. (6 октября 2026: ключ
  создан не в сессии, а на устройстве автора — скриптом на OpenSSL в
  Termux; в контейнере его не было. Отпечаток — `docs/PROVENANCE.md`, §7.)
- **Как сборка получает ключ.** Из переменных окружения:
  `DPPASS_SIGNING_KEYSTORE_BASE64` (или путь `DPPASS_SIGNING_KEYSTORE`),
  `DPPASS_SIGNING_STORE_PASSWORD`, `DPPASS_SIGNING_KEY_ALIAS`,
  `DPPASS_SIGNING_KEY_PASSWORD`. Облачные сессии получают их секретами
  окружения, которые задаёт автор. Без ключа APK не подписываются —
  без молчаливой подмены отладочным ключом.
  - Подписывает не Gradle, а `tools/release/sign_apks.py` через
    `apksigner`, пароли — по имени переменной (`env:…`), не в командной
    строке: ключ не попадает в демон Gradle и в кеш конфигурации, а
    проверка подписи — в том же шаге, что и подпись. Gradle собирает
    `release` неподписанным, APK на ABI — по свойству `dppass.abiSplit`
    (уточнено 5 октября 2026 при реализации).
- **Это не выпуск** (`CLAUDE.md`, «Чего не делать»: релиз — этап 5).
  - Сборка — для устройств автора: `release` без R8, версия с `-dev`.
  - Отдельный APK на каждый ABI (D-28).
  - APK лежат в отдельной ветке `apk` без истории `main`: двоичных
    файлов в `main` нет (`docs/PROVENANCE.md`, §4).
  - В той же ветке — `SHA256SUMS` и отпечаток сертификата.
- **Ключ для магазинов (этап 5) — другой.** Его выбор — вместе с
  каналами распространения; этот ключ туда не идёт.

**Следствия.** Отпечаток сертификата SHA-256 записан в
`docs/PROVENANCE.md` (§7): по нему автор проверяет, что APK подписан его
ключом (`apksigner verify --print-certs`).

**Проверка.**
- `check_secrets.py` — файлы ключей в репозитории запрещены;
- `tools/release/sign_apks.py` — подпись `apksigner`, проверка подписи и
  совпадения отпечатка с записанным; `check_apk.py` — каждый APK.

### D-36 — Подписки в приложении: хранение, загрузка по HTTPS, базовая политика

Принято 5 октября 2026 по решению автора. Работа 2 этапа 3 (загрузка
подписок по HTTPS) сделана раньше, вместе с интерфейсом (D-34): без
неё подписка автора (`docs/research/REMNAWAVE_SUBSCRIPTIONS.md`) на
телефоне не загрузится.

**Решение.**
- **Хранение.** Подписки — запись `subscriptions/state` в
  зашифрованном хранилище (D-19), документ `dppass.subscriptions`
  версии 1. В записи: адрес и идентификатор устройства (секреты),
  название, привязка, метаданные, последняя удачная и последняя неудачная
  ревизии. Запись атомарна; что не читается, уходит в карантин (D-06).
- **Загрузка.**
  - `HttpsURLConnection` с системными CA (T5), только `https://`;
    переадресация — тоже только на `https://`.
  - Тайм-аут и предел размера — из `FetchPolicy`; предел действует во
    время чтения, а не после.
  - Заголовки — ровно `SubscriptionRequest` (D-12, D-33).
  - Код ответа не 2xx — отказ с кодом HTTP в причине. Адреса в
    сообщениях нет: он секрет.
  - Загрузка идёт из процесса приложения, то есть мимо туннеля:
    собственный пакет DPpass в туннель не входит (D-17).
- **Активная подписка одна.** «Применить» делает её серверы серверами
  активной конфигурации (`DPpassCore.activateSubscription`, D-07, D-08).
  - Маршрутизация и DNS — пользователя, если есть своя активная
    конфигурация.
  - Если её нет — базовая политика: всё через туннель, локальные сети
    мимо него, DNS — DoH `https://1.1.1.1/dns-query` через туннель.
  - Почему DoH через туннель: имена не видит сеть (T4), и проба
    здоровья D-32 идёт через этот сервер. Адрес — IP, чтобы не
    резолвить имя самого резолвера.
  - Свою маршрутизацию пользователь задаёт документом DPpass.
- **Обновление — вручную.** Автообновление по расписанию остаётся
  работой этапа 3: без AndroidX нет `WorkManager`, нужен `JobScheduler`.

**Состояние.** В части базовой политики заменено D-38 (политика
пользователя), в части «обновление — вручную» — D-39 (автообновление).

**Проверка.**
- `SubscriptionBookTest` — запись и чтение, порча — карантин, секреты
  не в открытом виде;
- `SubscriptionFlowTest` — добавление, обновление, активация с базовой
  политикой и с политикой пользователя, отказ поставщика не трогает
  удачную ревизию;
- `HttpsSubscriptionFetcherTest` — предел размера во время чтения,
  только `https://`.

### D-37 — Формат конфигурации версии 2: отпечатки TLS, перегрузка Hysteria2, настройки XHTTP

Принято 5 октября 2026. Факты о подписке автора —
`docs/research/REMNAWAVE_SUBSCRIPTIONS.md`, §3; о Xray 26.9.30 — его
исходник (`transport/internet/tls/tls.go`, `infra/conf/transport_method.go`,
`infra/conf/transport_internet.go`, `transport/internet/hysteria/dialer.go`).

**Почему.** Из 35 записей подписки автора 7 отвергались не потому, что
их нельзя выразить, а потому, что в IR не было значений и полей:
отпечатков `edge` и `qq`, настроек XHTTP из `extra` и управления
перегрузкой Hysteria2 из `fm`. Xray 26.9.30 всё это понимает однозначно.

**Решение.**
- **Версия формата 2.** Она только добавляет; смысл прежних полей не
  меняется.
  - `security.fingerprint` — плюс `ios`, `android`, `edge`, `360`,
    `qq`, `random`, `randomizednoalpn`: готовые отпечатки Xray 26.9.30
    (`PresetFingerprints`). `random` — один из современных отпечатков,
    его ядро выбирает при каждом запуске; `randomized` и
    `randomizednoalpn` — сгенерированные. `unsafe` (TLS Go без
    подделки отпечатка, узнаваемый) не входит.
  - `protocol.congestion` у `hysteria2` — `bbr` или `reno`; нет поля —
    как раньше: Xray без скорости Brutal (её в IR нет) берёт BBR.
    `brutal`/`force-brutal` не входят: им нужны скорости канала.
  - У транспорта `xhttp` — необязательные `x_padding_bytes`,
    `sc_max_each_post_bytes`, `sc_min_posts_interval_ms` (диапазон
    «N» или «N-M», N ≥ 1), `no_grpc_header` и `xmux`
    (`max_concurrency` или `max_connections` — не вместе,
    `c_max_reuse_times`, `h_max_request_times`, `h_max_reusable_secs` —
    диапазоны ≥ 0; `h_keep_alive_period` — секунды ≥ 0).
  - Компилятор пишет их прямо в `xhttpSettings`, а не через `extra`:
    Xray заменяет всю настройку содержимым `extra` целиком. Заданный
    `xmux` заменяет значения Xray по умолчанию — так же, как у
    поставщика.
- **Миграция 1 → 2 — тождественная.** Это первая производственная
  миграция (D-06): на телефоне автора активная конфигурация хранится
  документом версии 1 (D-07). Без миграции она ушла бы в карантин.
- **Ссылки.** `fp` — те же значения. `extra` у `xhttp` — JSON только с
  ключами выше. `fm` у `hysteria2` — JSON только вида
  `{"quicParams":{"congestion":…}}` со значением `bbr` или `reno`. Любой другой ключ или
  значение — отказ с названием (D-05).

**Следствия.** Из записей подписки автора DPpass выражает 34 из 35;
отвергается только Shadowsocks со старым AEAD (D-16).

**Проверка.**
- `ConfigFormatV2Test` — новые значения и поля читаются, пишутся и
  читаются обратно; документ версии 1 проходит через миграцию;
  неверные диапазоны и `xmux` с обоими пределами отвергаются с путём;
- `ShareLinkParserTest.formatV2LinkParameters` — `fp`, `extra`, `fm`;
  незнакомый ключ в `extra` или `fm` — отказ;
- `XrayCompilerTest.formatV2FieldsReachXray`;
- корпус `tests/data/configs/valid-format-v2` (эталоны Xray принимает
  само ядро, шаг «Xray»), `tests/data/subscriptions/remnawave-format-v2`
  (что принимается и что отвергается с названием), `remnawave-links`
  (9 из 10 записей).

### D-38 — Политика пользователя: маршрутизация, DNS и приложения задаются в интерфейсе

Принято 5 октября 2026. Заменяет постоянную базовую политику D-36
настраиваемой.

**Почему.** По D-36 маршрутизацию пользователь мог задать только
документом DPpass, а с подпиской всё шло через туннель. Пользователю в
России нужны хотя бы «российские сайты напрямую», выбор приложений и
DNS. Без этого подписка на телефоне работает, но неудобно.

**Решение.**
- **Политика** — запись `settings/policy` в зашифрованном хранилище
  (D-19), документ `dppass.policy` версии 1. Чтение строгое, порча —
  карантин. Из политики строятся `RoutingPolicy` и `DnsPolicy`
  (`PolicyBuilder`).
  - **Режим маршрутизации.** «Всё через туннель» — по умолчанию.
    «Российское напрямую»: `geosite:category-ru` и `geoip:ru` —
    `direct`. DNS этих имён в этом режиме идёт к системному резолверу
    мимо туннеля. Соединение с ними и так идёт мимо туннеля, а ответ
    зарубежного резолвера указывал бы на зарубежные узлы CDN. Это
    видно в интерфейсе.
  - **Реклама** — `geosite:category-ads-all` → `block`; по умолчанию
    выключено.
  - **Локальные сети мимо туннеля** — по умолчанию включено.
  - **Приложения**: все; все, кроме выбранных; только выбранные
    (`AppPolicy`, D-09). Список — только приложения с ярлыком запуска
    (`<queries>`); `QUERY_ALL_PACKAGES` не запрашивается.
  - **DNS** — DoH через туннель по IP-адресу: Cloudflare `1.1.1.1` (по
    умолчанию, как в D-36), Google `8.8.8.8`, Quad9 `9.9.9.9`.
- **Где действует.**
  - Политика — основа активной конфигурации из подписки вместо
    постоянной базовой политики D-36.
  - Смена политики — новая активация действующих серверов с новой
    маршрутизацией и DNS. Это транзакция D-07: при отказе остаётся
    прежнее.
  - Документ DPpass со своей маршрутизацией действует, пока
    пользователь не сменит политику. Интерфейс предупреждает, что смена
    её заменит.
- Коды geosite/geoip политики сверяются с набором геоданных так же, как
  правила документа (`GEO_CODE_UNKNOWN`, D-27).

**Проверка.**
- `PolicyBuilderTest` — каждый режим даёт ожидаемые правила и DNS,
  решения `RouteEvaluator` по ним верны;
- `PolicyStoreTest` — запись и чтение, порча — карантин;
- `PolicyServiceTest.changingPolicyReactivatesActiveServers` — смена
  политики сохраняет серверы и подписку, меняет маршрутизацию; отказ
  активации оставляет прежнюю.

### D-39 — Автообновление подписок по расписанию

Принято 5 октября 2026. Работа 2 этапа 3 — вторая половина (первая —
D-36).

**Решение.**
- **Обновляется только применённая подписка.** Обновление
  неприменённой сделало бы её активной: её серверов нигде, кроме ответа
  поставщика, нет (D-36).
- **Срок** — `UpdatePolicy.intervalMinutes` подписки: 12 часов по
  умолчанию; пользователь выбирает «выкл», 6, 12 или 24 часа.
  `profile-update-interval` поставщика показывается как подсказка и не
  применяется сам (D-11, §3 `SECURITY_MODEL.md`).
- **Когда пора** — решает ядро, а не Android (`UpdateSchedule.due`):
  пора, если с последней удачной загрузки прошёл срок, а после неудачи
  — не раньше чем через 30 минут. Это проверяется на хосте.
- **Как запускается.** `JobScheduler` раз в час, только при сети
  (`onlyUnmetered` — только без тарификации). Задача не переживает
  перезагрузку (`setPersisted` требует `RECEIVE_BOOT_COMPLETED`) и
  ставится заново при каждом запуске процесса.
- **Туннель поднят.** Новые серверы активируются (D-07). Туннель
  переподключается, только если подключённого сервера больше нет или он
  изменился. Иначе соединения не рвутся.
- Загрузка идёт мимо туннеля, как и вручную (D-36).

**Проверка.**
- `UpdateScheduleTest` — сроки, пауза после неудачи, выключенное
  автообновление;
- `SubscriptionFlowTest.backgroundRefreshKeepsUnchangedConnection` —
  неизменный подключённый сервер не требует переподключения.

### D-40 — Жизненный цикл туннеля: always-on, перезапуск, плитка, сеть устройства

Принято 5 октября 2026. Работа 4 этапа 3.

  гибели (`START_STICKY`, пока туннель нужен) поднимают последнюю
  активную конфигурацию (D-07), а не пустую. Остановка пользователем —

- **Сеть устройства.** `NetworkCallback` по сети по умолчанию →

  сеть сами. Для этого — разрешение `ACCESS_NETWORK_STATE` (обычное,
  без запроса у пользователя).
- **Из фона.** Если система не даёт сервису стать foreground (Android 12+,

- **Уведомление** — время с подключения, скорость и трафик (раз в 2 с,

  без имени сервера (T9).
- **Счётчики** — `EngineSession.stats()` (D-25), опрос раз в секунду
  только пока виден экран «Подключение».

  своим системным разрешением, `ACCESS_NETWORK_STATE` — в утверждённых;

### D-41 — Задержка до серверов: TCP-рукопожатие по действию пользователя

Принято 5 октября 2026.

**Решение.**
- **Только по действию** «Проверить задержку» на экране «Серверы».
  Сам по себе DPpass к серверам не стучится (D-14: без залпов).
- **Что мерится** — время TCP-рукопожатия до адреса и порта сервера из
  процесса приложения, то есть мимо туннеля (D-17).
  - Серверы — по одному, с паузой 150 мс; тайм-аут 3 с; не больше 128
    серверов за проверку.
  - Hysteria2 (UDP) так не мерится и показывается как «UDP».
  - Имя сервера резолвит система, как и для ядра (D-29). Это
    единственное место вне ядра, где DPpass резолвит имя
    (`network/Latency.kt`, `check_forbidden_apis.py`, правило
    `dns-resolve`). Длительность — монотонными часами (`Clock.MONOTONIC`).
- **Что это значит.** Задержка до сервера, а не «работает»: TCP
  проходит и там, где режется TLS (D-13). Интерфейс так и пишет.
- **Место в плане (D-15).** Известная задержка — порядок среди
  кандидатов с одинаковым здоровьем, классом и приоритетом. Меньше —
  раньше, неизмеренные — после измеренных. В причинах попытки —
  «задержка N мс». Тайм-аут — как неизмеренный, а не как отказ.
  Результаты живут в памяти процесса.

**Проверка.**
- `LatencyBookTest` — запись, тайм-аут, UDP;
- `CandidatePlannerTest.latencyOrdersEquallyHealthyCandidates`;
- `check_forbidden_apis.py` — резолв имени только в `TcpLatencyProbe`
  (`network/Latency.kt`).

### D-44 — Адаптивная устойчивость: обучение на наблюдениях, устойчивость важнее скорости

Принято 5 октября 2026 по решению автора. Версия 0.5.0 (`app/build.gradle.kts`).
Исследование подхода — `docs/research/ZAPRET_ADAPTIVE_METHODS.md`; факты о
сети — `docs/research/RUSSIA_NETWORK_RESTRICTIONS.md`.

**Почему.** Блокировки меняются неделями и по сетям (L5, L7): сервер,
рабочий вчера, сегодня «подключается, но данных нет» (L7). Пользователю
важнее стабильное соединение и быстрая реакция на сбой, чем пиковая
скорость: критичны джиттер, задержка и устойчивость. Политика
подключения D-15 уже упорядочивает кандидатов, но не учится и забывает
исход сразу после попытки.

**Решение.**
- **Что учится.** В модуле `connection` (`StabilityModel`,
  `StabilityBook`) ведётся по паре «сеть, сервер» агрегат наблюдений
  `StabilityObservation` (успех, RTT, «замерзание» L7, прошедшие байты).
  Из него — оценка устойчивости. Это **не** десинхронизация пакетов
  (её делает Zapret, ей нужен root — отложенный вопрос «Локальная
  DPI-десинхронизация»): «стратегия» DPpass — выбор кандидата (D-15),
  параметры сервера не меняются (D-05, D-11).
- **Устойчивость, а не скорость.** Оценка = `0.55·надёжность +
  0.25·стабильность джиттера + 0.12·задержка + 0.08·отсутствие
  «замерзаний»`. Скорость в оценку не входит; при прочих равных меньшая
  задержка — тай-брейк. Веса — ориентир первой версии, меняются замером.
- **Надёжность — пессимистично.** Доля успехов — Beta(α,β) с априором
  (1,1) и **затуханием** по полураспаду (`HALF_LIFE_MILLIS`, сутки,
  D-21): старое наблюдение весит меньше. Порядок — по **нижней границе**
  доверия (α/(α+β) минус запас по дисперсии): 3 успеха из 3 не обгоняют
  95 из 100.
- **Задержка и джиттер — пассивно.** Сглаженный RTT и его отклонение —
  по RFC 6298 (SRTT, RTTVAR); джиттер — по RFC 3550, §6.4.1. Источник —
  время установки соединения и пробы D-32, без отдельных пакетов и
  залпов (D-14).
- **Быстрая реакция — обнаружение смены режима.** Тест Пейджа — Хинкли
  по исходам проб: когда отказы резко учащаются, уверенность в сервере
  сбрасывается за 2–3 наблюдения, не дожидаясь затухания. Переключение —
  с гистерезисом (`switchStreak ≥ 2` подтверждённых отказов или
  «замерзание» с проваленной пробой), с паузой и пределом переключений в
  час: смена сервера сама нагрузка и сигнал фильтру (L7).
- **Обобщение — лёгкая модель.** `TransportAdvisor` — один слой
  (логистическая регрессия: нейросеть из одного нейрона) над признаками
  сети и сервера (класс транспорта one-hot, класс ограничения,
  достижимость TLS/UDP). Онлайн-SGD, детерминированный, веса ограничены.
  Переносит опыт на серверы без своей истории: «в этой сети UDP не
  проходит» относится ко всем Hysteria2 новой подписки сразу. Модель не
  переопределяет явные правила и жёсткие исключения D-15 (белый список,
  UDP BLOCKED, backoff) — только порядок внутри годных.
- **Ключ сети — непрозрачный и грубый.** `NetworkKey` = соль установки
  (`SecureRandom`, D-21) ⊕ тип сети (Wi-Fi/мобильная/прочее) и класс
  ограничения. **Ни SSID, ни BSSID, ни адреса, ни оператора, ни
  идентификатора устройства** (D-12): модель хранит агрегаты, не трафик.
- **Хранение.** `StabilityBook` пишет агрегаты в зашифрованное хранилище
  (D-19), запись `adaptive/state` версии 1; переживает перезапуск.
  Повреждение — карантин (D-06), не затирает. Предел записей
  (`MAX_RECORDS`) и затухание держат размер.
- **Наблюдатель сессии.** Чистая логика `SessionSupervisor` (без Android,
  проверяется на хосте) по потоку наблюдений решает «держать или
  переподключиться»; Android-слой (`DPpassVpnService`) снимает пробу
  D-32 раз в `SUPERVISION_INTERVAL` и передаёт исход. Переподключение —
  проверенным путём жизненного цикла (`ACTION_RECONNECT`): план D-15
  строится заново, и модель к этому моменту уже понизила отказавший
  сервер, поэтому берётся другой кандидат. Удержание TUN поднятым на время
  переподключения (без разрыва трафика приложений) — уточнение на
  устройстве (`TODO.md`, этап 3).

**Отравление модели — угроза T14.** Короткий сбой не делается постоянным
выбором (априор, затухание, гистерезис); модель не хранит ничего о
содержимом трафика; наблюдения в неё кладёт только сам клиент по своим
попыткам, не сеть и не подписка.

**Честные пределы (D-13).** Пороги и веса не выверены на настоящих сетях
(этап 3): это разумная первая модель, а не доказанный оптимум.
«Самооптимизация» не обещает обойти блокировку — только быстрее выбрать
из того, что в конфигурации есть.

**Следствия.** `CandidatePlanner` получает `StabilityModel` как сигнал
порядка; `DPpassCore` держит `StabilityBook`; сервис — наблюдателя.
Поведение детерминировано при фиксированных входах и времени.

**Проверка.**
- `StabilityModelTest` — затухание, пессимистичная граница, джиттер
  (RFC 3550), смена режима (Пейдж — Хинкли), гистерезис переключения,
  устойчивость к одиночному сбою (T14);
- `TransportAdvisorTest` — обучение переносит вывод на новый сервер того
  же класса; веса ограничены; детерминизм;
- `SessionSupervisorTest` — держит при редких сбоях, переключает при
  подтверждённой деградации, не чаще предела;
- `CandidatePlannerTest.learnedStabilityOrdersViableCandidates` — опыт
  меняет порядок, но не трогает жёсткие исключения и выбор пользователя;
- `StabilityBookTest` — запись/чтение, карантин, отсутствие секретов и
  идентификаторов в хранимом;
- `check_forbidden_apis.py` (время — `Clock`, случайность — `SecureRandom`).

**Слияние линий (6 октября 2026).** Версию 0.5.0 сделали дважды:
здесь и в `main` (PR #25: свой `StabilityBook` и описание адаптивного

деградация — ещё и отказ в журнале здоровья, а выбранный пользователем
сервер заменяется только с его согласия (D-58).

### D-45 — Автоматический раздельный маршрут: отечественное мимо туннеля без ручного выбора

Принято 5 октября 2026 по решению автора. Версия 0.5.0. Уточняет D-38.
Факт — `docs/research/RUSSIA_NETWORK_RESTRICTIONS.md`, §4, п. 4: отечественные
сервисы с 15.04.2026 ограничивают пользователей с VPN, и раздельный
маршрут для них — условие их работы, а не удобство.

**Почему.** По D-38 «Российское напрямую» (`RU_DIRECT`) уже уводит
отечественные сайты и адреса мимо туннеля явными правилами. Но это
отдельный режим, а пользователю нужно, чтобы отечественное шло напрямую
**само**, без выбора сайтов и приложений.

**Решение.**
- **По назначению, а не по приложению.** Раздельный маршрут
  автоматический по адресу назначения: `geosite:category-ru` и `geoip:ru`
  из подписанного набора геоданных (D-27) → `DIRECT`. Приложение,
  обращающееся к отечественному серверу, идёт напрямую само — список
  приложений выбирать не нужно. Коды `ru` сверяются с набором (D-27,
  `GEO_CODE_UNKNOWN`).
- **Флаг `automatic_domestic`** в `RoutingPolicy` (формат v2, по
  умолчанию **false**). Когда включён — после всех явных правил
  пользователя добавляется запасное: отечественное назначение (по имени,
  по адресу и по адресу после резолва) → `DIRECT`. Явные правила
  пользователя всегда главнее (их проверяют первыми), поэтому смысл
  документа не меняется молча (D-05).
- **Где включается.** Только политикой пользователя (D-38), не самим
  документом: режим **`AUTO`** (`RoutingMode.AUTO`, рекомендуемый по
  умолчанию для подписок) = отечественные напрямую + `automatic_domestic`
  + отечественные имена системному резолверу (как `RU_DIRECT`: ответ
  зарубежного резолвера указал бы на зарубежные узлы CDN). Собственный
  документ пользователя (`user-import`) получает `automatic_domestic`,
  только если сам его задал.
- **Приложения — не угадываются.** Эвристика «имя пакета → отечественное
  приложение» ненадёжна (проверено 5 октября 2026 на наборе dlc: имя
  пакета вида `ru.<бренд>` или `com.<бренд>` совпадает с явной записью
  `category-ru` примерно у 60 %, у `ru.sberbankmobile`, `ru.hh.android`
  — нет). Молча исключать приложение по догадке нельзя (D-05): маршрут по
  назначению и так уводит их отечественный трафик напрямую, а целиком
  вывести приложение из туннеля остаётся явным выбором (`EXCEPT`, D-38).
- **Реклама** в `AUTO` — как в D-38: `category-ads-all` → `block`,
  по умолчанию выключено.

**Честные пределы (D-13).** Назначение домашним не делает приложение
работающим: если приложение проверяет сам факт VPN (T8), раздельный
маршрут назначения это не скрывает — для таких нужен явный `EXCEPT`.
Соответствие «домен ↔ Россия» — из набора геоданных на дату его сборки.

**Следствия.** `RouteEvaluator`, `XrayCompiler` и `PolicyBuilder`
понимают `automatic_domestic`; экран «Настройки» (D-34) предлагает `AUTO`
по умолчанию и объясняет, что отечественное пойдёт напрямую.

**Проверка.**
- `AutomaticDomesticRoutingTest` — явное правило главнее автосплита;
  отечественное (имя, адрес) → DIRECT; зарубежное — по умолчанию; по
  умолчанию выключено;
- `PolicyBuilderTest.autoModeEnablesDomesticSplit`;
- `XrayCompilerTest.automaticDomesticAddsCheckedRuRulesAfterUserRules` —
  два правила geosite:ru и geoip:ru (отдельными, не И) после правил
  пользователя, коды сверены с набором;
- `WriterAndNormalizerTest.automaticDomesticRoundTrips` — поле читается и
  пишется, по умолчанию false.
- На устройстве и отдельный корпус с эталоном ядра (шаг «Xray») —
  `TODO.md`.

**Слияние линий (6 октября 2026).** В `main` (PR #25) миграция
документа 1 → 2 включала разделение у всех прежних документов
(`automatic_domestic: true`) — маршрутизация менялась молча, вопреки
D-05. Оставлено решение отсюда: миграция тождественна, флаг по
умолчанию выключен. Коды разделения те же, что в PR #26
(`geosite:category-ru`, `geoip:ru`); есть ли они в собранном наборе,
проверяет `tools/xray/geodata.py` (проверка перенесена из PR #26).

### D-46 — Обнаружение VPN: честная позиция и раздельный маршрут как мера

Принято 5 октября 2026 по решению автора. Версия 0.5.0. Усиливает T8.
Факты — `docs/research/ANDROID_NETWORK_MODEL.md`, §6;
`docs/research/RUSSIA_NETWORK_RESTRICTIONS.md`, §1 (методика выявления VPN
приложениями, 06.04.2026).

**Что проверяют** (по открытым описаниям методики и приложений-проверок,
5 октября 2026): активную сеть с `TRANSPORT_VPN`, интерфейс `tun*`,
маршруты и host-route `/32`, аномалию MTU, `dumpsys` служб VpnService,
несовпадение IP по геолокации/ASN/ДЦ, локальные входы прокси.

**Решение (что DPpass делает, не ломая работу).**
- **Раздельный маршрут — главная мера** (D-45): трафик отечественных
  сервисов и собственный пакет DPpass идут **мимо** туннеля (D-17),
  поэтому их соединения — с домашнего IP, и проверка «underlying network»
  / exit-IP для них не срабатывает. Это помогает именно потому, что не
  прячет VPN, а убирает отечественный трафик из туннеля.
- **Нет локальных входов** (T11) и экспортируемых внутренностей (T13):
  проверки, ищущие порт прокси на `127.0.0.1` или gRPC/REST API ядра, у
  DPpass ничего не находят — их и нет.
- **Быстрая пауза**: кнопка и плитка (D-40) снимают туннель сразу, когда
  приложение требует «без VPN».
- **Название без «VPN»** (D-47): в списке приложений и в ярлыке DPpass не
  называет себя VPN; это не делает VpnService невидимым, но не подсвечивает
  его проверкам по имени.

**Чего DPpass не может (D-13, T8).** Скрыть `TRANSPORT_VPN` и `tun*` от
других приложений нельзя: это свойство `VpnService` Android. Клиент этого
**не обещает**. Режим без `VpnService` (локальный прокси для выбранных
приложений) не создаёт `TRANSPORT_VPN` — остаётся отложенным вопросом
(«Режим без VpnService»), архитектура его допускает.

**Проверка.** `PolicyBuilderTest`, `TunnelSpecBuilderTest` (отечественное
и свой пакет вне туннеля), `check_manifest.py` (нет экспортируемых
внутренностей и локальных входов), `go test` моста (входов, кроме TUN,
нет — T11).

### D-47 — Защита внутренних данных и интерфейса от анализа на устройстве

Принято 5 октября 2026 по решению автора. Версия 0.5.0. Усиливает T3, T7,
T9, T13. Правило CLAUDE.md «не обещать незаметности» (D-13) действует.

**Решение (меры, не влияющие на работу).**
- **Экран.** `FLAG_SECURE` на всех окнах, включая диалоги и нижние листы
  (снимки, запись экрана, миниатюры «Недавних» — пусты, T9). Чувствительные
  элементы (кнопка питания, согласие на импорт) не принимают касания
  через наложение (`setFilterTouchesWhenObscured`): чужое окно поверх не
  подтвердит действие и не прочитает его (tapjacking).
- **Журнал — только по кнопке.** Автокопирование журнала в буфер обмена
  при уходе с экрана и остановке сервиса убрано: содержимое буфера читают
  другие приложения. Наружу журнал уходит только явной кнопкой
  «Копировать журнал», с пометкой «чувствительное» (Android 13+) и после
  `STRICT`-редактирования (D-26). Заменяет часть D-26 про автокопию.
- **Данные.** Как прежде: `noBackupFilesDir`, AES-256-GCM, ключ в
  Keystore, без резервных копий и переноса (D-19, T7); модель устойчивости
  тоже в зашифрованном хранилище (D-44).
- **Поверхность.** Экспортированы только нужные компоненты под системными
  разрешениями (T13); локальных входов ядра нет (T11); видимость пакетов —
  только ярлыки запуска (D-38).
- **Случайные имя пакета и ярлык — личная сборка.** Автор собирает DPpass
  только для себя (не выпуск, D-35; публикации релиза до этапа 5 нет,
  `CLAUDE.md`), поэтому у личной сборки `applicationId` и ярлык
  приложения **случайны** и не называют ни «VPN», ни «DPpass»: в списке
  установленных приложений и по имени пакета (методика §1,
  `RUSSIA_NETWORK_RESTRICTIONS.md`) приложение неотличимо от обычного.
  - **Когда.** Android закрепляет `applicationId` при **сборке**, не при
    установке: отдельной «рандомизации в момент установки» в системе нет.
    Поэтому каждая личная сборка получает свежую случайную личность, и
    каждая переустановка — это новое, иначе названное приложение. Это
    верный для Android способ добиться запрошенного. (6 октября 2026:
    заменено D-49 — личность постоянна для ключа разработчика, сборки
    ставятся поверх.)
  - **Как.** `applicationId` = `com.<случайный>.<случайный>` (валидные
    сегменты пакета), ярлык — слово из нейтрального встроенного списка
    (без брендов и чужих названий, D-01, D-20). Значение — из свойства
    `dppass.identitySeed` (одно и то же зерно → та же личность,
    воспроизводимо) или случайное (`SecureRandom`). Включено для сборки
    `release` (личной); отладочная сборка и `check_apk.py` — со
    стабильной личностью, чтобы проверки были детерминированы. Кеш
    конфигурации Gradle может «заморозить» случайное значение между
    сборками: для гарантированно новой личности — свежий
    `dppass.identitySeed` или `--no-configuration-cache` (`TODO.md`).
  - **Что это не ломает.** Внутреннее пространство имён кода остаётся
    `com.dpsmpx.dppass` (классы, `R`, нативная библиотека, `check_apk.py`
    по коду — без изменений); меняется только устанавливаемая личность.
    Подпись и отпечаток (D-35) от `applicationId` не зависят. Собственный
    пакет вне туннеля (T4) берётся из `context.packageName` в момент
    работы — случайный id исключается правильно.
  - **Цена, принятая автором.** У каждой сборки своя личность, поэтому
    согласие на VPN и always-on запрашиваются заново, а данные прежней
    сборки (подписки, конфигурация, модель D-44) остаются у старого
    пакета. Для личного приложения это приемлемо (заявлено автором:
    обновления «поверх» не нужны). Для **публичного** выпуска
    `applicationId` фиксируется один раз (D-01, этап 5) — рандомизация
    туда не идёт.
- **Обфускация кода (R8) — этап 5.** До выпуска сборка без R8 (D-35);
  обфускация имён классов и строк — работа этапа 5, когда включаются
  подпись и R8 (`docs/direction/ROADMAP/05-release.md`). Защита от анализа
  кода приложения — там, не переобещается здесь.

**Честные пределы (D-13, T8).** Эти меры защищают данные и интерфейс на
устройстве без root; случайные имя и пакет убирают приложение из поиска
«по имени пакета/ярлыку», но **не** скрывают факт работы VPN
(`TRANSPORT_VPN`, `tun*`) от приложений и сайтов (T8) и не защищают от
устройства с root (вне модели, `docs/SECURITY_MODEL.md`, §2).

**Проверка.** `check_manifest.py` (экспорт, разрешения), `check_apk.py`
(личность не меняет корни кода и компоненты — сверка по пространству
имён, не по `applicationId`), `IdentityTest` (случайный `applicationId` —
валидный пакет; зерно воспроизводимо; ярлык без «VPN»). Экранные меры
(`FLAG_SECURE` диалогов через `Ui.secure`, tapjacking
`filterTouchesWhenObscured`, экспорт журнала только по кнопке —
`DeviceLog.onWorkFinished` не копирует) — обзор кода и проверка на
устройстве (`TODO.md`): это Android-слой, на хосте он не исполняется.

**Состояние.** В части «каждая сборка — новая личность» заменено D-49:
личность постоянна для ключа разработчика, сборки ставятся поверх.

### D-48 — Несмысловые параметры ссылок: поимённо отбрасываются с находкой

Принято 6 октября 2026. Уточняет D-05 и D-37 для ссылок подписок.

**Почему.** На телефоне автора (6 октября 2026, `TODO.md`, «На
устройстве») запись Hysteria2 подписки панели пропадала целиком из-за
`fm={"quicParams":{…,"debug":true}}`: незнакомый ключ `fm` по D-05 и
D-37 — отказ. Сервер терялся из-за флага, который на соединение не
влияет.

**Факт (исходники Xray 26.9.30, модуль `xray-core`
`v1.260327.1-0.20260930074004-b26a91de4f32`, проверено 6 октября 2026).**
`infra/conf/transport_internet.go`: `quicParams.debug = true` только
задаёт переменные окружения `HYSTERIA_BBR_DEBUG` и
`HYSTERIA_BRUTAL_DEBUG` — отладочный журнал управления перегрузкой во
всём процессе. В `internet.QuicParams` флаг не попадает: на провод, на
TLS и на выбор алгоритма он не влияет.

**Решение.**
- Параметр ссылки, который не меняет соединения, отбрасывается — но
  только **поимённо**: список в коде (`ShareLinkParser`), у каждого
  имени — датированный факт по исходникам закреплённой версии ядра.
  Сейчас в списке один `fm.quicParams.debug`.
- Отброшенный параметр — находка `SHARE_LINK_PARAM_IGNORED` (INFO) с
  местом записи, а не молчание (D-05). Значение не того типа (`debug`
  не true/false) — отказ записи, как у любой испорченной ссылки.
- Всё, чего нет в списке, — по-прежнему отказ с названием (D-05, D-37).
  «Похоже на косметику» — не довод; довод — исходник ядра.
- DPpass флаг дальше не передаёт: включать отладочный журнал ядра во всём
  процессе по слову поставщика незачем (D-11).
- Новая версия ядра — список сверяется заново вместе с остальной
  матрицей (D-24).

**Проверка.** `ShareLinkParserTest.quicDebugFlagIsDroppedWithNote`, файл
корпуса `tests/data/subscriptions/remnawave-fm-debug.txt` (запись с
флагом принимается с находкой).

### D-49 — Личность личной сборки постоянна для ключа: обновления ставятся поверх

Принято 6 октября 2026 по решению автора. Уточняет D-47 (когда меняется
личность) и согласует его с D-35 (ради чего ключ разработчика).

**Почему.** По D-47 каждая сборка `release` получала свежие случайные
`applicationId` и ярлык. Тогда любая новая сборка — другое приложение:
обновить установленное нельзя, подписку и идентификатор устройства
(D-33) приходится заводить заново, а поставщик видит новое устройство.
Ключ разработчика (D-35) нужен именно для обновлений поверх — с
меняющимся пакетом он ничего не даёт. Автор выбрал: имя случайное на
вид, но постоянное.

**Решение.**
- Зерно личности `dppass.identitySeed` для сборки `release` задаёт
  `tools/release/sign_apks.py`: SHA-256 строки
  `dppass-identity:<отпечаток сертификата>:<пароль хранилища>`.
  - Тот же ключ и пароль — тот же `applicationId` и ярлык: следующая
    сборка ставится поверх, данные остаются.
  - Без пароля зерно не вычислить: по открытому отпечатку (§7
    `PROVENANCE.md`) имя пакета не узнать.
  - Зерно передаётся Gradle свойством `-Pdppass.identitySeed`; сборка
    `release` — без кеша конфигурации, иначе он отдал бы прежнюю
    личность.
- Свойства D-47 сохраняются: имя пакета и ярлык не называют ни «VPN»,
  ни «DPpass»; пространство имён кода прежнее; отладочная сборка и
  проверки — со стабильной личностью `com.dpsmpx.dppass`.
- Новый ключ (или новый пароль) — новая личность и новое приложение. Так
  же по D-47 «сменить личность» можно сменой ключа.
- `sign_apks.py` проверяет, что у APK всех ABI один пакет, и пишет пакет
  и ярлык в `CERTIFICATE.txt` и в итог.

**Следствия.** Первая сборка с ключом `dppass-dev` ставится отдельным
приложением рядом с установленной отладочной (`com.dpsmpx.dppass`):
подписку добавить в новом, старое удалить, а прежнее устройство — в
панели поставщика. Дальнейшие сборки — обновления поверх.

**Проверка.** `sign_apks.py` повторяет `AppIdentity` на Python и сверяет
пакет собранного APK с ожидаемым для ключа: не совпало (кеш конфигурации,
свойство не дошло до Gradle) — APK не выходит. Release собирается без
кеша конфигурации, зерно — через `-P`.
`IdentityTest.knownVectorMatchesSignApksCopy` держит обе стороны в
согласии; тесты build-logic — в шаге hostcheck «сборка и тесты ядра».
Сквозная проверка на одноразовых ключах (6 октября 2026): два ключа —
`com.radamome.fasohol` «Opal» (дважды подряд) и `com.hikih.rehilum`
«Compass»; первая попытка (зерно через окружение) дала одно случайное
имя для обоих ключей — так ошибка и найдена.

### D-51 — Раздача туннеля другим устройствам: прокси с паролем на интерфейсах модема

Принято 6 октября 2026 по запросу автора. Пересматривает правило T11
(«локальных входов нет») ровно в той мере, какую T11 оговаривает заранее:
вход — только с аутентификацией и случайным портом.

**Почему.** Автор хочет пускать через туннель DPpass другие свои
устройства — по Wi-Fi (точка доступа), USB или Bluetooth. Android ведёт
трафик клиентов раздачи мимо `VpnService`; без root раздать сам туннель
нельзя (`docs/research/ANDROID_NETWORK_MODEL.md`, §9). Остаётся прокси на
телефоне, который другое устройство указывает у себя.

**Решение.**
- **Выключено по умолчанию.** Включает пользователь в настройках; работает
  только пока туннель поднят и включена системная раздача (точку
  доступа, USB- или Bluetooth-модем включает сам пользователь — стороннее
  приложение не может).
- **Вход ядра** — один на интерфейс: SOCKS5 (с UDP), который на том же
  порту понимает и HTTP-прокси с теми же учётными данными (Xray 26.9.30,
  `proxy/socks/server.go`: первый байт не 4/5 — запрос HTTP):
  - **только на адресах интерфейсов раздачи**, никогда не на `0.0.0.0`,
    loopback, Wi-Fi-клиенте или мобильной сети: иначе прокси был бы
    виден в домашней сети или из интернета. Интерфейс раздачи — поднят,
    широковещательный (не точка-точка), с частным IPv4 и подсетью для
    клиентов (не длиннее /30, целиком внутри RFC 1918) и **не** сеть
    `ConnectivityManager` (`TetherInterfaces`). Сети устройства узнать
    не удалось — входа нет: ошибка в сторону «не раздавать». (17 октября
    2026: сначала — список раздающих интерфейсов от системы, D-57.)
  - **с логином и паролем** (T11): случайные, хранятся зашифрованно
    (D-19, запись `settings/share`, документ `dppass.share` v1; не
    читается — карантин, раздача выключена, пароль новый),
    показываются на экране раздачи (`FLAG_SECURE`), их можно сменить;
  - **порт случайный** (20000…59999), выбирается при включении и
    сохраняется — чтобы не перенастраивать другие устройства.
- **Приложения самого телефона прокси не получают**: первое правило
  маршрутизации пускает на входы раздачи только клиентов из подсетей
  раздачи и не с адресов самого телефона; остальное — блок. Иначе любое
  приложение могло бы обойти через прокси политику приложений (D-38) —
  пароль у него может оказаться. Перечисляется разрешённое, а не
  запрещённое: приложение может привязать сокет к любому адресу
  телефона (Wi-Fi-клиента, loopback). Правила Xray не умеют «кроме» —
  «всё, кроме подсетей раздачи» компилятор строит дополнением
  (`Cidr.complement`).
- **Маршрутизация та же, что у телефона**: правила пользователя,
  раздельный маршрут (D-45), блокировка; «напрямую» — через сеть
  телефона (сокеты ядра защищены, D-25). Правила по приложениям к другим
  устройствам не относятся (их пакетов DPpass не знает).
- **«Напрямую» для раздачи — не на loopback телефона** (T11): у
  приложений телефона трафик на `127.0.0.0/8` через ядро не идёт, а
  клиент раздачи через SOCKS или HTTP мог бы попросить и его — службы,
  которые слушают только loopback, стали бы видны из сети раздачи.
  Поэтому у раздачи свой исходящий `dppass:direct-share`: тот же
  `freedom`, но с `finalRules`, закрывающими `127.0.0.0/8`, `0.0.0.0/8`,
  `::1`, `::` (Xray проверяет и адрес из имени — до соединения и после).
  Перед каждым правилом `direct` — его копия только для входов раздачи
  (`ruleTag` `dppass:share:<id>`), при действии по умолчанию `direct` —
  последнее правило для них же. Общий `direct` не меняется: DNS-сервер
  на 127.0.0.1 с маршрутом «напрямую» у документа остаётся рабочим, а
  без раздачи конфигурация ядра та же байт в байт.
- **Смена интерфейсов** (раздачу включили, выключили, сменился адрес)
  замечается опросом раз в 5 с, пока раздача включена и туннель поднят;
  при смене туннель переподключается с новыми входами: конфигурация ядра
  неизменна во время работы. Пропавший интерфейс — сразу; новый — когда
  виден два опроса подряд: сеть Wi-Fi-клиента в первые секунды может
  ещё не значиться в `ConnectivityManager` и на миг выглядеть
  интерфейсом раздачи. По той же причине и при подключении берутся
  только адреса, видные в двух снимках подряд (через 1,5 с). Включение,
  выключение и смена пароля на экране — тоже переподключение.
- **Вход раздачи не встал** (адрес пропал между снимком и запуском, порт
  занят другим приложением): ядро с её входами не запускается, и та же
  попытка повторяется без раздачи. Это отказ запуска, а не сервера: в
  `HealthBook` и адаптивную модель (D-44) он не идёт; остальные попытки
  — тоже без раздачи. Туннель работает, на экране раздачи — причина.
  Опрос сравнивает интерфейсы с предложенными адресами: тот же набор —
  без переподключения по кругу, другой — новая попытка.
- **Остановка во время подключения** («Отключить», `onRevoke`,
  переподключение) останавливает и ядро, запущенное посреди проверки
  здоровья: иначе оно работало бы без TUN, а вход раздачи — со старым,
  уже сменённым паролем.
- **Мост** (D-25, T11) пропускает вход, кроме TUN, только если это SOCKS
  с тегом раздачи компилятора, с логином и паролем, на частном
  IPv4-адресе и с портом от 1024. Остальное (HTTP-вход, SOCKS без
  пароля, `0.0.0.0`, loopback, чужой тег) — по-прежнему отказ.

**Честные пределы (D-13).**
- Открытый порт на адресе раздачи видят приложения телефона и устройства
  в раздаче — пока раздача включена, это примета прокси (§9 исследования,
  D-46). Об этом сказано на экране.
- Другие устройства должны уметь работать через прокси: HTTP-прокси в
  настройках Wi-Fi (Android, iOS) пароль не передаёт — браузер спросит
  его сам, а остальные приложения могут не работать; надёжнее — клиент с
  SOCKS5 и паролем на том устройстве. Это не «VPN для всего устройства»
  у клиента.
- DNS клиента, если его приложения не идут через прокси, остаётся у
  клиента.

### D-54 — Копия журнала с выключенным журналом — события этого запуска из памяти

  экране в локальном отчёте.
- Выключатель по-прежнему отказывается от записи в файл, а не от
  кольца в памяти; значение по умолчанию — по D-26.

### D-55 — Подключение через устройство раздачи: другой DPpass как сервер

Принято 17 октября 2026 по запросу автора, к D-51, D-11 и T11. Автор
раздаёт туннель с одного телефона (D-51) и хочет подключать другие свои
телефоны с DPpass к нему: вводом адреса, логина и пароля, добавлением
доверенных устройств и выбором одним нажатием среди тех, что рядом, — по
Wi-Fi, Bluetooth и USB.

**Решение.**
- **Устройство раздачи — сервер особого вида.** В IR — протокол
  `ProtocolSpec.Socks` (SOCKS5 с логином и паролем) и класс транспорта
  `LOCAL_RELAY`. Вход раздачи другого DPpass (D-51) — сервер для ядра;
  Xray — исходящий `socks` с паролем.
  - **Адрес — только частный IPv4 своей сети** (RFC 1918): SOCKS
    передаёт логин, пароль и трафик открыто, поэтому в интернет такой
    профиль не пускается (`RELAY_ADDRESS_NOT_LOCAL`). Транспорт — `tcp`,
    без TLS.
  - **Только от пользователя.** В формате документа и в подписке такого
    протокола нет: поставщик не может направить трафик пользователя
    через чужое устройство в его сети (D-11). Устройства живут в своём
    списке — записи `settings/relays` (документ `dppass.relays` v1,
    зашифрованно, D-19; не читается — карантин, список пуст), до 16.
- **Адрес по умолчанию — шлюз сети.** Устройство раздачи — шлюз сети,
  через которую к нему подключён этот телефон: его точки доступа Wi-Fi,
  Bluetooth- или USB-модема. Android выбирает подсеть раздачи сам и
  меняет её от включения к включению, поэтому адрес не запоминается, а
  ищется при подключении. Явный адрес — по желанию, тоже частный IPv4.
- **Поиск без объявлений.** Телефон ничего не рассылает и не объявляет
  в сети (D-47, §9 исследования сети): он берёт шлюзы IPv4 своих сетей
  Wi-Fi, Bluetooth и Ethernet/USB (не VPN) и спрашивает каждый по
  протоколу входа раздачи — SOCKS5 с методом «логин и пароль» (RFC 1928,
  1929), сокетом, привязанным к этой сети. Ответит только вход, который
  знает этот логин и пароль; соединение закрывается сразу после входа.
  Так экран «Устройства раздачи» показывает, какие доверенные устройства
  рядом и по какой сети, а шлюзы без ответа — как «сети рядом», из
  которых устройство можно добавить.
- **Подключение — только через выбранное устройство.** Выбор — одним
  нажатием в списке (туннель есть — переподключение, нет — подключение).
  План — один кандидат; отказ устройства — отказ подключения с причиной
  (`RELAY_NOT_FOUND`, `AUTHENTICATION_FAILED`), другие серверы молча не
  подставляются (D-05). Маршрутизация и DNS — пользователя (свой
  документ, если он действует, иначе политика, D-38); активация не
  меняется — подключение работает и без подписки.
- **Сокеты ядра — в сеть устройства.** С Bluetooth- и USB-модема путь к
  шлюзу не идёт через сеть по умолчанию, поэтому в этом режиме
  защитник сокетов (D-25) ещё и привязывает их к сети устройства
  (`Network.bindSocket`); сеть под туннелем — она же.
- **Опыт не смешивается.** Исход устройства говорит о своей сети, а не
  о сети оператора: обобщение адаптивной модели по классам (D-44) на
  `LOCAL_RELAY` не учится, модель сети в тестах к нему не применяется.
- **Как добавить.** Вручную — имя, адрес (пусто — шлюз), порт, логин,
  пароль с экрана «Раздача туннеля» того телефона; или ссылкой:
  «Поделиться входом» на том телефоне отдаёт
  `socks5://логин:пароль@адрес:порт#имя` в выбранное пользователем
  приложение, а здесь импорт (буфер обмена, «Поделиться», D-42)
  распознаёт её и с согласия пользователя добавляет устройство с адресом
  шлюза. Тот же адрес, порт и логин — обновление, а не копия.
- **Сопряжение без ввода пароля** (обмен ключами с кодом на обоих
  экранах, свой вход у каждого устройства, отзыв доверия) — следующим
  решением: до него устройство добавляется вводом или ссылкой. (17
  октября 2026: принято — D-56.)

**Честные пределы (D-13).** Без шифрования прокси — только своя сеть:
точка доступа с паролем, Bluetooth, USB. На том телефоне должен быть
подключён DPpass и включена раздача (D-51). USB между двумя телефонами
работает, только если этот телефон видит USB-модем другого как сеть
(хост USB с драйвером NCM или RNDIS) — у многих телефонов этого нет;
Bluetooth-модем включается в настройках Bluetooth Android (доступ к
интернету через сопряжённое устройство) — DPpass это сделать не может.

**Проверка.**
- `ProfileValidationTest.relayDeviceIsOnlyPrivateIpv4WithPasswordOverPlainTcp`,
  `ProfileValidationTest.documentCannotCarryRelayDevice`;
- `XrayCompilerTest.relayDeviceCompilesToSocksWithPassword`,
  `XrayJniTest.relayDeviceOutboundPassesFullValidation` (ядро 26.9.30
  принимает исходящий целиком);
- `RelayTest` — ссылка (только частный IPv4, причины без значений),
  распознавание при импорте, хранение и карантин, проверка черновика,
  предел, обновление вместо копии, вход SOCKS5 (принят, отвергнут, не
  SOCKS), подключение только через устройство без активации.

### D-56 — Сопряжение устройства раздачи по коду: свой вход у каждого, отзыв

Принято 17 октября 2026 по запросу автора, к D-55, D-51 и T11. Ввод
порта, логина и пароля с другого экрана неудобен, а общий вход раздачи
нельзя отозвать у одного устройства, не сменив его всем.

**Решение.**
- **Ход сопряжения** — как сравнение чисел при сопряжении Bluetooth
  (Secure Simple Pairing, numeric comparison), на стандартных примитивах
  JDK и Android, без своих TrustManager (T5):
  1. подключающийся телефон («гость») отправляет раздающему («хозяину»)
     открытый ключ P-256;
  2. хозяин отвечает своим ключом и обязательством `HMAC-SHA256(Nh,
     ключ хозяина ‖ ключ гостя)` — случайное Nh закреплено до того, как
     хозяин увидит число гостя;
  3. гость шлёт Ng, хозяин — Nh, гость сверяет обязательство (не
     сошлось — подмена, `PAIRING_BROKEN`);
  4. код — 6 цифр из `SHA-256(ключи ‖ Ng ‖ Nh)`; подмена ключей в
     середине даёт на экранах разные коды, угадать — 1 из 10⁶ за попытку;
  5. пользователь подтверждает совпадение на **обоих** телефонах; только
     тогда хозяин создаёт вход и отправляет его, зашифрованный ключом из
     ECDH (HKDF-SHA256, AES-256-GCM, данные шагов — связанными данными).
     Отказ на любой стороне — входа нет (`PAIRING_REFUSED`).
- **Свой вход у каждого устройства.** Хозяин выдаёт сопряжённому
  отдельный логин и пароль; вход раздачи ядра принимает основной вход и
  входы сопряжённых (`ShareSpec.guests`, логины не повторяются: ядро
  держит входы по логину). Документ `dppass.share` — версия 2 с
  `devices` (имя, логин, пароль, когда сопряжено), до 8; версия 1
  читается как раздача без них. «Убрать» — отзыв доверия только у этого
  устройства; «Новые логин, пароль и порт» убирает всех.
- **Порт сопряжения** — 47521: открывается только нажатием «Сопряжение
  с устройством», не дольше двух минут, **только на адресах раздачи**
  (как вход раздачи, D-51) и принимает одно соединение — одна попытка на
  одно нажатие. Слушает приложение, а не ядро; другого времени и места
  у этого входа нет (T11).
- **Поиск хозяина гостем** — там же, где устройство раздачи (D-55): на
  шлюзе своих сетей Wi-Fi, Bluetooth и USB, сокетом этой сети; ничего не

**Проверка.**

### D-57 — Интерфейсы раздачи — сначала по сведениям системы

Принято 17 октября 2026, к D-51, по проверке на телефоне автора: Redmi
13, Android 15 (API 35), 0.6.7-dev — точка доступа включена, клиент
подключён, а журнал при подключении говорит `share endpoints=0`: по
признакам D-51 интерфейс раздачи не нашёлся, вход раздачи не открылся, и
подключиться к телефону было нечем (ни по D-55, ни сопряжением D-56).

**Решение.**
- Интерфейсы раздачи сначала берутся **у системы**: из её липкой
  рассылки о состоянии раздачи (`android.net.conn.TETHER_STATE_CHANGED`,
  список `tetherArray`) — приёмник не регистрируется, читается только
  последнее состояние (`docs/research/ANDROID_NETWORK_MODEL.md`, §9).
  Названные системой интерфейсы берутся, если они подняты и у них
  частный IPv4 с местом для клиентов; значатся ли они сетью и есть ли
  широковещательный адрес — уже не важно.
- Сведений у системы нет или список пуст — прежние признаки D-51
  (ошибка в сторону «не раздавать» остаётся).
- Раздача включена, а интерфейсов нет — в журнал `share_no_tether`: что
  говорит система и каждый интерфейс с IPv4 — имя, признаки, длина
  префикса, частный ли адрес; **без адресов**. Следующий такой случай
  будет виден из журнала, а не угадываться.

**Почему не только признаки.** Публичный список раздачи в SDK появился
только в Android 16 (`TetheringManager.TetheringEventCallback`, API 36);
до него у приложения есть только эта рассылка, и её отправляет сама
система без разрешения. Признаки остаются для устройств, где рассылки
нет.

**Проверка.** `TetherInterfacesTest.systemNamedInterfacesWinOverHeuristics`
(названный системой — даже если значится сетью и без широковещания;
IMS и выключенный — нет; только частный IPv4), прежние тесты признаков.

### D-58 — Сбой выбранного сервера: вопрос с причиной, переход — с согласия; тумблер «Автопереключение»

Принято 17 октября 2026 по решению автора, к D-34 и D-44, по проверке на
телефоне (Redmi 13, Android 15, 0.6.8-dev): выбранный автором сервер
подключался, через 30–40 с пробы наблюдателя (D-44) падали по 8 с,
наблюдатель переподключал — и снова к нему же. Выбор пользователя в
плане первый (D-34), а «последний удачный» шёл вторым, поэтому и в режиме
«Автоматически» новый план начинал бы с того же сервера: обещание D-44
«модель понизила отказавший сервер, берётся другой» не выполнялось.

**Решение.**
- **Подтверждённая деградация — отказ в журнале здоровья.** Когда
  наблюдатель решает переподключиться, сервер получает отказ с кодом
  последней проваленной пробы (`HealthBook.recordFailure`): он перестаёт
  быть «последним удачным» и уходит на паузу D-15. В режиме
  «Автоматически» новый план начинает с другого кандидата.
- **Выбранный пользователем сервер молча не заменяется** (D-05, D-34).
  DPpass показывает причину и предлагает замену — первого кандидата
  плана без выбора пользователя (`DPpassCore.degraded`):
  - уведомление «Сервер перестал отвечать» с причиной и кнопками
    «Перейти» и «Остаться»; то же — карточкой на экране «Подключение»,
    если уведомления выключены;
  - пока ответа нет, всё как прежде: переподключение к выбранному
    (D-34), не чаще предела наблюдателя;
  - «Перейти» — замена становится выбранным сервером, переподключение;
  - «Остаться» или смахнутое уведомление — больше не спрашивать об
    этом сервере до остановки туннеля.
- **Тумблер «Автопереключение»** («Настройки», «Подключение»; выключен по
  умолчанию) — согласие заранее: DPpass сам делает замену выбранным
  сервером и сообщает уведомлением, с какого на какой и почему.
- **Не спрашивается**, когда спрашивать не о чем: выбран режим
  «Автоматически», подключение через устройство раздачи (D-55: другие
  серверы не подставляются), замены нет (сервер один или остальные на
  паузе и исключены).
- **На заблокированном экране** — без имён серверов и без кнопок (T9):
  «Сервер перестал отвечать»; выбор — после разблокировки.
- **Канал уведомлений** — отдельный («Смена сервера»), его можно
  выключить, не трогая уведомление туннеля.

**Почему не переходить молча всегда.** Пользователь выбирает сервер не
только по устойчивости: страна, поставщик, тариф. Замена без согласия
меняла бы смысл его выбора (D-05). Согласие заранее — тумблер, и он
выключен, пока пользователь сам его не включит.

**Проверка.** `DegradationTest` — отказ снимает «последний удачный» и в
«Автоматически» план начинает с другого; выбранный сервер — вопрос, с
тумблером — замена; «Остаться» — без вопроса; устройство раздачи, один
сервер — без вопроса; на устройстве — `TODO.md`.

### D-59 — Отказ через устройство раздачи — своя причина

Принято 17 октября 2026, к D-55, по проверке на телефонах (Redmi 13 и

### D-60 — Пробы сети на устройстве: свои ориентиры, по просьбе пользователя, мимо туннеля; в план — после сверки

Принято 17 октября 2026, этап 3 (работа 3, `docs/direction/ROADMAP/03-device.md`),
к D-14. Факты — `docs/research/RUSSIA_NETWORK_RESTRICTIONS.md` (сверено
17 октября 2026, §4, п. 8).

**Почему.** Классификация сети D-14 проверена только на модели: пробы
выполняла `SimulatedNetwork`. Критерий выхода этапа 3 — классификация на
устройстве совпадает с моделью на тех же условиях. Для этого нужен
исполнитель проб на настоящих сокетах, и его поведение само не должно
быть сигналом фильтру (L7) и не должно ничего сообщать о пользователе
(D-12).

**Решение.**
- **Исполнитель** — `SocketProber` (модуль `network/`, чистый JVM; сеть,
  резолвер и сокеты — снаружи, `ProbeNetwork`). Виды проб:
  - DNS — системным резолвером сети (как у ядра, D-29); только
    частные, служебные или нулевые адреса в ответе — подмена;
  - TCP — соединение с портом 443;
  - TLS — рукопожатие с SNI ориентира и **платформенной** проверкой
    сертификата и имени (T5: ни своего `TrustManager`, ни отключения
    проверки);
  - UDP — **настоящий QUICv1 Initial** с SNI ориентира (RFC 9000, RFC 9001):
    фильтр расшифровывает именно его и решает по SNI, пакет другой
    версии сказал бы «проходит» там, где Hysteria2 не пройдёт; любой
    ответ сервера на этот пакет — «прошло», рукопожатие не доводится;
  - крупная передача — HTTPS-запрос 64 КБ: пришло ≥ 32 КБ — прошло,
    данные встали после начала — «замерзание» (L4, L7);
  - страница входа — **по сведениям системы** (на Android
    `NET_CAPABILITY_CAPTIVE_PORTAL`): своего HTTP-запроса нет.
- **Ориентиры** (`Landmarks`, меняются только решением):
  - отечественный — `ya.ru`: из типичного белого списка (L9), отличает
    «внутрь можно, наружу нельзя» от «нельзя никуда»;
  - зарубежный — `speed.cloudflare.com`: сеть доставки, где наблюдалось
    ограничение 16 КБ, и адрес `/__down?bytes=` с заданным объёмом для
    крупной передачи.
- **Мимо туннеля**: сокеты проб — в сети под туннелем (`Network`), как и
  весь пакет DPpass (D-17). Проба меряет сеть, а не сервер.
- **Когда** — только по кнопке «Проверить сеть» (экран «Проверка сети»).
  Бюджет D-14 общий на процесс: по одной, пауза к ориентиру, предел за
  окно. Одна оценка — два TLS-рукопожатия и один QUIC Initial к
  зарубежному ориентиру: меньше порога «заморозки по отпечатку» (L7).
- **Что видно**: класс сети, уверенность и доводы, исход и время каждой
  пробы — на экране и в журнале (`network_probe`, `network_assessed`) —
  **без адресов**.
- **В план подключения (D-15) и в контекст адаптивной модели (D-44)
  оценка пока не идёт.** Эвристика проверена только на модели;
  ошибочный вывод («UDP не проходит») исключил бы рабочих кандидатов.
  Сначала — сверка на устройстве в разных условиях (критерий выхода
  этапа 3), подключение к плану — отдельным решением по её итогам.
- **Приватность** (D-12): в пробах нет ничего о пользователе и
  устройстве. Ориентиры видят адрес телефона, как при открытии сайта;
  в HTTP-запросе — только `Host`, собственный `User-Agent` DPpass без
  версии и `Connection: close`. Это сказано в «О программе» и на экране
  проверки.

**Проверка.** `SocketProberTest` — исходы проб на локальных серверах
(успех, отказ, тайм-аут, подмена DNS, «замерзание» передачи, ответ и
молчание по UDP); `QuicInitialTest` — ключи и маска заголовка по
векторам RFC 9001, приложение A; размер, версия и SNI пакета; ответ
сервера отличается от чужого пакета; `code.forbidden` (`dns-resolve`,
`weak-crypto` — разрешены только файлы проб); на устройстве — `TODO.md`.

### D-61 — Скорость, пинг и jitter через туннель — по кнопке, с пределом трафика

Принято 17 октября 2026 по просьбе автора, к D-60: в проверку соединения —
тест скорости, пинга и jitter.

**Решение.**
- **Что меряется — путь приложений в туннеле**: через исходящий `proxy`
  работающего ядра, мимо правил маршрутизации — тем же путём, что проба
  здоровья D-32 (`bridge.SpeedTest`). Мимо туннеля это не меряется: процесс
  DPpass вне своего туннеля (D-17), а зарубежный ориентир в сети оператора
  может быть недоступен вовсе (`TODO.md`, проверка 17 октября).
- **Как**: одно TLS-соединение (платформенные корни, проверка сертификата
  всегда, T5) к `speed.cloudflare.com` — ориентиру D-60:
  - 10 малых запросов (`/__down?bytes=0`) по очереди по уже открытому
    соединению: **пинг** — медиана времени до ответа, «лучший» — минимум;
  - **jitter** — среднее модулей разностей соседних пингов (так считают
    измерители скорости; RFC 3550 сглаживает поток, а здесь десять замеров);
  - одна загрузка — **не больше 25 МБ и не дольше 8 с**; **скорость** —
    биты тела за время его передачи.
  - Одно рукопожатие на замер — не залп (L7).
- **Когда** — только по кнопке «Измерить скорость» и только с поднятым
  туннелем; один замер за раз. На экране сказано, сколько трафика уйдёт:
  на мобильной сети международный трафик сверх лимита платный
  (`docs/research/RUSSIA_NETWORK_RESTRICTIONS.md`, §1, 2026-04 – 05).
- **Наблюдатель сессии (D-44) на время замера пропускает пробы**: нагрузка
  замера не должна выглядеть деградацией сервера и переключать его (T14).
- **Итог** — на экране и в журнале (`speed_test`: пинг, jitter, скорость,
  байты, время — без адресов); в адаптивную модель и в план не идёт.
- Ориентир видит адрес сервера, а не телефона; в запросе — `Host`,
  `User-Agent` DPpass без версии.

**Проверка.** Go: `TestSpeedTestPingsThenDownloadsThroughProxy`,
`TestSpeedTestStopsAtTimeLimit`, `TestSpeedTestOutcomes` (через proxy и
защитника, срок загрузки, не 200, чужой сертификат, «встало», договор);
`XraySpeedTest` (медиана, jitter, скорость, отказы, договор ответа моста);
`XrayJniTest.speedTestGoesThroughProxyAndKeepsTheContract`; на устройстве —
`TODO.md`.

**Уточнение (17 октября 2026, по просьбе автора).** Между замерами — пауза,
и пользователь её видит: кнопка недоступна, на ней — «через N с», отсчёт
раз в секунду. Скорость — 60 с после замера (и после прерванного: трафик
ушёл), 15 с после отказа (можно сменить сервер и повторить); пауза одна на
процесс, уход с экрана её не сбрасывает (`Cooldown`, `CooldownTest`).
Проверка сети (D-60) — пауза из бюджета проб D-14: кнопка доступна, когда
полная проверка в него уложится (`ProbeBudget.waitForMillis`).

**Уточнение (17 октября 2026, по замерам на телефоне).** Средняя скорость
не отличает медленный канал от вставших данных: дважды подряд пришло
~237 КБ за 8 с — ровно столько и на других серверах. Мост отдаёт ещё время
последнего байта загрузки; если до конца срока после него не пришло ни
байта 2 с и больше (`XraySpeed.STALL_GAP_MILLIS`), итог говорит «данные
встали через N с» и скорость до остановки (`SpeedReport.stalledAfterMillis`,
`activeBitsPerSecond`; `TestSpeedTestSeesDataStoppingMidTransfer`,
`XraySpeedTest.dataStoppingEarlyIsAStallNotASlowLink`). Загрузка — одно
соединение: так её видит одно соединение приложения; измерители с
несколькими потоками (LibreSpeed) «заморозку» одного соединения сглаживают.

**Уточнение (17 октября 2026, по журналам телефона).** Пауза наблюдателя
только на время замера мала. Трижды подряд (14:27, 14:30, 15:33,
0.7.2–0.7.4-dev) сразу после замера скорости проба наблюдателя падала по
сроку 8 с. И каждый раз она шла вместе с проверкой сети (D-60), которую
автор запускал следом. Между замерами пробы проходили. Что именно мешает —
очередь в канале после загрузки или пробы мимо туннеля, — по журналу не
отделить, но в обоих случаях исход мерит сам замер, а не сервер.
Поэтому окно тишины (`network.QuietWindow`, `NetworkCheck.probesQuiet`)
теперь шире:
- оно открыто, пока идёт замер скорости или проверка сети, и ещё **15 с**
  после (`NetworkCheck.QUIET_AFTER_MILLIS`);
- в окне наблюдатель пробу не начинает (`adaptive_probe_skipped`);
- пробу, во время которой окно открылось, не учитывает
  (`adaptive_probe_discarded`): ни в модель устойчивости (D-44), ни в
  решение о переподключении.

Ложный провал опасен вдвойне: он снижает «устойчивость» сервера в
сохранённой модели, а два подряд (`StabilityModel.SWITCH_STREAK`) могут
привести к переподключению и смене выбранного сервера по D-58 (T14).
Проверка — `QuietWindowTest`, в том числе ход 14:30; на устройстве —
`TODO.md`.

### D-62 — Второй зарубежный ориентир: закрытый поставщик — не белый список

Принято 17 октября 2026, к D-60, по проверке на телефоне автора (Redmi 13,
мобильная сеть, 0.7.0–0.7.2-dev, `TODO.md`): соединение с ориентиром
`speed.cloudflare.com` сбрасывается сразу, QUIC к нему молчит, а его имя
резолвится; в те же минуты сервер автора VLESS + REALITY у другого хостера
отдавал 24 Мбит/с. Один зарубежный ориентир не отличает «закрыты адреса
одного поставщика» (L4) от «закрыто всё зарубежное» (L9), а правило 4
требовало ещё и отказа DNS, которого у этого оператора нет.

**Решение.**
- **Второй зарубежный ориентир** `www.google.com` (`ProbeTarget.FOREIGN_ALT`)
  — у другого поставщика, чем сеть доставки: пробы TCP, TLS и QUIC, без DNS
  (имя резолвит проба соединения) и без крупной передачи. Пробы к двум
  ориентирам — вперемежку; оценка — 11 проб, в бюджете D-14 (12 за минуту).
- **Что сеть пропускает наружу** (`tcp`, `tls`, `udp` оценки) — лучшее из двух
  ориентиров: закрытый поставщик не делает «TCP не проходит» вообще.
- **Один закрыт, другой открыт** — довод «закрыты адреса поставщика (L4)»,
  класс `DEGRADED`.
- **Белый список (правило 4)**: отечественное доступно, а зарубежное не
  отвечает по TCP и TLS. Отказ DNS обязателен, только когда зарубежный
  ориентир один (старые наблюдения); при двух — нет, и тогда уверенность
  не выше средней: такой белый список не совпадает с описанным (L9).
- **Модель сети** — новое условие `PROVIDER_BLOCKED`: ориентир сети доставки
  сбрасывает соединения, второй и серверы вне списка заблокированных
  работают. Наблюдение с телефона — файл корпуса
  `network/observations/cdn-landmark-refused-mobile.json`.
- Ориентир видит адрес телефона, как при открытии сайта; HTTP-запроса к нему
  нет — только рукопожатия.

**Почему Google.** Крупный зарубежный сервис не у сети доставки, с QUIC и
без блокировки в обычной сети (на октябрь 2026), но не из белых списков
(L9). Если его закроют отдельно, это и будет довод L4 — ориентир меняется
решением.

**Проверка.** `SecondLandmarkTest` (закрыт поставщик — L4; закрыты оба при
резолвящихся именах — белый список со средней уверенностью; без второго
ориентира — как раньше), `NetworkClassifierTest.table` (`PROVIDER_BLOCKED`),
`CorpusTest.networkObservations`, корпус условий сети.

**На телефоне (17 октября 2026, 0.7.3–0.7.4-dev).** С двумя ориентирами
проверка семь раз сказала «похоже на белый список» (оба зарубежных — сброс,
имена резолвятся), и автор подтвердил, что белые списки действовали
(`TODO.md`; корпус `network/observations/allowlist-mobile-confirmed.json`).

же белый список, а не закрытый поставщик: с одним ориентиром проверка честно
не могла сказать больше «что-то ограничивается».

### D-63 — Форматтер Kotlin — ktlint в стиле IntelliJ, строка до 160 символов

Принято 17 октября 2026 по долгу из `TODO.md` («форматтер не выбран»: 78
строк длиннее 160 символов, самая длинная — 257); выбор — по чек-листу D-18.

**Зачем.** `check_format.py` и `format.text` проверяют только минимумы
текста. Длину строк и переносы никто не держал: строки длиннее 160 символов
появлялись и в новом коде. Стиль, который держит человек, а не проверка,
расползается.

**Решение.**
- **Инструмент — ktlint 1.8.0** (Pinterest, MIT), стиль `intellij_idea`.
  Он ближе всего к нынешнему коду, а в `gradle.properties` уже
  `kotlin.code.style=official`.
- **Правила — в `.editorconfig`.** Строка — не длиннее 160 символов.
  Выключены правила переносов, которые спорят с принятым стилем: вызов,
  сигнатура, короткая лямбда и ветка `when` остаются одной строкой, пока
  она не длиннее 160 символов. Причина каждого выключенного правила — там
  же, рядом с ним. Остальные правила стандартного набора включены:
  отступы, порядок импортов, пустые строки, висячие запятые, переносы
  вокруг многострочных лямбд и другие.
- **Подключение.** ktlint берётся одним файлом: вариант с классификатором
  `all`, без транзитивных зависимостей. Конфигурация своя, в корневом
  `build.gradle.kts`, и разрешается только задачами `ktlintCheck`
  (проверка, шаг `project.build`) и `ktlintFormat` (исправление). Сборке
  APK и `cli` он не нужен и в них не попадает. Сумма SHA-256 — в
  `gradle/verification-metadata.xml`; она совпала с опубликованной на
  Maven Central.
- **Весь код приведён к правилам в том же изменении.** Автоисправления
  ktlint и ручной перенос длинных строк идут отдельным коммитом, без
  изменения смысла. Корпус `tests/data/` не трогается.

**Отвергнуто.**
- **ktfmt** (Meta, Apache-2.0) — без настройки: переписал бы весь код в
  свой стиль, с другой шириной строки и другими переносами.
- **Spotless** — обёртка: дала бы плагин сборки со своими зависимостями,
  а нужен один ktlint.
- **Базовый список старых нарушений** (baseline ktlint) — он
  привязан к номерам строк и после любой правки файла выдаёт старые
  нарушения за новые.

**Проверка.** `ktlintCheck` в шаге `project.build`
(`tools/hostcheck/steps.sh build`); `check_dependencies.py` — строки
матрицы и PROVENANCE той же версии и суммы в
`gradle/verification-metadata.xml`. Обновление ktlint — по D-18; заодно
проверить, что парсер ktlint понимает используемый синтаксис Kotlin (в
1.8.0 — парсер Kotlin 2.2, код DPpass разобран без ошибок).

### D-64 — Режим сети: белый список по свежей проверке — мягко, с отдельным опытом

Принято 17 октября 2026 по просьбе автора, к D-60 (подключение оценки к
плану — «отдельным решением после сверки»), D-15 и D-44.

**Почему.**
- **Опыт смешан.** DPpass помнит, какие серверы работают, одним общим
  опытом: оценка в план не шла (D-60), и все наблюдения лежали в контексте
  «сеть неизвестна». Опыт под белым списком и в обычной сети смешивался.
  План начинал с «последнего удачного» — часто с сервера, который под
  списком сбрасывается.
- **Распознавание белого списка сверено.** На телефоне 17 октября оно
  совпало с моделью: 7 проверок, автор подтвердил список (D-62). Другие
  классы ещё не сверены.
- **Режим меняется.** Со слов автора, 17.10.2026: белые списки иногда
  выключают, и тогда доступны почти все серверы подключения. Без белых
  списков обычно действуют чёрные (YouTube, Telegram и др.), так что
  туннель нужен и тогда.

**Решение.**
- **Память о режиме** (`RegimeMemory`). Хранит итог последней проверки
  сети (D-60) и непрозрачный ключ сети (`Network.getNetworkHandle()`).
  Живёт только в памяти процесса: ни итога, ни сети нет ни на диске, ни
  в журнале (D-12). В план идёт **только белый список** и только пока он:
  - **свежий** — моложе 30 минут (`RegimeMemory.TTL_MILLIS`; ориентир, не
    замер);
  - **в той же сети** — смена сети, например Wi-Fi ↔ мобильная, делает
    режим неизвестным;
  - **не сменён** — новая проверка с другим итогом заменяет прежний;
  - **не опровергнут** — подключился сервер, который под списком чаще
    отказывал, чем работал (`DPpassCore.failingUnder`): список, скорее
    всего, выключили. Режим забывается (`network_regime_dropped`), и
    порядок снова общий.
- **Мягко: порядок, без исключений.** Жёсткое исключение неотмеченных
  кандидатов при белом списке (D-15) остаётся только для оценки,
  переданной в план явно; режим из памяти никого не исключает. Список
  включают и выключают без предупреждения, серверы подписок не отмечены
  как доступные из него, а исключение отрезало бы и рабочие CDN.
- **Порядок под белым списком.** Сразу после выбора пользователя (D-34) —
  опыт под списком: устойчивость в его контексте. Он стоит выше
  «последнего удачного» и здоровья: те общие для всех режимов, а под
  списком закрыто то, что в обычной сети работает. Причина — в плане и
  на экране «Почему этот сервер»: «под белым списком работал»,
  «отказывал» или «ещё не пробовался».
- **Отдельный опыт.**
  - Попытки подключения и пробы наблюдателя (D-44) под режимом
    записываются в контекст белого списка, а общий опыт не трогают.
  - Под списком опыт других сетей не переносится: сервер без опыта под
    списком судится по обобщению класса (`TransportAdvisor`).
- **Через устройство раздачи** (D-55) режим не применяется: путь идёт по
  своей сети, а не по сети оператора.
- **Проверка сети по-прежнему только по кнопке** (D-60). Автоматическая
  проверка при каждом подключении отвергнута: ориентиры видели бы адрес
  телефона при каждом подключении. Вернуться к ней — после сверки
  остальных классов на телефоне.

**Проверка.** `RegimeTest`:
- память — свежесть, та же сеть, новая проверка, забывание;
- под режимом опыт под списком идёт раньше «последнего удачного», никто
  не исключён, выбор пользователя — первым, жёсткая оценка по-прежнему
  исключает;
- опыт других сетей не переносится;
- попытки под режимом записываются отдельно, и опровержение видно.

На телефоне — `TODO.md`.

### D-65 — QR с картинки: распознавание ZXing core, без камеры

Принято 18 октября 2026 по решению автора, к D-42 (QR — «позже»).
Версия 0.7.10-dev (`app/build.gradle.kts`).

**Почему.** Поставщики подписок показывают QR-код: на сайте, в боте, на
экране другого телефона. Сейчас его можно только переписать руками.
Камера требует нового разрешения (`CAMERA`) и Camera2 без AndroidX
(D-34). Картинку — снимок экрана, фото, файл — можно прочитать без
разрешений, а снимок экрана — самый частый случай.

**Решение.**
- **Откуда.** «Добавить» → «QR-код с картинки» — системный выбор
  изображения (`ACTION_OPEN_DOCUMENT`, `image/*`), без разрешений.
  «Поделиться» картинкой — второй фильтр `SEND` у `MainActivity`
  (`image/*`). Камера — позже, отдельным решением.
- **Распознавание.** ZXing core 3.5.4 (Apache-2.0, без зависимостей),
  только формат QR, светлый код на тёмном фоне тоже. Только в `app/`:
  больше он никому не нужен. Свой распознаватель — много кода и риск
  ошибок разбора. ML Kit и Google Code Scanner — сервисы Google (D-12,
  D-20).
- **Дальше — как текст.** Распознанное идёт тем же путём, что буфер
  обмена (D-42): распознавание, сводка, подтверждение (T13). Ни картинка,
  ни текст нигде не сохраняются и в журнал не пишутся.
- **Пределы.** Файл — не больше 32 МиБ. Картинка читается с уменьшением
  до 2048² пикселей (`QrImage.sampleSize`): снимок экрана телефона
  читается целиком, фото — уменьшенным. Память и время разбора
  ограничены, какой бы ни была исходная.
- **Отказ — с причиной.** Нет кода — `IMPORT_QR_NOT_FOUND`; не картинка
  или больше предела — `IMPORT_IMAGE_UNREADABLE` (D-22).

**Проверка.**
- `QrImageTest`:
  - текст как есть: UTF-8, переводы строк;
  - код на снимке экрана 1080×2400;
  - светлый код на тёмном фоне;
  - «не найден» на пустой картинке, шуме и пустом коде;
  - пределы уменьшения.
- `check_manifest.py` — у `MainActivity` фильтры запуска, `SEND
  text/plain` и `SEND image/*`.
- `check_apk.py` — классы `com.google.zxing` утверждены, ZXing назван в
  уведомлениях.
- `check_dependencies.py` — строки матрицы и PROVENANCE, суммы в
  `gradle/verification-metadata.xml`.

### D-66 — IPv6 через сервер: проба выхода и строка на экране, без смены маршрута

Принято 18 октября 2026 по решению автора (вариант 2 из `TODO.md`:
«начать со строки»). Версия 0.7.11-dev (`app/build.gradle.kts`).

**Почему.** 17 октября 2026 через Hysteria2 автора сайты только с IPv6 не
открывались по тайм-ауту, а сайты с IPv4 и IPv6 открывались сразу. По
исходникам Xray 26.9.30 ждёт сам сервер: у него, видимо, есть адрес
IPv6, но нет выхода (`TODO.md`). Клиент этого заранее не знает, а
молча выключать IPv6 нельзя (D-05). Сначала — показать, что сервер IPv6
не выпускает. Что делать дальше (маршрут, DNS), решит автор.

**Решение.**
- **Проба** (`XrayIpv6`). Запрос DNS по TCP через сервер профиля к адресу
  IPv6 открытого резолвера — через исходящий `proxy`, в обход
  маршрутизации, как проба здоровья (D-32); мост уже умеет
  (`ProbeDNS`, `tcp://[…]:53`). Ориентиры — Cloudflare и Google, те же
  операторы, что у проверки сети и замера (D-60…D-62). Они видят адрес
  сервера, а не телефона; запрос «. NS» ничего не говорит о пользователе
  (D-12). Срок пробы — 5 с.
- **Итог.**
  - Ответ по IPv6 от любого из двух ориентиров — «выпускает».
  - Оба ориентира IPv6 не ответили (отказ или данные не пошли) — проба
    IPv4 к первому ориентиру через тот же сервер. Ответил — «не
    выпускает»; нет — «не понять»: сбой сервера не должен выглядеть
    отсутствием IPv6.
  - Ответ не DNS, ядро не запущено, отказ договора — «не понять» сразу.
  - Не больше трёх проб.
- **Когда.** Раз за сессию, после удачной пробы наблюдателя (D-44): сервер
  сейчас работает. Не во время своих замеров (`QuietWindow`, D-61). Итог
  «не понять» — ещё попытка в следующий раз, всего до трёх. Не через
  устройство раздачи (D-55) и не когда TUN не берёт IPv6
  (`Ipv6Mode.BLOCKED`). В модель устойчивости проба не идёт.
- **Где видно.** «Почему этот сервер» — строка под последним подключением,
  пока сессия та же: «выпускает», «не выпускает: сайты только с IPv6 не
  откроются, будут ждать до тайм-аута» или «проверить не удалось»; в
  журнале — `ipv6_egress` с исходом и временем каждой пробы (с 0.7.12-dev),
  без адресов.
- **Чего нет.** Маршрут, DNS и `Ipv6Mode` итог не меняет. Быстрый отказ
  IPv6 для такого сервера не понадобился: на телефоне отказ и так быстрый
  (ниже).

**На телефоне** (автор, 18.10.2026). У трёх серверов автора (HTTP/CDN,
Hysteria2, TCP) — «не выпускает»: пробы IPv6 отказывают за 1,1…1,7 с, IPv4
отвечает за 0,1…0,7 с. В браузере сайт только с IPv6 (ipv6.google.com)
сразу показывает «Соединение было сброшено», а не ждёт. «Тайм-аут» видел
только test-ipv6.com: так этот тест называет неудачу сам. Быстрый отказ
не нужен: отказ и так быстрый.

**Проверка.**
- `XrayIpv6Test` — порядок проб; «не выпускает» только при ответе IPv4;
  ответы не про путь — «не понять» сразу.
- `XrayProxyEngineTest.ipv6ProbeGoesThroughTheRunningCoreToIpv6LiteralsThenIpv4`.
- На устройстве — `TODO.md`, «На устройстве».
